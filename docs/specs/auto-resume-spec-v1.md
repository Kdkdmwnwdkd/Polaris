# 规格：自动续跑（进程被杀后，接着把上次的事做完）

> 状态：**已实现**（2026-11-14）｜实现位置：`core/agent/AutoResumePolicy.kt` +
> `app/.../ui/ChatViewModel.kt` 的 `autoResumeIfPossible`
> 验证：`scripts/qa/run-auto-resume-verification.sh`（11 条结构 + 39 条行为）

---

## 0. 一句话

进程被系统回收之后，用户下次打开 App，**助手自己把上次没做完的事接着做完**，
不用他记得「我还有个任务」，也不用他打字说「继续」。

---

## 1. 问题

`AgentRunService`（前台服务）早就有了，它解决的是「别被杀」：

> 前台服务**只能防「系统回收」，防不了「用户强行停止」或「设备断电重启」**。

但真机上被杀的路径远不止一条：低内存回收、后台限制、`START_STICKY` 重建失败、
用户划掉任务。进程一没，那一轮协程就没了——**没有可重放的执行栈**。

改造前的行为是「不失忆，但也不自己动」：

| 已有能力 | 位置 | 效果 |
|---|---|---|
| 运行态落盘 | `AgentRunStateStore` | 知道上次做到第几步、做过哪些工具 |
| 冷启动对账 | `reconcile()` | 把 `running` 改写成 `interrupted`，给一句提示 |
| 续跑上下文 | `buildResumeContext()` | 用户说「继续」时，把进度摘要拼进下一轮请求 |
| 孤儿调用提示 | `TurnJournal` / `recoverInterruptedJournal` | 提示「某个写操作可能已经生效，别重做」 |

也就是说：**能力全齐了，只差最后一步没人推**。用户要自己打两个字。

用户不会打。这正是「桌面助手」这个产品的全部意义——它该在用户回来时就在那儿，
而不是等着用户想起来自己曾经交代过一件事。

---

## 2. 方案

冷启动对账拿到 `interrupted` 之后，**替用户发一句「继续」**。

### 2.1 为什么是「代发一句『继续』」而不是「恢复执行栈」

因为根本没有执行栈可恢复。Agent 回合跑在进程内的协程里，进程死了，
函数帧、局部变量、等待中的 IO 全没了。能恢复的只有**对话历史**——
它已经落盘了。

所以自动续跑在语义上是**重放**：让模型看着已完成的历史和进度摘要，
自己判断「接着做什么」。这不是缺陷，而是这件事的本质。

> 由此带来一条硬约束：**重放可能重复已完成的副作用**。
> 这一条已由既有的 R1 孤儿调用机制兜住——它会把「越过了执行边界但没记到结果」的
> 工具调用列出来，注入下一轮，提醒模型先核对再动手。自动续跑复用同一个 `send()`
> 入口，因此这段提示**照样会被注入**（见 §5.3）。

### 2.2 执行路径

```
冷启动
  └─ IO 协程：reconcile()  → running 变 interrupted，落盘
       └─ complete(interrupted)            ← runStateReady（Deferred）
类体末尾的 init                              ← 这里所有字段都已初始化
  └─ await() 拿到结论
       └─ AutoResumePolicy.decide(...)     ← 纯函数，core，JVM 可测
            ├─ RESUME       → markAutoResumeAttempt() → input="继续" → send()
            └─ PROMPT_ONLY  → 只显示一句「为什么没自动跑」
```

**为什么必须绕 `runStateReady` 这个 Deferred**：对账在第 991 行那个 `init` 里、跑在 IO 线程；
而自动续跑要用 `_activeConversationId`（第 1150 行才初始化）和 `modelReady`。
直接在那个 init 里跑，低端机上 IO 协程会抢在属性初始化之前执行——
**2026-11-09 模拟器上就是这么 NPE 的**。用 Deferred 把「结论」和「执行」拆开，时序问题消失。

**为什么复用 `send()`**：续跑上下文拼接、历史构造、前台服务、运行态落盘、打断仲裁，
这五件事任何一处抄错都比功能本身更难查。复用现成路径，它们一个都不用重写。

代价是界面上会多一条用户气泡「继续」。它确实是应用替用户表达的意思，
而且顶部提示会同时写着「已自动继续」，不会被误认为是自己打的。

## 3. 决策表

判定全部在 `AutoResumePolicy.decide()`，一个**纯函数**：同样输入永远同样输出，
不读时钟、不做 IO。理由枚举 `AutoResumeReason` 有 11 个取值，逐个对应一种真实现场。

| 判据 | 结果 | 理由 |
|---|---|---|
| 一切就绪 | **RESUME** | `OK` |
| 磁盘上没有运行态 | SKIP | `NO_STATE` |
| 状态不是 interrupted | SKIP | `NOT_INTERRUPTED` |
| 此刻已有回合在跑 | SKIP | `BUSY` |
| 用户关了开关 | SKIP | `DISABLED` |
| 没留下原始请求 | PROMPT_ONLY | `NO_PROMPT` |
| 已自动续跑 ≥ 2 次 | PROMPT_ONLY | `ATTEMPT_LIMIT` |
| 中断超过 24 小时 | PROMPT_ONLY | `TOO_OLD` |
| 会话已被删除 | PROMPT_ONLY | `SESSION_MISSING` |
| 当前打开的不是那个会话 | PROMPT_ONLY | `OTHER_SESSION` |
| 没有可用模型 | PROMPT_ONLY | `NO_MODEL` |

### 3.1 为什么是三态而不是两态

`SKIP` = 什么都不做；`PROMPT_ONLY` = **不跑，但要说话**。

分三档的原因是：冷启动时已经有一条通用提示（`AgentRunState.note`，
「……可以直接说『继续』」）。当「说继续」**并不管用**时——会话被删了、没有模型——
那条通用提示就是误导。`PROMPT_ONLY` 的作用是**覆盖**它。

反过来，用户自己关了开关时用 `SKIP`：原提示已经够用，不必再补一句。

### 3.2 判定顺序

先判「能不能跑」（状态 / 未完成 / 不忙），再判「该不该跑」（开关 / 熔断 / 时效），
最后判「跑得成吗」（会话 / 模型 / 有没有原始请求）。

顺序反了会出现「明明正在跑别的任务，却弹一句『上次任务已过期』」这种噪声。

### 3.3 熔断：为什么上限是 2

最凶的失败模式是**死循环**：任务本身把内存撑爆 → 被杀 → 自动续跑 → 再被杀 → …

上限取 2 而不是 1：系统在低内存下可能连着杀两次（第一次杀进程、第二次杀刚重建的进程），
只给 1 次会让功能在最该生效的场景里失效。
取 2 而不是更多：同一个任务连杀 3 次，基本可以断定「它一跑就会被杀」，
再续只是在烧 token 和电，应该把问题交回给用户。

计数 `autoResumeAttempts` 随运行态一起落盘，**跨进程存活**——不落盘的话，
每次冷启动计数归零，熔断形同虚设。

## 4. 开关

设置 → 通用 → **自动续跑**，默认**开**。

默认开的理由：功能的价值就是「不用记着手动接着做」，默认关等于没做。
但它每次触发都是一次真实请求，所以必须可关——关掉之后行为退回改造前：
只提示「可以说继续」，不自动发。

---

## 5. 已知边界

### 5.1 它是重放，不是恢复

见 §2.1。副作用可能重复，靠 R1 孤儿提示兜底。

### 5.2 只在「当前会话」自动跑

不自动切会话。冷启动打开的不是那个会话时，给提示让用户自己切过去。
自动切会话会在用户正在看别的对话时把人带走，得不偿失。

### 5.3 依赖已有的续跑上下文

`buildResumeContext()` 要求状态里有 `prompt`。prompt 为空（老数据、或写入中途被杀）
时判定为 `NO_PROMPT`，不跑——模型只收到一句「继续」而不知道要继续什么，比不跑更糟。

### 5.4 24 小时窗口

隔夜回来接着跑是合理的（用户就是回来继续的）；隔三天回来还被自动扣一次钱，就说不通了。
