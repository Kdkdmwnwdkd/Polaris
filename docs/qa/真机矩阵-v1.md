# 真机矩阵 v1（L3）

> 架构方案 §5.1 的第三层：**模拟器永远测不出来的那些**。
>
> 现在的结论全部来自模拟器（P11 9/10 通过）。国产 ROM 的省电策略、键盘高度、
> 磁贴权限三件事，模拟器给不出答案——它们恰好是用户投诉最多的三件。

## 怎么跑

```bash
# 一台或多台设备都行（USB / 无线 adb 均可）
ADB=adb bash scripts/qa/device/matrix.sh            # 自动项 + 生成报告骨架
ADB=adb bash scripts/qa/device/matrix.sh --apk app-release.apk   # 先重装再跑

# MCP 对外提供（H 段）：先在手机上开开关、生成令牌，再把端口与令牌喂给脚本
ADB=adb bash scripts/qa/device/mcp-e2e.sh --port 41234 --token '粘贴令牌'
```

产物：`qa-logs/device-matrix-<型号>-<API>-<时间>.md`，AUTO 项带结论，
SEMI / MANUAL 项是待勾选清单——**报告里没勾的项不算通过**。

机型建议（用户在 2026-11-17 拍板「都做」）：

| 槽位 | 建议 | 为什么是它 |
|---|---|---|
| S1 | Android 12 / API 31，原生或接近原生 | `SYSTEM_ALERT_WINDOW` + 前台服务在 12 上的行为分水岭 |
| S2 | Android 14 / API 34，国产 ROM（MIUI / ColorOS / EMUI 任一） | 省电白名单、后台弹窗、磁贴权限三件事都在这类 ROM 上不一样 |
| S3（可选） | Android 15 / API 35 | 前台服务类型新限制（`SPECIAL_USE`） |

没有 S2 时，矩阵只能证明「代码没坏」，证明不了「在用户手机上能用」——报告里会标 `COVERAGE INCOMPLETE`。

## H. MCP 对外提供（6）

> 这套东西的失败模式是「电脑端以为自己在操作手机，实际手机没动」或者反过来
> 「手机动了但用户没看见」。所以每一项都要有**两侧证据**：电脑端拿到什么、手机屏幕发生什么。

`scripts/qa/device/mcp-e2e.sh` 覆盖 H1/H2/H3/H4/H6 的电脑侧断言（端口转发 + 协议 + 档位 + 审计）。
它需要手输端口与令牌——令牌只在屏幕上出现一次，端口是系统随机分的。

| # | 项 | 判据 | 自动化 |
|---|---|---|---|
| H1 | 开关即监听 | 打开「MCP 接入」开关 → 卡片显示 `127.0.0.1:<port>`，`adb forward` 后能握手成功（`initialize` 回 `polaris`） | AUTO |
| H2 | 令牌是硬门槛 | 不带 / 带错 token → 401；带对 → 200。**401 时不得出现任何工具执行**（看审计，不是看界面） | AUTO |
| H3 | 档位只影响可见性 | 只读档 `tools/list` 含 `app_list`/`ui_tree`，不含 `shell_run`/`app_uninstall`；切标准档后 `app_launch` 出现、`ui_tap` 仍不出现 | AUTO |
| H4 | 真机调用与本地一致 | 电脑端 `app_list` 的结果与手机上同名工具结果逐字一致（同一次会话内比对） | SEMI |
| H5 | **亮屏锁屏 = 拒绝** | 手机亮屏停在锁屏界面（不熄屏、不解锁）→ 电脑端调 `app_launch` 应得 `-32006`，调 `calculator` 仍成功。这一条是「在场」判定的真机唯一证明 | MANUAL |
| H6 | 关开关即断 | 关掉开关 → 已建的 `adb forward` 立即 `Connection refused`，且通知栏的常驻通知消失 | AUTO |

> H5 为什么必须是 MANUAL：模拟器里 `KeyguardManager.isKeyguardLocked` 恒为 false，
> 自动化只能证明「代码调了这个 API」，证明不了它在那台 ROM 上返回什么。而 MIUI 的
> 「锁屏显示」类开关会影响这个返回值。

## 自动化边界（诚实说明）

标 AUTO 的项由 `scripts/qa/device/matrix.sh` 直接判定；标 SEMI 的项脚本会把
`adb` 能查到的证据（权限位、进程、日志、文件内容）抓进报告，但**结论要人看**；
标 MANUAL 的项只能人点。

不把 SEMI/MANUAL 标成 AUTO 的理由很具体：这些判据里有一半是「体验对不对」——
键盘有没有挡住按钮、声音是不是叠了、提示文案读起来像不像人话。能被 `adb` 断言的
只有「有没有」，而用户投诉的从来是「对不对」。

## 2026-11-17 云机实测（x86_64 模拟器，API 30）

在一台 4 vCPU / 8 GB 的云 Linux 上装了 Android SDK 34 + system-image android-30，
用 `-accel off`（该机没有嵌套虚拟化，`/dev/kvm` 节点存在但打不开）跑纯软件模拟。

| 项 | 结果 | 说明 |
|---|---|---|
| 构建 | ✅ | `assembleRelease` 39 MB（arm64 完整，含 onnxruntime 22 MB + sherpa 9 MB）；`-PnoNative -Px86Rootfs` 的 x86 版 26 MB |
| 全量 QA | ✅ 146/146 | 包括 40 个需要 kotlinc 的 harness（`deps.sh` 从 gradle 缓存里找到了 compiler-embeddable） |
| A5 转屏 | PASS | rot 0/1/0 三次采样 frame 均合法 |
| A8 通知 | PASS | 本应用 `NotificationRecord` = 1 条 |
| C4 优先级 | PASS | `importance=2`（MIN） |
| G3 落盘 | PASS | `{"turns":[{"role":"user",…},{"role":"assistant",…}]}` |
| G4 上限 | PASS | 1 条（未做 15 轮压测，上限逻辑由 `run-pet-history` 覆盖） |
| A3 加窗失败 | SKIP | 需要先撤权，脚本无法自己造这个前置条件 |

跑通的端到端链路（截图与 `adb` 证据都在当轮记录里）：

```
设置页开「显示桌面助手」→ 前台服务 + 常驻通知 + 悬浮窗
→ 气泡输入 hello_mock → mock LLM(10.0.2.2:8200) 回一句
→ 气泡显示 → files/pet/history.json 落盘
→ am force-stop → 重开 → 气泡仍显示上一轮（回放，时间戳前缀已剥）
→ 菜单「清空对话」→ 气泡回引导语，history.json 被删除
```

### 这一轮抓到的真 bug（不是环境问题）

**冷启动必闪退**：`RemoteServiceException: Context.startForegroundService() did not
then call Service.startForeground()`。

服务里 `startForeground` 明明是 `onCreate` 第一句，问题在**服务没被创建**——
启动请求排在主线程队列里，主线程正忙首帧渲染，超过 5 秒。那个窗口由系统计时，
超时在 `ActivityThread` 里抛，进程直接死，`runCatching` 抓不住。

修法：`PetState.ensureRunning`（只在 `Activity.onResume` 调用，前台）改用
`startService`，不参与 5 秒窗口；磁贴/通知入口仍用 `startForegroundService`
（那条路径可能在后台，必须靠前台服务声明换执行资格）。守卫 `B3`/`B4` 钉住这个区分。
