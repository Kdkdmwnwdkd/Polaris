一、定位：三层分工

1.1 主轴

北辰是住在手机里的常驻者，不是被遥控的工具。

对比：Cline 是插件，OpenHands 是服务器，mobile-use / droidrun / OpenClaw 全是电脑通过 ADB 遥控手机——手机在它们眼里是一块屏幕。北辰反过来：agent 就住在被操作的那台设备里。

1.2 三层各归谁

层 归属 我们的做法 会被平台收走吗
手脚 平台最终会提供 先收成一套接口，无障碍只是其中一个实现 会，换实现即可
脑子 只有我们能做 跨 App 状态接力、失败恢复、什么时候该问人 不会
看得见 只有我们愿意做 思考与工具同链、失败直接浮出、可回放 不会（官方不愿担责）

关键判断：特点不该长在表达层，该长在内核层。 表达层做得好，用户说"这 App 挺好看"；内核层不一样，用户才说"这个只有它能干"。

1.3 官方口子的时间窗（已核实）

平台 官方通道 关键限制
Android AppFunctions（Android 16+，2026-02 公开） 每个 App 变成设备端 MCP server 调用方需 EXECUTE_APP_FUNCTIONS，protectionLevel = internal\|privileged ——普通 App 拿不到
Android 系统级 UI 自动化 Gemini 自己点界面 首发仅 Galaxy S26 / Pixel 10，仅美韩，仅几个品类
Apple App Intents / Siri AI（2026-11-03 开发者预览） App 声明能力，Siri 调度 未声明的能力调不到；发消息/分享/删除每步都要确认

时间表：Google Play 的 Apps Experience Program 已含 "Android MCP" 准则，2027-03-01 生效；苹果 2027 春季开放送审。

结论：2026–2027 是窗口期。手脚终会降级为兜底，脑子必须现在就长出差异化。

1.4 官方不会做的那件事

官方给能力，官方助手做黑盒编排；我们做透明编排。

Gemini 怎么拆步骤、为什么选这家、点了哪个按钮——你看不见也改不了。苹果更直接，每步都要确认。官方不会做"可看、可改、可回放"的编排，因为那意味着替结果负责。

1.5 特点成立要过三关

  1. 别人是做不到，还是没做？ 没做的会被抄，"没沙箱所以每步可回放"抄不走。
  2. 用户能不能一句话说出好处？ 说不出来就是技术自嗨。
  3. 能不能录 30 秒屏演示？ 演示不出来的等于不存在。

二、交互：过程实时，结果整段

2.1 一句话

思考链在运行时要一条一条往外冒；正文要憋到最后，整段一次性出现。

理由是用户原话："你一个字一个字地出也不好，因为它是整个答案……你全部做完之后才思考怎么出。"

2.2 完整时序

阶段 屏幕上 判据
跑工具 思考 / 工具一条条实时出，最后一步转圈 —
开始生成正文 正文不显示，最后一步显示"整理回答中" finish_reason 未到
正文生成完 整段一次性出现，同时过程折成摘要行，失败步浮出 finish_reason 到达且该条有正文
中途断连 显式说"回答中断"，已生成部分落地 + 重试，不装正常 超时 / 错误

为什么敢等这几秒：那几秒屏幕上写着"还在思考"，用户不会觉得慢。反过来"出两行字然后卡住"才是真难受——用户会以为答完了、答错了、或者死了。

2.3 折叠

项 决定
折叠时机 答案整段上屏的那一刻（不是第一个 token，因为那时正文还没出现）
摘要行写什么 ▸ 已完成 6 步思考 · 14 次工具 · 1 分 20 秒（不是"思考了 8 秒"那种没信息量的）
失败步 不折进摘要，单独红条浮在外面：✕ 1 步失败 · github_status 仓库不存在
用户手动展开过 touchedByUser 为真则不自动折叠——手动操作优先于自动行为
纯问答（无工具） 不折，思考留在正文上方一行，与 ChatGPT 同形
重启后看历史 默认折叠，只显示摘要行（失败步仍浮出）

旧版为什么被骂：旧版折叠建立在"中间步根本没落库"之上——数据一开始就不全，折起来只剩一条。那叫丢失，不叫收起。现在 trace 完整，折起来才是真的"收"。

2.4 中间正文不吞（已定）

过程中的正文不丢弃，进思考链、可展开、全部让用户看到。

执行细节：一轮只认最后一段正文当答案，前面的正文进 trace 当"说明"（1.921 的 asTrace 逻辑）。前面若有超过一定长度的正文，不能丢，挂在链里可展开。

2.5 中断：没写完就不给答案，但让你看见卡在哪

用户原话："只要没有完成到最后一步，按暂停的话，是没有任何正文回答的，只会思维链收起来。但是我又可以从思维链中看到你做了什么、在做什么、后面要做什么。"

项 决定
半截正文 不进正文区。收进 trace，标注「（未完成的回答 · 按停止时中断）」，展开可见
过程链 收成摘要行，不散着
摘要行写三层 已做 6 步 · 14 次工具 / 正在做 ui_tap 【购买】 / 打算做 最后一段思考的意图，一句话
恢复 摘要行给「继续」，从断点接着跑（和"一键继续"是同一件事）

"后面要做什么"这一条是新的，也是北辰比 WorkBuddy 更开放的地方。 它要求最后一段思考的意图能被单独提出来——好在 trace 里本来就保序存着，取最后一条 thinkingStep 的末句即可。

2.6 已知代价（明确接受）

  1. 再也没法"看着它写、写歪了随时停"——要么信它写完，要么看思考链判断方向。中断能拿到"卡在哪"，但拿不到"写到一半的答案"。
  2. 超长回答等待明显（4000 字约十几到二十几秒），这期间屏幕上只有"整理回答中"。所以 heartbeat 是必需的，不是可选的。

三、审批：三档必须名副其实

3.1 现在的问题（已核实 ApprovalTier.kt）

档位 实际行为 名字说的
逐步确认 全部问（含截图、读文件） ✅ 一致
常规 全都问，只有勾了"始终允许"的组才免 ❌ 名为"常规"，实为"全都问"
全自动 界面/截图/朗读/写文件免问，装卸载、GitHub、shell 仍弹窗 ❌ 名为"全自动"，副标题自己写"仍必问"

用户原话："第三档完全放权，还是和第二档一样……那我选第二档不就行了吗？直接把第三个删了。"

结论：要么让第三档真放权，要么删掉它。不做一个名不副实的档位。

3.2 新定义

档位 问什么 一句话
逐步确认 每一步都问，含截图、读文件、点击 你不放心时用，逐个把关
智能审核（默认） 只有危险的才问 日常用，AI 自己判断
完全放权 一律不问，只告知 你说"我认了"的时候用

判定逻辑（两级：先看组，再看落点）：

STRICT -> 问                                          // 全问
AUTO   -> 不问                                        // 全不问
else   -> 组级危险(group)      -> 问
          落点级危险(toolCall) -> 问
          其余                -> 不问

3.3 危险的判据：三层筛子

三把尺子（用户定义，一字不改）：

不威胁隐私、不触碰财产、不损害财产 —— 三者都不沾，就不算危险。

动作类型本身没有意义。 点"返回"和点"立即支付"是同一个 ui_tap；搜网页和读短信都是"读"。所以判据必须落在这一步会造成什么上。

第一层：App 级（整体隐身）

有些应用，整个都不该进模型的视野——不是"看了再问"，是根本不给看。

类别 例子 判
金融 银行、支付宝、微信支付、券商 隐身：ui_tree 里没有，截图里也没有
密码管理 1Password、Bitwarden、系统钥匙串 隐身
证件/身份 电子身份证、社保、护照类 隐身

为什么隐身强于提问：问了，用户很可能点"允许"；而且此时模型已经读到了内容，问只是事后追认。Pinky（DIYgod 开源项目）就是这么做的——"银行、钱包、密码管理器应用默认对 Agent 完全隐形，通知也会在通知栏和锁屏上被藏起来"。

代价：任务做不了（"帮我看下余额"）。所以要给一个出口：用户可以在白名单里手动解除某个 App 的隐身，单次有效。

第二层：组级（工具本身就只能干危险事）

归组 判 理由
应用安装 / 卸载 / 停止 问 不可逆，数据会没
GitHub 写入（push） 问 外发，别人看得见，撤不回
shell 破坏性 问 rm -rf 级
shell 提权（uid 2000） 问 —
本机隐私读取（短信/通讯录/相册/通话记录） 问 隐私
普通 shell 放行 靠 ShellCommandRules 按参数判
网络请求 放行 纯读，外发另有 EgressGuard 三道闸
工作区外文件读取 放行 纯读
工作区文件写入 放行 FileBackupStore 逐文件备份，可回滚
截图 / 读界面树 / 朗读 / 通知 放行 只看、只说

第三层：落点级（同一把工具，点哪儿决定危不危险）

界面操作、输入、点击这类工具组级一律放行——否则第二档就退化成第一档（连续界面操作要弹十几次窗），这正是当初做三档要解决的问题。

危险与否，看这一下的落点：

落点 判 例子
文案含 发送/支付/转账/付款/确认/删除/授权/同意/提交/购买/下单/申请/绑定 问 "立即支付"、"确认转账"、"发送"、"删除对话"
密码框 / 验证码框 / 银行卡号框 问 —
打开 App、返回、关闭、滚动、翻页、切换标签 放行 —
搜索框、普通输入框打字 放行 —
识别不出目标（图标按钮、纯图形） 不可逆 → 问；可逆 → 放行但链上标黄"未识别目标" —

技术前提：ui_tree 能读到落点控件的文案/资源 id。绝大多数 Android 控件能读到；读不到走最后一行的兜底。

多语言：风险词表不能只有中文。Pinky 做的是 10 种语言的标签识别。我们至少要覆盖中/英，加上常见的"Pay / Send / Delete / Confirm / OK"。

三级优先级

隐身  >  问  >  放行

App 级命中的，不管组级和落点级怎么判，一律隐身。

为什么是三层：业界的档位都按"操作类别"分，没有按"单步危不危险"分的（见 §3.4）。原因是类别可预测、可解释，用户能形成预期；单步判断永远有误判空间。所以档位定类别，单步判定只做加法——在类别之上再加一层拦截，而不是拿它替代类别。

3.4 业界怎么判（五家对照）

来源 判定单位 具体分类 我们的对应
Claude Code 操作类别（6 档） default 只读 / acceptEdits 加文件编辑 / plan 只读+分类器 / auto 全部+第二个模型当分类器 / dontAsk 只跑预批准 / bypass 全放 §3.2 三档 = 它的精简版。它没做"单步危不危险"，做的是"哪类操作不用问"
Pinky（开源） App + 落点 金融/密码管理器整体隐身；风险按钮标签 10 语言识别；60 秒无响应=不允许；验证码读前打码 我们完全没有前两条，见 §3.5
FoneClaw 变更时刻 查询状态、整理文字、产生建议 = 不改变外部世界；发消息、删文件、改设置、分享位置 = 有可见结果。确认强度要与影响相称 我们只有"弹/不弹"二元，缺强度分级
掘金「策略引擎」 能力 + 参数 白名单、参数范围、调用频率、风险级别；"整理相册只能生成候选分组，删除必须逐项确认；回复消息只生成预览，发送留给用户" 草稿态，我们完全没有，见 §3.5
Mika 碰"钱、权、密" 登录输密码、收发验证码、点支付、系统权限弹窗 → 主动暂停，通知用户手动介入 方向一致，粒度比我们细

一个共同的空白：五家里没有一家用"这一步危不危险"作为主判据。都是"哪一类不用问" + "哪一类永远问"，中间地带靠 App 名单和落点表填。我们原来只想做落点判据，是漏了两层。

3.5 三条我们缺的（都是别人已经做出来的）

# 缺什么 谁做了 我们现在的状态
1 App 级整体隐身 Pinky grep 零命中，没有包名黑名单
2 验证码读前打码 Pinky 没有。只有注释写过"通知正文里有验证码，读一次等于把用户此刻的手机看穿"（审计 F9），但没实现
3 草稿态 掘金策略引擎 没有。我们只有"允许 / 拒绝"两个按钮

草稿态最值得学，因为它改变了"问"的形态：

与其问"要不要发这条消息"，不如把消息写好放在输入框里，让用户按发送。

用户看到的不是抽象的"允许/拒绝"，而是真实的、可改的结果。信息量完全不是一个量级，而且它天然符合我们的主轴——完全可见。

适用范围：发消息、填表单、发邮件、提交评论。不适用：删文件、卸载 App（这些没有"草稿"可言，只能问或不做）。

3.6 第三档凭什么敢做

用户的话说到了根子上："电脑完全放权不就这么做的吗？只不过他们有黑箱、有回收站……我们手机做不到而已。"

先纠正一个事实：电脑上的"完全放权"也不是 100%。 Claude Code 的 bypassPermissions 文档里明确写着，即使在最放的一档，四条硬底线仍然会拦：

  1. 显式 ask 规则（用户自己标过的）
  2. 需要用户交互的工具（AskUserQuestion）
  3. 对关键路径的 rm / rmdir
  4. 工作目录外的读取（开启 blockReadsOutsideWorkingDirectories 时）

而且官方建议"仅在容器/虚拟机里使用此模式"。换句话说，连 Anthropic 都不敢给一个真的 100%。

所以第三档的定义应该是：跳过所有弹窗，但保留四条断路器。

断路器 内容
隐身 App 第三档下依然隐身。这不是权限，是看不见
自伤保护 关键路径的 rm -rf、卸载系统应用 → 仍拦
硬止损 60 步 / 30 分钟，不受档位影响
全程留痕 每步落 trace，事后可回放（这条本来就一直有）

补偿机制（手机没有回收站，所以要补两样）：

第一样：全程可见、随时能掐。 这正好接着 §2 的"过程链实时展开"。第三档不是闭眼放权——它每点一下你都看得见，觉得不对随时按停止。电脑上你也不知道它点了哪个按钮，我们知道。这是手机端唯一比电脑强的地方，也正是第三档成立的前提。

第二样：事后一份清单，不可撤的标红。 跑完给一张"这轮做了什么"的表，能撤的给撤销入口（文件写入有 FileBackupStore），撤不了的（卸载、push、发消息）明确标出来。

3.7 文案要改

  • 第二档副标题：~~"危险操作弹窗确认，勾选后同类不再问"~~ → "不危险的我直接做，危险的问你"
  • 第三档副标题：~~"……应用装卸、GitHub 提交、shell 命令仍必问"~~ → "一律不再询问。每一步你都能看见，跑完给你清单，撤销不了的会标出来"

四、视觉：怎么不"像 AI"

4.1 判断

问题不是配色不好看，是"平均"——整屏每个元素都被同等对待，没有主次。真人设计一定偏心。

4.2 四个症候

症候 表现
全灰 整屏没有一处是黑的。全是不同程度的灰，没有视觉锚点，眼睛不知道先看哪
等权 每个元素都加说明、加圆点、加边框，不敢让任何东西"轻"下去
盖章癖 "思考"两个字重复十几次，每行盖一个章。真人不这么写字
冷暖打架 底色暖米黄 + 文字冷灰（0xFFF7F8FB 那套偏蓝），屏幕显脏

4.3 三处最刺眼

  1. 顶部四行全是小字：导航栏只有汉堡和"+"、中间空着；"默认配置"是最淡的一行；再下面 API 地址；再下面 token 统计。四行字号接近、颜色接近——用户不知道先看什么。
  2. 十几条工具调用一路平铺：同样大小的绿点、同样大小的字、同样宽的竖线，没有段落。中间 JSON 块突然撑开，把后面全推出屏。用户看不出这轮到底做了几件事。
  3. 原始 JSON 占三分之一屏：{"text":"","desc":"id":"content","cls":"FrameLayout",...} 是模型看的，不是人看的。它比思考重、比工具名重、比整屏任何东西都重。

4.4 只改三处

  1. 每页只留一个最响的：会话名用正文大小、接近黑；token 统计退到最淡最小，点开才看。
  2. 工具结果折成一行：读取 60 个节点 · 点 3 次，点开才是 JSON。JSON 永远不主动出现。
  3. 圆点只在异常处出现：正常步骤用细竖线，失败/拒绝才上色点。全是绿点 = 没有点。

改完信息密度降一半，能读懂的部分翻倍。

五、地基

5.1 落盘截断（已发 928）

MAX_FIELD_CHARS = 4000 → 正文/思考 40000、工具结果 20000 且保留头尾（头 8000 + 尾 12000，中间插可见省略标记）。

理由：4000 这条线砍下去，用户看到的是"会话里读全文正常，关掉重进只剩四千字"，而且半截会被当上下文发给下一轮，模型接着半句话往下写。

配套：切点回退到 code point 边界（Cline #14563 同一件事）、标记里写"需要完整内容请缩小范围重跑"（Cline 的 Refine the command）。

5.2 手收成一套接口（未做，优先级最高）

ui_tree / ui_tap / ui_click / input 不关心背后是无障碍、shell、还是将来的 AppFunction 声明。

现在 ShellChannel 已经抽象了一层，但 AgentAccessibilityService 仍是独立路径。这个抽象现在不做，等官方口子开了再改，就是重构整个循环。现在做只是一层接口。

5.3 heartbeat（未做）

超过 20 秒没有新内容，在流尾显示一行：已 20 秒无新内容 · 可中断重试。

这是 §2 的强制配套——正文憋着不出的那二十秒，和卡死长得一模一样。

六、已定（原「待拍板」三件，2026-11-27 夜定）

# 问题 结论
1 危险组怎么划 看落点，不看动作。三把尺子：隐私 / 财产 / 外发。详见 §3.3
2 按停止时半截正文落不落地 不落地。正文区一个字都不出，半截收进 trace 可展开，摘要行写「已做 / 正在做 / 打算做」三层。详见 §2.5

八、从零做 Agent：十四个部位对照

这一章回答一个问题：如果今天从零搭一个手机 Agent，每个部位应该长什么样，北辰现在长什么样。
看别人怎么做，不是搬参数，是搞清"他为什么必须这么干"，再想我们能改造成什么。

8.1 全景表

# 部位 业界锚点 北辰现状 改造方向
1 模型接入 多 provider + 失败切换 + 按任务选模型（Droidrun：Manager 用强模型，Executor 用快模型） 30+ 预设，含本地 Ollama 已在第一梯队，不动
2 提示词架构 指令分散布置在不同段落，不堆在一处；记忆双注入（system prompt + 最后一条用户消息） 单块 system prompt 记忆双注入，小改
3 上下文管理 前缀稳定、只追加、遮蔽而非移除；预算内整步丢 已有 ContextBudget + 钉锚点 补"空 success 优先丢、失败最后丢"
4 循环控制 Manager→单步→Manager 紧反馈，不做一次性长计划 单循环 + 60 步 + 熔断 加 complete() 完成信号
5 工具设计 少而准；组合优于罗列（search_contacts 而非 list_contacts）；30-50 个是劣化线 52 个，按 Strength 分组 + __find_tools 命名空间收敛 + response_format
6 感知 a11y 树为主、截图为辅、差分状态（当前树 + 上一次树同送） 树 + 截图 + OCR + 通知 加差分，这一步省最多 token
7 执行 click(index) 而非坐标；动作后等画面稳定（0.5s 起，比对到不变） ui_click 按文本/ID，ui_tap 坐标兜底 补画面稳定判定
8 状态与恢复 checkpoint + resume AgentRunStateStore + 启动自救 已够
9 记忆 remember() / get_memory()；app 卡片（YAML 教模型怎么用某个 App） 工作区 + 会话，没有 app 卡片 中文 App 卡片库 = 最大差异化
10 审批 三层筛子 + 草稿态 + App 隐身 见 §3 按 §3 做
11 人机交互 什么时候该问人；中断后能接管 ask_user 有 补"接管"语义
12 可观测 trace / 回放 / 每步截图 trace 完整、保序 可回放 = 第二条差异化
13 评测 模块级评测与人工判断一致度 94.7%（MobiBench）；AndroidWorld 已饱和 R06 就是模块级 路子对，别追榜
14 成本 输入输出比 100:1；缓存价差 10 倍；单次工具输出限 25k token 有计量，无软告警 补 70% 告警

8.2 工具设计：我们的 52 个，已经在劣化区

Anthropic 的量化口径：超过 30–50 个可用工具后，模型挑对工具的能力开始劣化；超过 10 个工具、或工具定义超过 1 万 token 时，官方建议启用工具搜索按需加载。

我们有 52 个，正好压在线上面。

已有的解法是对的（按 Strength 分组暴露 + __find_tools 查回），但还差三件事：

缺什么 别人怎么做 具体数字
response_format 开关 返回值加 concise / detailed 枚举，默认只给核心字段 Anthropic 用这招把 Slack 线程响应从 206 token 压到 72 token
命名空间 asana_search / jira_search，按域加前缀 前缀 vs 后缀的效果差异"非平凡"，要自己评测
组合型工具 schedule_event（查空闲 + 建日程）替代 list_users + list_events + create_event 减少中间输出，也就减少上下文

我们的 ui_tree 是最好的例子：它现在返回全量 JSON（每个节点的 cls、bounds、clickable、focusable…），一次几百个节点。这正是 Anthropic 说的"把数据库整行倒出来"。

改造方向：ui_tree(format="concise") 默认只返回可点元素 + 文本 + 稳定 index，detailed 才给全量。

这个改动一举两得：省上下文，同时正好是 §4 里"JSON 不主动出现"的那件事。一个改动，治两个病。

8.3 感知：差分比全量省得多

Droidrun（AndroidWorld 91.4%）的做法值得抄思路：

最近一条用户消息放当前截图 + 当前树；上一条放上一次的树。模型自己就能看出"变了什么"。

对比我们：每一步都把整棵树重发一遍。一次 200 个节点，十步就是 2000 个节点，其中 95% 没变。

为什么差分在手机上特别有效：手机界面变化幅度小——点一下通常只变一个开关、一个弹窗、一行文字。整棵树重发是巨大的浪费。

我们能改造成什么：差分之外再做一层界面指纹。

给每次 ui_tree 的树算一个指纹（包名 + 可见文本的哈希）。同一个指纹第二次出现，直接复用上次的解析结果，只标注"回到此页"。

效果：模型连续几步在同一个页面里操作（找按钮、点、再找），只付一次解析成本。这条公开资料里没见过，是我们自己能长的东西。

8.4 执行：等画面稳定，别等固定时间

Droidrun 的做法：每次动作后等 0.5 秒，比对屏幕状态，重复直到稳定或超时。

我们现在有 getFreshUiTreeSnapshot（等窗口切换事件），但没有"画面是否已经不动了"这一层。差别在于：

场景 现在的行为 稳定的行为
点了一下，页面有 300ms 动画 可能读到动画中间态，节点对不上 等到不动再读，节点一定是对的
点了一下，加载要 2 秒 读到的还是旧页面，模型以为没反应，重复点 等到新页面出现
点击确实无效 直接判定失败 等 1 秒仍未变，才判失败

我们能改造成什么：稳定判定 + 失败回执带"屏幕没变"这个事实。现在失败只说"没找到"，不说"点了但界面没动"——后者才是模型最需要知道的。

8.5 循环：缺一个 complete()

Droidrun 的动作空间里有个 complete() 工具，任务结束由模型显式声明。

我们现在的终止条件是"tool_calls 为空"——模型不说话就等于做完了。这有两个问题：

  1. 模型可能只是这一轮不想调工具，但任务没完
  2. 模型说"我完成了"，没有任何东西能校验它是不是真完成

改造方向：加 complete(summary, evidence)。evidence 要求给出"我凭什么说完成了"——比如"设置页里开关已显示为关闭"。

这比"沉默即完成"强得多，而且它天然接上 §2：complete 一到，正文整段出、过程折叠。一个信号管三件事。

8.6 记忆：app 卡片是别人没做的中文空白

Droidrun 有个东西叫 app card：一份 YAML，告诉模型"这个 App 是干什么的、主要页面有哪些、常见操作在哪"。

他们的卡片是英文 App（Gmail、YouTube、Maps）。中国用户用的是微信、支付宝、美团、钉钉、小红书、高德。

这些 App 的界面逻辑、常用路径、容易踩的坑（"微信的发送按钮在右下角，不是右上角"），英文资料里一条都没有。

这就是北辰最实在的差异化资产：

一套中文 App 卡片库。不是代码，是知识。

它符合 §1.5 的三关：
1. 别人做不到吗？——不是做不到，是没人做，因为他们的用户不在中国
2. 用户能一句话说清吗？——"它认识微信"
3. 能录 30 秒演示吗？——能：同样一句"帮我在群里发个通知"，有卡片和没卡片，步数差一半

而且卡片可以让用户自己长：用过三次的 App，自动把路径记下来，问用户"要不要存成卡片"。这是"住在手机里"才有的能力——云端 Agent 不知道你昨天怎么用美团。

8.7 五条能变成特色的（其余十二条是必须对齐的）

# 特色 为什么别人不会做 能否演示
1 中文 App 卡片库 他们的用户不在中国，没这个需求 能，步数对比
2 可回放：从结果点回"当时那一屏 + 点了哪个节点" 官方做等于替结果担责 能，录屏
3 界面指纹缓存 云端 Agent 每次都是新会话，没有"回到此页"的概念 能，token 对比
4 失败不折叠、失败步不裁剪 别人默认收起过程，失败也一起收 能，报错场景
5 过程实时 / 结果整段 他们的用户只要结果 能，录屏

其余十二条不要想着做出花。 模型接入、上下文、循环、工具、感知、执行、恢复、审批、交互、可观测、评测、成本——这些必须长得像别人，因为它们是语义层：模型要认、供应商要认、用户要认。在这一层搞"特色"，等于让模型学一门新语言。

8.8 一句话总结这一章

十二条对齐，五条长出自己。
对齐的部分照抄结论（数字、阈值、结构），长出来的部分只抄思路（为什么这么做），形态自己定。
