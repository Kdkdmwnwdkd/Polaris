# 北辰 · Polaris 架构方案 v3

> 写于 **2026-11-17** ｜ 评审方式：五条独立评审线（分层 / 运行时 / 安全 / 工程效能 / 多入口）各自读码取证，交叉核对后收敛
> 基线：`main@5a7324b`（桌宠收尾三处修复），`:core` 215 文件 4.28 万行、`:app` 194 文件 5.58 万行
> **这份文档只写判断和取舍，不写教科书原则。** 每条结论都带 `文件:行` 或实测数字，可逐条反查。
> 与 v2（2026-11-06）的关系：v2 解决的是「怎么拆」，v3 解决的是「谁来装配、谁来负责」。

---

## 0. 一页结论

现在这套代码**不是分层不清，而是没有所有者**。

具体说：内核能力（loop、守卫、接缝、能力桥）全都写好了，但没有任何一处「装配者」把它们接起来——`productionSeams` 全仓 0 调用，`RealAgentLoop` 的 `seams` 默认 `NONE`，守卫链只有机制没有实例，审批是一个挂在 `MainActivity` 上的弹窗组件而不是一份契约。于是每加一个入口，就得把 `ChatViewModel` 里那 54 次 `register(...)` 和 21 个参数的 loop 构造再抄一份，抄的时候顺手丢掉审批与守卫。

**三个必须承认的事实：**

| # | 事实 | 证据 |
|---|---|---|
| 1 | 入口数量已经超过装配方式的承载能力 | 5 个入口 × 3 处手写 loop（`ChatViewModel.kt:2000`、`PetAgentSession.kt:104`、`SubAgentRunner.kt:97`），桌宠只装 4 个工具、`approval=null`（`PetAgentSession.kt:116`） |
| 2 | 安全机制处于「已实现、未启用」状态 | `productionSeams` 只有定义与注释引用，**零调用点**；`RealAgentLoop.kt:208` 默认 `AgentSeams.NONE` |
| 3 | 验证体系在膨胀，但判别力在下降 | 146 个 runner 中 **499 处 `grep -q`**，只有 2 个脚本会先剥注释（`run-arch-guard-verification.sh:145`、`run-desktop-pet-verification.sh:328`）；门禁 5 遇 `SKIP>0` 直接放行（`gate.sh:146-155`） |

**一句话方案：把「运行时」抽成一个所有者（`AgentRuntime`），把「同意」抽成一份契约（`Consent`），把「验证」抽成三层（静态契约 / JVM 行为 / 真机矩阵）。** 其余都是这三件事的推论。

## 2. 五个结构性判断

### 判断一：缺的不是分层，是**运行时所有者**

`RealAgentLoop` 被三个地方各自 `new` 一次，参数各写各的：

| 调用点 | 工具集 | 审批 | 预算 |
|---|---|---|---|
| `ChatViewModel.kt:2000` | 54 个 register | 全局弹窗 | 默认 |
| `PetAgentSession.kt:104` | 4 个只读 | `null`（关闭） | 6 步 |
| `SubAgentRunner.kt:97` | 继承父级子集 | 继承 | 240s / 12k |

后果有三层：

1. **串行化靠约定**。主界面靠 `isRunning` 的 check-then-act（`ChatViewModel.kt:1587`）而非互斥量；`FailureGuard` 是 loop 实例字段，注释直说「一次只有一个回合在跑（UI 侧串行保证）」（`RealAgentLoop.kt:284`）。桌宠有 Mutex，但只保护自己的 history。**进程级没有第二道闸**。
2. **没有计费落点**。token 用量记在每个 loop 里，没有统一账本，所以「这个月花了多少 / 哪个入口最贵」答不出来。
3. **中断语义分叉**。主界面 `cancelAndWait()`（`GenerationRunController.kt:186`），桌宠只能关掉整个服务（`PetOverlayService.kt:257-285`），后台任务连停止按钮都没有。

> **判断**：这不是「代码写得乱」，是缺一个 **`AgentRuntime`**——它拥有 loop、拥有队列、拥有账本、拥有中断权。三个入口退化成「提交 Task 的壳」。

### 判断二：扩展点写好了，但**没接线**

三个接缝的形状是对的：

| 接缝 | 机制完整度 | 装配状态 |
|---|---|---|
| `AgentSeams`（用户消息 waterfall / 助手消息 parallel / 工具守卫） | 好：`NONE` 首行短路零分配（`AgentSeams.kt:198`） | **没人传**。`RealAgentLoop.kt:208` 默认 `NONE`，`ChatViewModel.kt:2000` 未传 |
| `ToolGuardChain`（3s 超时 + fail-closed + 取消透传，`ToolGuard.kt:106-145`） | 好 | **零实现**。唯一实现是 Chain 自己 |
| `productionSeams`（把日志接回 `AgentLogger` 的生产装配） | 写好了 | **零调用**，只有注释在引用它 |

这造成一个很具体的后果：**今天想加「只读模式」或「路径边界」这条规则，写不出一个 guard 就能生效的东西**——必须改 `ChatViewModel`，因为装配权在那里。

同一类问题在能力层更严重：`Capability` 是 2 值封闭枚举（`RUN_SHELL` / 界面操作，`CapabilityChain.kt:50-56`），加第 3 类端侧能力要改 core 枚举 + `when` 分支 + `CapabilityBridges`。对照 `ProviderCatalog` 的 30+ 家供应商是**数据驱动**的，零代码接入——同一个仓库里，两种扩展风格并存。

### 判断三：审批是**一个 UI 组件**，不是一份契约

审批现在的形态：`ApprovalHost` 挂在 `MainActivity.kt:166`，pending 状态属于 `ChatViewModel` 单例，弹窗只给前 500 字符（`ChatViewModel.kt:1745`），后台任务 30 秒自动拒绝（`ApprovalDeadline.kt:12`）。

由此产生四个真实风险（按危害排）：

| 风险 | 触发条件 | 现有防线 | 缺什么 | 等级 |
|---|---|---|---|---|
| 守卫链未装配，实际只有审批 | 任何工具调用 | `SeamDeny.kt:31` 写好了，但没接 | 装配 + 决策留证 | **P0** |
| 零弹窗外泄：`read_file` → `web_search` | 被注入的网页/UI 文本要求「把这段内容当关键词搜」 | `ReadFileTool` 只标 readOnly 免审（`BuiltInTools.kt:234`）、`WebSearchTool` 同样 `readOnly = true`（`:51`）且 query 直接拼进 GET（`:127`） | 出站内容管控（污点传播） | **P0** |
| shell 路径边界被 cwd 绕过 | `cd /sdcard` 批准一次后 `cat DCIM/x` | `ShellCommandRules.kt` 按命令词与绝对路径判（不认会话 cwd）；会话保存 cwd（`ShellTool.kt:84`） | 执行上下文级 root | P1 |
| 自动续跑重放已生效副作用 | 进程被杀后冷启动 | `AutoResumePolicy` 有 11 种判定，但不看 journal 的 `OUTCOME_UNKNOWN`（`AutoResumePolicy.kt:209-220`） | 续跑前的核对闸 | P1 |

> **判断**：威胁模型里最现实的不是「被黑」，是**审批疲劳**——用户对第 11 个弹窗点了「本次会话不再询问」，或者桌宠把工作区内容当搜索词发了出去。事故报告里会写「用户自己点的允许」。所以同意机制必须从「弹窗」升级为「带作用域与过期时间的票据，且无 UI 入口也必须有默认策略」。

### 判断四：多入口的差异，一半是设计，一半是漂移

| | 会话历史 | 工具集 | 审批 | 语音 | 打断 |
|---|---|---|---|---|---|
| 主界面 | 落盘 | 54 | 全局弹窗 | 只填入不发送 | 有 stop |
| 桌宠 | 仅内存 20 条 | 4 只读 | 无 | 识别即发送 | **无**（只能关服务） |
| 磁贴 / 通知 | 共用桌宠 | 同桌宠 | 无 | 直达聆听 | 无 |
| 后台任务 | 同主界面 | 同主界面 | 前台才有，后台 30s 自动拒 | 仅 SpeakTool | 无 |

**刻意的**：桌宠不共享上下文、工具集压到只读、不支持本地模型、语音为主（`PetAgentSession.kt:44-60`，spec §2.3）——这些是产品判断，保留。

**漂移的**（必须修）：

- `ChatScreen.kt:252` 自建 `TtsController`，绕过 `ChatViewModel:674` 的 `AudioGraph.speaker`——与桌宠「朗读必须走仲裁」（`PetOverlay.kt:571` 注释）直接矛盾，结果是仲裁器不知道主界面在说话，可能叠音、也可能被桌宠开麦时录进去。
- 桌宠「关闭」= 杀服务 + 销毁 composition，气泡与上下文一起消失且无二次确认（`PetOverlayService.kt:83`）。
- 磁贴点一次「听一句」会把 `enabled` 永久写成 true（`PetState.kt:114`）——spec 里说是刻意的，但用户心智里磁贴是「用一下」不是「常开」。
- spec 写「10 秒自动拒绝」，代码是 30 秒（`ApprovalDeadline.kt:12`）。

### 判断五：验证体系在膨胀，判别力在下降

实测账（本机 `run-all.sh`，缺 kotlinc）：

| 类别 | 数量 | 说明 |
|---|---|---|
| 纯 Kotlin 自编译真跑 | 81 | 用自建 kotlinc + 手拼 classpath |
| 需要 AGP 产物（`app/build/…/kotlin-classes`） | 38 | skip-allowlist 恰好 38 条 |
| 纯源码扫描 | 25 | bash 18 + python 7 |
| 真机 | 2 | — |

三类假绿，都是机制性的，不是个别失误：

1. **grep 命中注释**。499 处 `grep -q`，只有 2 个脚本会先剥注释。我今天就在 `run-desktop-pet-verification.sh` 里踩到：`grep stopSpeech` 会因为 KDoc 里写着 `arbiter.stopSpeech()` 而绿。
2. **门禁 5 遇 SKIP 放行**。`gate.sh:146` 明说「有 SKIP 时 PASS 下限不可比」——理由成立（环境差异不该判红），但它意味着「全 SKIP」也能过门禁 5，只剩门禁 6 逐条核对。
3. **arch 基线零校验**。给 `core` 加一行 `import ui.UiItem` 会红；但在 `arch-baseline.txt` 里加一行 `layer` 豁免，就绿了。护栏本身没有护栏。

CI 19–24 分钟的成本结构也有问题：每轮重装 NDK/cmake（`build.yml:57-70`）、`~/.gradle` 不缓存、`--no-daemon`（`build.yml:288`）、146 个脚本串行里含 94 次 kotlinc 冷启 JVM + 114 次 `java` 冷启。

## 3. 目标架构 v3

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│  app-entry    Activity · Service · Tile · 通知 · Worker       │
│               只做三件事：拿 Session、把事件转成 UI、报生命周期  │
├──────────────────────────────────────────────────────────────┤
│  app-ui       Screen / Composable / 各 feature 的 Controller   │
│               渲染与输入；不持有 loop、不注册工具、不弹审批      │
├──────────────────────────────────────────────────────────────┤
│  app-runtime  AgentRuntime（唯一的 loop 所有者）                │
│               SessionFactory · ToolSource 注册表 · ConsentBroker│
│               Scheduler · QuotaLedger · Egress                  │
├──────────────────────────────────────────────────────────────┤
│  core-kernel  纯 Kotlin：loop / 工具协议 / TurnEvent /         │
│               CapabilitySpec / Journal / AutoResumePolicy       │
├──────────────────────────────────────────────────────────────┤
│  core-platform Android 能力：terminal · proot · 无障碍 ·        │
│               local-llm · ASR/TTS · Service · 通知              │
├──────────────────────────────────────────────────────────────┤
│  core-data    会话 · 配置 · 日志 · 备份 · 迁移                  │
└──────────────────────────────────────────────────────────────┘
        依赖只能向下；entry 与 ui 互不依赖；kernel 不 import Android
```

**为什么不建议这一轮就切成 6 个 Gradle 模块**：`core` 现在混着 Android `Service` 与纯逻辑，硬拆要先做完 `UiItem → TurnEvent` 的迁移（25 处 `when` 分支），一次性代价 12–18 人日且期间无法发版。**先做包级分层（目录 + import 守卫），等 S3 完成再物理拆模块**——顺序反了会把重构风险叠在发版风险上。

### 3.2 运行时：一个所有者

```
入口   Chat │ Pet │ AutoResume │ SubAgent(≤3)
         └────────┬──────────────┘   只提交 Task，禁止 new loop
调度   AgentRuntime
       ├ Scheduler：单线程 FIFO + 优先级，去重键 = (会话, 来源)
       ├ QuotaLedger：回合前预留 token/费用，超限在步边界软停
       ├ 并发闸：云端 maxInflight=1，本地=1，子代理共用额度
       └ 中断：每 Task 一个 Job + 代次号，抢占只走 revoke(reason)
执行   TurnRunner：唯一持有 RealAgentLoop；loop 不存跨 Task 状态
记账   usage → CostLedger → UI（复用 TokenUsage / ModelPricing）
```

四条硬不变量（写进守卫）：

1. `RealAgentLoop` 的构造点在整仓**只能有一处**（`AgentRuntime`）。
2. 任何入口拿不到 `RealAgentLoop` 类型，只能拿 `SessionHandle`。
3. `Scheduler` 是进程内唯一能启动回合的地方；`isRunning` 这类布尔不再参与并发控制。
4. 每个 Task 必须有 `source` 与 `quota`，缺一个就抛——不允许「默认不限量」。

### 3.3 同意：从弹窗到契约

```kotlin
// core-kernel，不依赖 Android
interface Consent {
    suspend fun request(req: ConsentRequest): ConsentTicket
}
data class ConsentRequest(
    val tool: String, val argsDigest: String,
    val scope: Scope,            // Once / Session / 5m / Persistent
    val channel: Channel,        // Dialog / Bubble / Notification / Headless
    val risk: Risk,              // ReadOnly / Write / Egress / Privileged
)
data class ConsentTicket(val granted: Boolean, val scope: Scope, val expiresAt: Long, val issuedBy: Channel)
```

三条规则：

- **`approval = null` 在编译期不再可能**。`RealAgentLoop` 的参数改成 `consent: Consent`，无 UI 入口必须显式给 `HeadlessPolicy`（只读白名单 + 禁外发清单）——把「靠约定」变成「靠类型」。
- **桌宠 = `PetConsent` 实现**：越出只读集时，气泡里一条确认；30 秒超时拒绝；逃生路径是通知栏里可撤销的 5 分钟授权（「代理同意」）。这样桌宠既能保持「随手问一句」，又不会因为将来某次注册了一个写工具就变成无审批通道。
- **审批与判定同源**：弹窗展示的内容必须与判定用的内容一致。现在弹窗 `take(500)` 而判定用全量（`ApprovalScope.kt:92`），长 heredoc 的危险尾部正好落在人看不到的那段。改成「展示摘要 + 可展开全文，判定基于全文，摘要里标注被截断」。

### 3.4 工具与能力：从 register 列表到可组合来源

```kotlin
interface ToolSource { fun tools(ctx: ToolContext): List<Tool> }   // FileSource / TerminalSource / MemorySource / McpSource / AutomationSource
data class CapabilitySpec(                                          // 数据驱动，替代 2 值枚举
    val id: String, val title: String,
    val candidates: List<Backend>,   // 无障碍 → Shizuku → 失败
    val consent: Risk, val guards: List<String>
)
```

- `ChatViewModel` 里 54 次 `register(...)` 变成 `ToolSource` 组合，桌宠换成 `FileSource + MemorySource`——**差异变成数据，不再是一份复制**。
- `CapabilitySpec` 走 `ProviderCatalog` 同一条路：加第 3 类端侧能力只加一行数据 + 一个 `Backend` 实现。
- 顺带解决 `ToolCatalog` 58 vs 生产 54 的对账问题：来源自报，`audit` 才对得上。

### 3.5 事件流：UI 不再依赖 core 的 `UiItem`

`UiItem` 现在住在 `core`（`core/UiItem.kt:5`），`ConversationStore` 直接做 UI↔存储映射（`ConversationStore.kt:177`），ui 侧 22 处 `is UiItem.`（`ChatScreen.kt` 17 处）。加一种消息形态（计划卡、审批卡、桌宠带回来的卡片）要同时改 core 存储和 17 处分支。

目标：`core-kernel` 只产出 `TurnEvent`（`UserSaid` / `ToolStarted` / `ToolSettled` / `AssistantDelta` / `TurnEnded` / `Denied`），ui 侧做投影（`ConversationProjection`）。存储存事件，不存 UI 模型。

> 这条是 S4 的核心，也是 25 处 `when` 的迁移——**放在最后做**，因为它不影响前三条的收益。

## 4. 入口一致性规则

**规则一：同一句话，行为差异只能来自产品意图，不能来自实现。**
运行中再发一句：主界面是「打断旧轮再发」，桌宠是「静默丢弃」。两者都说得通，但必须写进 spec 并在 UI 上体现（桌宠至少给一句「等它说完」），不能是「因为 `if (!sending)` 写在那儿」。

**规则二：每个入口都必须有「停」。**
桌宠现在只能关服务——用户想打断一句话，代价是丢掉整段对话。加一个 `stop` 到气泡标题栏，走同一个 `SessionHandle.cancel(reason)`。

**规则三：关闭不等于销毁。**
桌宠关闭应保留本次会话（落盘、可恢复、允许「带回主界面」），而不是连气泡一起抹掉。spec §2.3 拒绝共享上下文的理由是「ChatViewModel 三千行、绑 Activity」——那是技术耦合，不是产品理由。**独立 session 保留，关闭即焚要改。**

**规则四：朗读只有一个出口。**
`ChatScreen` 的 `TtsController` 合并进 `AudioGraph`，与桌宠共用仲裁。否则「谁在说话」这件事永远有两个答案。

## 5. 验证体系 v2

### 5.1 三层

| 层 | 守什么 | 规模 | 耗时 | 跑在哪 |
|---|---|---|---|---|
| L1 静态契约 | 禁止模式、分层、装配不变量（如「loop 构造点唯一」） | ~30 条 | <30s | pre-commit + CI |
| L2 JVM 行为 | 决策表、并发、账本、事件投影（81 个自编译 harness 并成一个 Gradle module） | ~90 条 | <60s | 本地 + CI |
| L3 真机矩阵 | 悬浮窗/键盘/磁贴/ASR/权限撤销/省电 | ~40 条 | 夜间 + 发版 | 2 个 API level |

### 5.2 反假绿（这是重点）

1. **断言必须剥注释再匹配**。578 处 `grep -q` 里只有 4 处做了；改成统一 helper `code_grep`（去掉 `//`、`*`、`#` 行首注释后再匹配），并把它写进 `gate.sh` 的必检项。
2. **每轮跑 targeted mutation**。仓库里已有 3 个 `mutate*.py`，但 CI 从不调用。选 20 条关键守卫，CI 里各做一次「删掉实现 → 必须变红」的自动验证，任何一条没红就判失败。
3. **门禁 5 加一条补充判据**：`SKIP>0` 时不算总数，但要求「PASS+SKIP+FAIL == 登记数」，任何一个 runner 既没 PASS 也没登记 SKIP 就红。
4. **arch 基线自校验**：`arch-baseline.txt` 的每一行 `layer` 豁免都必须有 `# 日期 + 理由 + 谁批的`，且 CI 比对「本文件的历史只增不减」——加豁免要过 review，不是改个文件就绿。

### 5.3 CI 成本

- 缓存 `~/.gradle` 与 NDK/cmake（现在每轮重装，`build.yml:57-70`）。
- 去掉 `--no-daemon`（`build.yml:288`）。
- 146 个脚本串行改成 4 组分片并行（按 core / app / qa-lib / 真机分组）。
- 目标：PR 反馈 **≤8 分钟**，发版全量 ≤15 分钟。

## 7. 明确不做

| 不做 | 理由 |
|---|---|
| 引入 Hilt/Koin | 装配问题不是「依赖注入框架缺失」，是「没有装配者」。加了框架只是把 `AppGraph` 换成注解，`SessionFactory` 该写还得写 |
| 现在就切成 6 个 Gradle 模块 | 编译期收益小，`UiItem` 迁移前硬拆会让每次改动跨模块，反而更慢 |
| 唤醒词 | spec §3.7 的账没变：1–3% 电量/小时换「少点两下」 |
| 重写 UI | `ChatScreen` 3,186 行的债要用「切 Controller」还，不是用重写还——重写会把 30 多个真机修过的边界条件一起丢掉 |
| 引入协程调度框架 / Actor 库 | `AgentRuntime` 用单线程 FIFO + Mutex 足够，一行 `Mutex` 比一个框架的可观测性更好 |

## 8. 需要你拍板的六件事

1. **运行时所有者放哪个模块**：新建 `:runtime`（干净，但要动 `settings.gradle` 与 CI），还是先放 `app/runtime` 包（快，但边界靠守卫）。**建议先包后模块**。
2. **桌宠历史要不要落盘**：保留独立上下文但落盘可恢复（本文建议），还是继续关闭即焚。前者多 2 人日，后者每次关闭都在惩罚用户。
3. **外发审批的默认档**：本回合读过文件/屏幕后，`web_search` 是「必须每次确认」还是「首次确认后 5 分钟内免问」。后者体验好，前者安全账更干净。
4. **是否接受 P1 期间暂停新功能**：`AgentRuntime` 落地会碰三个入口，同期加功能会反复冲突。
5. **真机矩阵的机型**：现在只有模拟器结论（P11 9/10）。国产 ROM 的省电策略、键盘高度、磁贴权限三件事，模拟器永远测不出来。
6. **验证改造的优先级**：先做「剥注释 helper + mutation 进 CI」（1–2 人日，立刻提升判别力），还是先做「81 个 harness 并成 Gradle module」（5–7 人日，提升本地反馈速度）。**建议先前者**——假绿比慢更贵。
