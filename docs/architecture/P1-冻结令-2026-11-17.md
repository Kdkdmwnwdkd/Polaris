# P1 冻结令（2026-11-17 起生效）

> 一句话：**到 `AgentRuntime` 落地为止，这个仓库只修不加。**
>
> 依据：[`AICoding-架构方案-v3-2026-11-17.md`](AICoding-架构方案-v3-2026-11-17.md) §6 路线图 P1（22–29 人日）。
> 拍板来源：用户在 2026-11-17 选择「P1 期间暂停新功能」。

## 为什么必须冻

P1 的核心动作是把「谁拥有运行时」从三个入口各自为政，改成一个所有者：

| 入口 | 位置 | 现状 |
|---|---|---|
| 主界面 | `ui/ChatViewModel.kt`（3400+ 行） | 自建 loop、自带 45 个工具注册、自带审批 |
| 桌宠 | `pet/PetAgentSession.kt` | 自建 loop、5 个工具、`approval = null` |
| 子代理 | `agent/SubAgentRunner.kt` | 自建 loop、另一套工具集 |

这三处要合并成 `AgentRuntime`，意味着**同时改三个文件的构造、生命周期、事件投影**。
如果同期还有人在加工具、加设置项、加第四个入口，冲突不是「偶尔 merge 一下」，
而是「每加一个功能，三个入口都要跟着改一遍」——那正是这套结构烂掉的原因。

冻结不是流程洁癖，是让一次结构性改动有可能收敛。

## 允许 / 不允许

| 改动 | 判定 | 说明 |
|---|---|---|
| 修 bug（有复现步骤） | ✅ 允许 | 包括 UI 崩溃、数据丢失、权限、真机适配 |
| 加验证（`scripts/qa/run-*.sh`、harness 用例） | ✅ 允许 | 越多越好，这是 P1 的验收资产 |
| 改文档 / 注释 / KDoc | ✅ 允许 | 尤其是把过时注释改成事实 |
| 性能 / 启动时间 / 耗电优化 | ✅ 允许 | 不改对外行为即可 |
| 依赖升级（含安全补丁） | ✅ 允许 | 但 `core` 的架构约束不变 |
| 新增工具（`ToolCatalog` 加行） | ❌ 冻结 | 三个入口的工具集都要跟着改；P1 里统一由 `ToolSource` 声明 |
| 新增设置项 / 开关 / 档位 | ❌ 冻结 | 设置面已经是 6 页；冻结期只允许给已有项补说明 |
| 新增桌面入口（磁贴 / 通知 / 快捷方式 / 小组件） | ❌ 冻结 | 每个入口都是一份 `SessionFactory`，P1 要把它们做成一份 |
| 新增 `Capability` 枚举值 | ❌ 冻结 | 现在只有 2 值，P1 要与 `CapabilitySpec` 一起定 |
| 重构 `ChatScreen` / 换 UI 框架 | ❌ 冻结 | 见方案 §7「明确不做」 |
| 加唤醒词 / 常驻录音 | ❌ 冻结 | 电量账没变 |

## 例外怎么走

只有一种情况可以破例：**不修就会让用户丢数据或没法用**。

破例要同时满足三条，缺一条就等 P1 结束：

1. 在本文末尾「破例记录」里写一行（日期 / 改了什么 / 为什么不能等）；
2. 该改动**不新增**上面表里的任何一类结构（不新增工具、不新增入口、不新增设置项）；
3. 改动后 `bash scripts/qa/gate.sh` 全绿，`arch-baseline.txt` 与 `harness-baseline.txt` 不增行。

## 冻结期的日常判据

改完代码问自己一句：**这次改动会不会让 `AgentRuntime` 多一个要迁移的调用点？**

- 不会 → 可以提交。
- 会 → 它属于 P1，写进路线图，不要现在做。

## 解冻条件

三条同时满足才解冻：

1. `AgentRuntime` 接管主界面、桌宠、子代理三个入口的 loop 构造（`productionSeams` 有真实调用者）；
2. `Consent` / `ToolSource` / `CapabilitySpec` 三个契约有第一版实现，且桌宠有审批通道；
3. 真机矩阵（[`docs/qa/真机矩阵-v1.md`](../qa/真机矩阵-v1.md)）跑过一轮，结论落在仓库里。
