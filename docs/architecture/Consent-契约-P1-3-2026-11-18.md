## 0. 一句话

`ToolApproval?` 里的 `null` 同时表示「这条通道没有弹窗位置」和「忘了传」。
把前者变成 `Consent.Deny(reason)` 之后，**「没能力」必须带理由写出来**，后者只剩编译期可见的缺省。

## 1. 修前是什么样

| 构造点 | 参数 | 实际含义 |
|---|---|---|
| `RealAgentLoop` | `approval: ToolApproval? = null` | 主界面传值；桌宠不传 |
| `SubAgentRunner` | `approval: ToolApproval? = null` | 透传主回合，可能为 null |
| `RegistryToolExecutor` | `approval: ToolApproval? = null` | 由上面两层传下来 |
| `SkillExecutor.buildToolExecutor` | `approval = { … }` | 技能网络白名单 |

审计 F4 已经把运行期改对了：**缺审批 → 拒绝执行**（`no_approver`），不再静默放行。
所以这次改造不是为了堵安全洞，是为了堵**表达**的洞：

```kotlin
// 修前：读者无法判断这是设计还是疏忽
approval = null
```

一个 `null` 背后可能是「桌宠气泡上没地方放按钮」（设计），也可能是「新加的第四个入口忘了接线」
（bug）。两者的运行时表现完全一样，只有翻 git blame 才能分开。

## 2. 为什么不用「必填参数」

这是本次设计里唯一有争议的决定，值得写清楚。

「让 `approval` 成为必填」听起来最彻底：编译器会点名每一处构造。实测代价是：

| 调用点 | 数量 |
|---|---|
| `RealAgentLoop(` | 96 |
| `RegistryToolExecutor(` | 11 |
| `SubAgentRunner(` | 1 |

其中绝大多数在 `scripts/qa/` 里，语义是「我只想测工具执行，不测审批」。把它们逐一改成必填，
得到的是 **107 行噪声**，而**判别力为零**——每个 harness 都会随手传一个值让编译过去，
没人会停下来想「这个通道到底该不该有审批」。

真正需要判别力的地方只有**四个生产入口**。所以改成三层：

| 层 | 手段 | 保证什么 |
|---|---|---|
| 类型 | `Consent` 是 sealed，`null` 不可表达；`Deny` 必须带 reason | 表态时必须想清楚「有没有通道」 |
| 默认值 | `Consent.unset("通道名")` | 忘记表态时退到**拒绝**（方向是关），且日志能看出是哪一层漏了 |
| 门禁 | `run-consent-verification.sh` 的 A4 | 四个生产入口逐个点名，漏一个立刻红 |

合起来的性质：**「忘记传」的后果是功能不可用且原因可见，不是静默放行。**

## 3. 契约长什么样

```kotlin
sealed interface Consent {

    /** 有弹窗通道：问过用户才执行。 */
    class Ask(val handler: suspend (AgentTool, JsonObject) -> Boolean) : Consent

    /** 本通道明确没有审批界面：需要审批的调用一律拒绝。 */
    data class Deny(val reason: String) : Consent

    /** 对一次「需要审批」的调用给出裁决。 */
    suspend fun decide(tool: AgentTool, args: JsonObject): Decision
}

sealed interface Decision {
    data object Allowed : Decision                    // 问了，允许
    data object Denied : Decision                     // 问了，拒绝
    data class Unavailable(val reason: String) : Decision  // 没问成：没有通道
    data class Failed(val cause: String) : Decision   // 想问了，但回调自己崩了
}
```

四种而不是布尔，是因为布尔会压扁两对区别：

- `Unavailable` vs `Denied` —— 前者要告诉用户「这里没有审批按钮」，后者是「你拒绝了」；
  混成 `false` 就会对桌宠用户说「你拒绝了该操作」，而他从没被问过。
- `Failed` vs `Denied` —— 前者要记 `AgentLogger.e`（我们的 bug），后者记 `w`（正常路径）。

### 3.1 为什么裁决也在契约里，而不是执行器里

原先把 try/catch 写在 `RegistryToolExecutor`：

```kotlin
val allowed = try { approver(tool, args) }
              catch (cancel: CancellationException) { throw cancel }
              catch (e: Throwable) { false }
```

两个后果：

1. **语义散落**——「取消不是拒绝」只有执行器知道。桌宠气泡、后台任务想复用就得抄一遍，
   抄漏一次，用户点「停止」就会看到「你拒绝了这个操作」。
2. **测不了**——`RegistryToolExecutor` 牵 `ToolRegistry`，后者用 `JsonSchema.serializer()`
   要序列化编译器插件。行为断言在没装插件的机器上编不过 → SKIP → **静默消失**。
   这和 `McpServerHost` 当初绕开 `ToolRegistry` 是同一个教训。

搬进 `Consent.decide` 之后，`Consent.kt + AgentContract.kt + ToolResult.kt` 三个文件就能
真编真跑——本 harness 就是这么跑的。执行器退化成一层 `when`，不再拥有任何审批语义。

## 4. 四个入口现在长什么样

| 入口 | 声明 | 语义 |
|---|---|---|
| 主界面 | `Consent.ask { tool, args -> approvalHandler(tool, args) }` | 弹卡 |
| 子代理 | `Consent.ask { … }`（lambda 间接引用） | 复用主回合的卡，不另造一份 |
| 桌宠 | `Consent.ask { tool, args -> PetApproval.ask(tool, args) }` | 气泡上的确认卡（**第二阶段已落地**，见 §6） |
| 技能 | `Consent.ask { … SkillNetGrant.allows(…) }` | 按 manifest 的网络白名单自动裁决 |

桌宠这一格在第二阶段之前是 `Consent.Deny("桌宠气泡上没有审批按钮")`。那句话在当时是对的
——它把「没有审批界面」写成了一个**带理由的值**，而不是一个含义含糊的 `null`，用户点开
桌宠会话能看到「该操作需要用户确认，但桌宠气泡上没有审批按钮，已拒绝执行（app_launch）」。

但它同时是一份**功能判决**：桌宠的工具表因此被永久锁在四个只读工具上。第二阶段把
判决撤掉了——不是因为「多一个工具更好」，而是因为那句话说的是「没有按钮」，
按钮是可以做的。

## 5. 验证（`scripts/qa/run-consent-verification.sh`）

**A 段（8 条契约事实）**

| # | 断言 | 破了会怎样 |
|---|---|---|
| A2 | 三个执行器的参数不再是 `ToolApproval?` | `null` 重新变成两种含义的共同表示 |
| A3 | 三处默认值都是 `Consent.unset()` | 缺省方向变成放行 |
| A4 | 四个生产入口都显式声明 | 某个入口退到默认拒绝，功能整体不可用 |
| A5 | 桌宠的 `Ask` 接到了 `PetApproval` | 写一个没人接的 `Ask`，比写 `Deny` 更糟：挂 45 秒后说「用户拒绝」 |
| A6 | 裁决与拒绝分支都在 `tool.execute` 之前（**行号比较**） | 「先执行后拒绝」 |
| A7 | 执行器里不再直接调用审批回调 | 语义被抄成两份 |

A6 是本 harness 里唯一能防「先执行再拒绝」的断言——B 段只测裁决本身，测不到分支顺序。

**B 段（12 条裁决行为，真编真跑）**

覆盖：`Deny` 的理由原样带出、`unset` 点名通道、`Ask{true/false}`、handler 恰好调一次、
**连续两次决定会问两次**（不缓存授权——「本次会话不再询问」的短路属于上层，不属于契约）、
handler 崩了归 `Failed`、**`CancellationException` 必须上抛**、四种 `Decision` 互不相等。

### 5.1 第二阶段（`run-pet-consent-verification.sh`，26 条）

**A 段（8 条接线事实）** —— 这些是「卡片真的会出现在屏幕上」的那一半，行为 harness 证不了：

| # | 断言 | 破了会怎样 |
|---|---|---|
| A2 | 桌宠的 `app_launch` 包了 `ConfirmRequiredTool` | 有副作用却不问用户 |
| A3 | 装饰器同时覆盖 `needsApproval` 与 `needsApprovalFor` | 工具自带的参数级判断把包装盖掉（「包了但没生效」） |
| A4 | `PetPanel` 渲染了 `ApprovalCard` 并接两个按钮 | 组件写好了没人画 |
| A5 | 宿主订阅 `pending` 并**自动展开气泡** | 收起态下用户空等 45 秒 |
| A6 | `hide()` 调 `onHostDestroyed()` | 协程吊满 45 秒，桌宠像卡住 |
| A7 | 超时窗口在 10s–120s | 太短来不及读，太长吊死回合 |
| A8 | 审批路径不落盘 | 「本次允许」被当成长期授权 |

**B 段（17 条网关行为，真编真跑）** —— 四种收场 + 不串台：

超时真的等满窗口、超时后点「允许」不算数、连点两下只认第一下、`cancelAll` 之后
新的 `await` 立刻 `CANCELLED`（不重新开一个没人看的等待）、`reopen` 后能重新等待、
**协程取消上抛且槽位已清**、后一个等待能接管前一个（不会双双吊死）。

B8 是这个 harness 建出来的当天就抓到的一个真 bug：`cancelAll` 原本用
`complete(false)`，等待方拿到 `DENIED`，「界面被销毁」被报告成「用户拒绝了该操作」。
现在槽位是 `CompletableDeferred<Outcome>`。

## 6. 第二阶段：桌宠的确认卡（已完成）

### 6.1 四件东西

| 文件 | 职责 | 为什么单独一层 |
|---|---|---|
| `core/ApprovalGate.kt` | 挂起 / 超时 / 取消，四种 `Outcome` | 只依赖 coroutines，一个文件就能真编真跑 |
| `app/pet/PetApproval.kt` | 进程级状态 + 参数摘要 + 生命周期 | 要 Context / StateFlow，不能进 core |
| `PetPanel.ApprovalCard` | 一张卡：工具名 + 一句参数 + 两个按钮 | 纯渲染，状态由宿主传 |
| `app/pet/ConfirmRequiredTool.kt` | 给任意工具加「必须确认」 | 场景差异留在调用点，不改工具类 |

桌宠的工具表因此多了 `app_launch`（`ConfirmRequiredTool(AppLaunchTool(ctx))`）。
选它不选写文件：桌宠的典型句子是「帮我打开微信」，用户说完就去看微信了，
这是悬浮球唯一无可替代的场景；写文件那种事该回主界面等。

### 6.2 三个取舍

**一、`cancelAll` 传 `Outcome` 而不是 `false`。**
最初实现里 `cancelAll()` 用 `complete(false)` 解除等待，和「用户点拒绝」共用一个值。
harness 的 B8 直接抓到了：界面销毁后等待方拿到的是 `DENIED`，工具结果会写「用户拒绝了
该操作」——而用户从头到尾没看见那张卡。现在 `CompletableDeferred<Outcome>` 把
`CANCELLED` / `DENIED` / `TIMEOUT` / `ALLOWED` 分开传。

**二、没有「本次会话都允许」。**
那需要一个持久化的策略表（哪类工具永久放行），现在没有。做一个只在内存里生效的
「本次允许」，用户会以为它长期有效，下次会点得比这次快——比每次都问更危险。
`run-pet-consent-verification.sh` 的 A8 盯着审批路径里不许出现 `SharedPreferences`。

**三、卡片出现时自动把气泡弹开。**
只订阅不展开，收起态下卡片根本不在组合里，模型会停在 45 秒超时——用户眼前只有
一个静静待着的悬浮球。`applyExpanded(true, focusInput = false)`：这一步是点按钮，
弹半屏键盘会把卡片自己盖住。

## 8. 与 MCP M1 的关系

M1 写的三句话现在有两句需要更新：

- ~~「没有审批界面就拒绝：`approver == null` 时一律 `-32004`」~~ → 机制不变，但
  `null` 会被 `Consent.Deny` 取代。M1 的行为是对的，**表达方式**会在 M2 统一。
- 「档位 ≠ 审批」—— 不变，且现在更清楚：档位决定**可见性**，`Consent` 决定**问不问**。
- 「不在场 = 拒绝」—— 不变，那是 `McpServerHost` 的在场判定，独立于 `Consent`。

也就是说：**M2 的审批卡不需要新造一套审批实现，它只需要一个 `Consent.Ask` 的实现**。
这是本次改造给 M2 省下的最大一笔。
