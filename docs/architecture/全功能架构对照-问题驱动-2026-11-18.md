# 全功能架构对照 · 以我们的缺陷为主轴 · 2026-11-18

> 上一篇《同类-Agent-架构横向对比》讲的是**范式**（五种，我们落在最差的 E）。
> 这一篇讲**逐个功能域**：我们的每个已知问题 → 谁撞过同一面墙 → 他们怎么解 → 我们的约束不同在哪 → 我们具体怎么改。
>
> 主轴是**我们的问题**，不是别人的项目。没问题的域也列出来（标「不动」），免得看起来像在凑数。

## 1. 运行时所有权

### 我们的问题

```
app/.../ui/ChatViewModel.kt:2039      private val loop = RealAgentLoop(
app/.../pet/PetAgentSession.kt:151               RealAgentLoop(
core/.../agent/SubAgentRunner.kt:99              RealAgentLoop(
```

三处平级，谁也不从属于谁。后果不是"代码重复"，是**三个真值源**：主界面和桌宠可以同时进 `send`，子代理再开 3 路（`SubAgentLogic.kt:33` `MAX_TASKS = 3`），而 `RealAgentLoop.kt:292` 的注释还写着「一次只有一个回合在跑（UI 侧串行保证）」——这个前提今天已经不成立。

### 谁撞过同一面墙

**OpenHands 的 V0 → V1 是最好的一课**：V0 有 `AgentController` + `Runtime` 两层抽象，V1 **把 Controller 删了**，收敛成 `Conversation`（持有状态与事件日志）+ `Workspace`（执行）。理由写在迁移说明里：**controller 没挣到它的位置**——它只是把「循环 + 状态 + 持久化」又包了一层，没有提供新的所有权。

Claude Code 走的是另一条：**一个 loop，subagent 是隔离子上下文**，只把摘要回传主会话（`AgentTool` 开新窗口，约 7× token，但主上下文零污染）。

### 约束差异

| | 他们 | 我们 |
|---|---|---|
| 进程模型 | 桌面/服务端，进程不会随时被杀 | Android，随时可能被回收 |
| 并发来源 | 用户开多个终端窗口 | 主界面 + 桌宠 + 子代理 + MCP 客户端，**四路** |
| 模型成本 | 云端为主，可并行 | 本地 4k 上下文，**并发即爆内存** |

### 所以我们的做法

`AgentRuntime` 的验收判据只有一条：**它能回答「现在有几个 loop 在跑」，并且答案永远是 ≤1/backend**。做不到这条，就只是第四个构造点。

```kotlin
// app/runtime/AgentRuntime.kt —— 不 import UI，不做决策，只发许可
interface AgentRuntime {
    /** 为 (session, source) 申请一次回合所有权；拿不到就挂起排队，不抛异常。 */
    suspend fun acquireTurn(sessionId: String, source: RunSource): TurnLease
    /** 资源级许可：local=1 / cloud=2 / terminal=1。TurnLease 内部再拿，调用方看不到。 */
    suspend fun acquireResource(kind: BackendKind): ResourceLease
    /** 代次号：取消后旧协程的写入必须被丢弃。 */
    fun generation(sessionId: String): Long
    fun cancel(sessionId: String): Boolean
}
```

- **不做**：不要在 Runtime 里塞审批、工具装配、上下文压缩——那是它变成第二个 controller 的开始。
- **验收**：一条 harness 断言——同时发起主界面回合 + 桌宠回合，第二个必须在 `acquireTurn` 挂起，且 `generation` 不变。
- 成本 5–7 人日。

## 2. 后台存活与冷启动续跑 —— **这块我们是对的**

### 我们的现状

- `AgentRunService`：前台服务保活，类注释明确写了边界——「防不了强杀，进程被杀不自动续跑」。
- `AgentRunStateStore`：运行态落盘。
- `AutoResumePolicy`：**三态决策表**（RESUME / PROMPT_ONLY / SKIP），有熔断（续跑次数）、有时效、有判定顺序，注释解释了"为什么不是两态"。

这是全仓设计质量最高的模块之一。**不要改。**

### 对照

| | 做法 | 结果 |
|---|---|---|
| DSH-Android | 内嵌 Node 引擎跑在 FGS 里，**任务后 5 分钟停引擎** | 省电，但后台插件定时器停摆 |
| Android 15+ | FGS 类型强制 + dataSync 6 小时/24h 配额，超时 `onTimeout` | 不处理就 `InternalServiceTimeoutException` |
| WorkManager | 保证最终执行，但**不保证准时**，periodic 最小 15 分钟 | 不适合「用户点了现在就要跑」 |

### 唯一要补的

`targetSdk=28` 让我们**绕过了** FGS 类型强制与 6h 配额——这是兼容性红利，也是**有到期日的债**。升级到 34+ 时：`foregroundServiceType` 必须声明、`dataSync` 配额要处理、`POST_NOTIFICATIONS` 变成硬要求。现在就把这三条写进 `docs/ops/` 的升级清单，别等到那天现查。

## 3. 会话与上下文

### 我们的问题

| 层 | 上限 | 证据 |
|---|---|---|
| 内存（发给模型） | `MAX_TOOL_RESULT_CHARS` = 24k 字符 | `ContextBudget.kt:101-108`，且做了 token 估算、剥图、整步丢弃、首条锚点、`tool_calls↔tool` 配对 |
| 落盘 | **4000 字符**，无标记 | `ConversationStore.kt:62`，`:181/:188/:193/:203/:206` |

同一份对话，两套保真度，差 6 倍。会话内 UI 看全文，重启后读到截断版，冷启动续跑基于断掉的内容继续推理——**模型会以为用户话说一半**。

### 谁撞过

- **Claude Code**：五层渐进压缩（budget → snip → microcompact → collapse → auto-compact），关键点是**压缩只影响「发给模型的视图」，append-only JSONL 存档不动**。
- **OpenHands**：Condensation 产出 `CondensationSummaryEvent`，被折叠的事件**仍在日志里**，只是不再进 LLM 视图。

两家的共同点不是"压缩算法好"，是**存档与视图是两个对象**。

### 所以我们的做法

```
Text
MsgRecord { content, truncated: Boolean, origChars: Int }
   └─ 正文 > 阈值时：正文外置 <turnId>.tool.jsonl，MsgRecord 只存 ref + 前 200 字符
```

- **先做标记**（1 天）：加 `truncated`/`origChars`，容量先不动。这一步就能消掉"看起来像模型话说一半"的误解。
- **再做外置**（2 天）：复用 `AtomicJsonFile`（tmp→fsync→rename），不新建存储。
- **不做**：不要上 gzip 分片、不要引入数据库。`ConversationShard` 已经只存 `turns`（真源）、`messages` 现算——这个大方向是对的，别推翻。
- 验收：重启后打开一个长工具结果会话，UI 显示「已截断，原文 18,432 字符」。

## 4. 工具装配

### 我们的问题

- `ChatViewModel.kt` 里 **54 处 `register(`**，桌宠 6 处，子代理另有一套。
- `ToolCatalog` 是单一真源（57 条，含 `Capability`/`Approval`/`audit`），但**生产注册不读它**——两份清单靠人保持一致。
- 工具顺序影响 KV 缓存前缀（`ToolCatalog.kt` 注释自己写了这一点），而顺序由「谁先 register」决定。

### 谁撞过

**Claude Code 的 5 步装配**：base 枚举（≤54）→ 模式过滤 → deny 规则预过滤 → 接 MCP → 去重。关键在**装配是纯函数、顺序确定**——同样的配置永远得到同样的工具表，KV 缓存前缀才稳。

**droidrun 的 App Cards**：11 个原子动作 + 每个 App 一份「这个 App 怎么用」的知识卡，按当前前台包名注入。常驻上下文只有动作定义，知识按需加载。

### 所以我们的做法

```kotlin
// core/tool/ToolSource.kt
interface ToolSource {
    val id: String
    fun tools(): List<AgentTool>          // 纯函数，不带状态
}
// 五个 View：Desktop(57) / Pet(6) / SubAgent(父级子集) / McpReadonly(capability==SAFE) / McpFull
// Assembler: sources.flatMap { it.tools() }.sortedWith(catalogOrder)  ← 顺序由 Catalog 定，不由注册顺序定
```

- **顺序锚点**：`Assembler` 输出必须按 `ToolCatalog` 的声明序排序，而不是并入序。这一条能直接写进 harness（比对两次装配的 JSON 字符串）。
- **App Card**：复用已有 `use_skill` / `LoadSkillTool`，加一个"按前台包名挂卡"的中间件，不新增工具。
- **砍工具？不砍**。OpenHands 能用 4 个工具是因为它写代码；手机端没有这个退路。57 个是必要的。
- 成本 8–10 人日。

## 5. 审批与授权

### 我们的问题

`ApprovalScope.kt:139`：

```kotlin
if (toolName !in SHELL_TOOLS) return ApprovalGrant(group, label, memorizable = true)
```

**除 shell 外所有工具默认可记忆**，包括 `github_commit`（`ToolCatalog.kt:183`，`Approval.GIT_WRITE`）。用户点一次"不再询问"，之后就是永久的。

### 谁撞过

- **Claude Code**：deny 永远压 allow；工具先被过滤出模型视野；**权限在 resume 时不恢复**（"trust is always re-established"）。
- 它给出了一条硬数据：**用户对权限弹窗的同意率 93%**——所以 Anthropic 的结论不是"加更多警告"，而是"上自动分类器 + 收紧默认"。手机端弹窗更烦、更容易无脑点，这条对我们更成立。
- **MCP 规范**：scope 最小化 + 逐步提权（step-up），token 必须绑定受众；明确"tool annotations 不可信，除非来自可信服务器"。

### 约束差异（为什么不能照抄 deny-first）

桌面端弹窗成本 ≈ 0（键盘回车），手机端要切窗口、要看清、要够到。全量重问会直接毁掉「说一句话就把事办了」的体验。**我们要的是记忆有边界，不是取消记忆。**

### 所以我们的做法

| 机制 | 参数 | 理由 |
|---|---|---|
| TTL | 30 分钟 | 覆盖"一次连续操作"，不覆盖"明天再来" |
| 回合上限 | 20 回合 | 防长会话里无限续期 |
| 升级失效 | 只读→写、写→发 | `github_commit` 属"发" |
| 身份失效 | uid 变化（Shizuku/shell） | 换执行身份等于换权限，`ApprovalScope` 已有类似审计注释 |

- 落点：`ApprovalScope.kt:139`，加一个 `GrantPolicy` 参数，不改 `ApprovalGate` 的四种 Outcome。
- 验收（静态可查）：`DEFAULT_EGRESS_TOOLS` ⊇ `ToolCatalog` 里所有 `Approval.GIT_WRITE` 工具。
- 成本 1–2 人日。

## 6. 外发与提示注入 —— 这是最被低估的一域

### 我们的问题

Polaris 同时具备三件事：

| 要素 | 我们的能力 | 证据 |
|---|---|---|
| 私有数据 | `read_file`、`conversation_search`、`memory_search`、通知、短信 | 沙箱 + 敏感目录审批 |
| 不可信内容 | `web_search`、`browser_*`、MCP 客户端返回、技能脚本输出 | 同一上下文 |
| 外发通道 | `http_request`、`github_commit` + `git push`、`web_*` | `EgressGuard` 只列了 5 个 |

这三件事凑在一个 context 里，就是 Simon Willison 说的 **lethal trifecta**——不需要漏洞，一段网页文字就能让 Agent 读走文件并发出去。而我们的唯一闸门 `EgressGuard` **漏了 `github_commit`**，且它是可记忆授权。

### 谁撞过

- **CaMeL（DeepMind）**：把控制流和数据流分开——特权模型只读用户指令、先写出计划；隔离模型读不可信内容但**没有工具权限**；解释器给每个值打能力标签，限制它能流到哪。AgentDojo 上拦掉 67–100% 注入，代价是任务成功率从 84% 降到 77%（7 个点）。
- **Rule of Two（Meta）**：一个无监督 Agent 最多同时持有三要素中的两个；需要第三个时必须人批。

### 约束差异（为什么不做 CaMeL）

CaMeL 要多一个模型 + 一个解释器。手机端本地模型 4k 上下文、单进程、耗电敏感——**多一次推理就是多 2 秒和多一倍电**。我们不能付这个代价。

### 所以我们的做法：Rule of Two 的**批次级**廉价版

在 `RealAgentLoop` 的工具批次处（已经有 `executeBatch`，`RealAgentLoop.kt:794`）加一条判定：

```
同一回合内：
  若 已发生「读私有数据」（read_file 命中敏感根 / conversation_search / memory_search）
  且 本批次含「外发工具」（EgressGuard 集合 ∪ GIT_WRITE）
  → 强制升档：不可记忆 + 弹窗必须显示「本次外发的内容来源：<file:line/工具名>」
```

- **为什么是批次级而不是数据流级**：数据流级要在每个工具结果上打 provenance 标签，改动面覆盖 57 个工具；批次级只需要在 `executeBatch` 一处判断，能拦住"读文件→发出去"这个真实攻击链的 90%。
- **代价**：会有误报（用户就是想"读文件然后发给我自己"）——但误报的代价是一次确认，漏报的代价是数据外泄。
- **配套**：`github_commit` 进 `EgressGuard`（v4 P0 已有）。
- 成本 3–4 人日。验收：一条行为断言——read_file(敏感) → github_commit，必须返回 `needsApproval=true` 且 `memorizable=false`。

## 7. 设备操控：动作没有回执

### 我们的问题

`UiAutomationTools.kt:231` → `"已在 (x, y) 点击"`。`dispatchTap()` 返回 true 只代表**事件注入成功**，不代表**界面响应**。模型要靠下一步 `ui_tree` 自己发现，多一次往返，还可能误判成"没反应，再点一次"。

### 谁撞过

| | 做法 |
|---|---|
| droidrun | 动作后等 0.5s 比屏幕，不 stable 继续等；下一步同时给「前一张树 + 当前树」 |
| Mobile-Agent-v3 | `ActionReflector` 比前后截图 → A/B/C 分级；**连续 2 次 B/C 才**上报重规划 |

### 约束差异（为什么我们更便宜）

他们只能从设备外部看屏幕（ADB/Portal），所以必须截图 + VLM 或像素 diff。我们有 `UiNodeSummary`（index/text/desc/resId/clickable/bounds，`AgentAccessibilityService.kt:93-101`）——**直接 diff 结构树，不用截图、不用模型**。而且 `waitForFreshWindow` 的轮询骨架已经写好（`:455-479`）。

### 所以我们的做法

改 `runOnService`（`UiAutomationTools.kt:40-68`）一个函数，覆盖 tap / long_press / swipe / input / key 五个工具：

1. 动作前取指纹：`节点数 + 前 N 个 (text|resId) 的哈希`
2. 动作后轮询到「指纹变化」或 600ms 超时（复用现有 `delay(pollMs)`）
3. 结果码：`tap_ok` / `tap_no_effect`（附可能原因：不可点区域 / 弹窗遮挡 / 未加载完）

- **只对 `clickable=true` 的点击做判定**，滑动/输入先不做（误报高）。
- 成本 2–3 人日。验收：注入一次空点击，结果码必须是 `tap_no_effect`。

## 8. 多入口

### 我们的问题

四个入口，四套装配，三套事件：

| 入口 | 装配 | 历史 | 审批 |
|---|---|---|---|
| 主界面 | 54 处 register | 落盘 | 弹窗 |
| 桌宠 | 6 处 register | **内存** | 桌宠气泡卡 |
| 子代理 | 父级子集 | 独立 | 继承父级？ |
| MCP 客户端 | `McpToolSource` | 无 | `McpTier` + 逐次审批 |

用户看到的"一个 App"，内部是四个近似独立的系统。

### 谁撞过

- **Claude Code**：多个入口（CLI / IDE / web）**共用同一个 loop**，只是渲染不同。
- **OpenHands**：多个客户端（WebSocket / CLI）订阅**同一个 EventStream**，事件是唯一真源。

### 所以我们的做法

一个 Runtime（§1）+ 一份事件真源（已有 `TurnEvent`，`TurnObserver.kt:44`）+ N 个 View：

- 桌宠**默认镜像**：订阅事件，用纯函数折叠成 phase（`phaseOf(List<TurnEvent>)`），零历史零并发。Mao-pet 就是这么做的——它**不持有窗口、不持有会话**，只推 12 态。
- 桌宠**独立模式**：用户显式"让它自己办"时，经 Runtime 拿许可，保留 `PetAgentSession`。
- 子代理：不再自建并发，改借 Runtime 的资源许可（这是 v4 已经定的）。
- MCP：`McpTier` 只做可见性，审批不变——这个设计是对的，别动。

成本：phase 纯函数 2–3 天；桌宠双模式 5–8 天（依赖 Runtime）。

## 9. 扩展机制 —— **方向对，别动**

| | 机制 | 上下文成本 |
|---|---|---|
| Claude Code | hooks（零）→ skills（低，`SKILL.md`）→ plugins（中）→ MCP（高） | 成本梯度是刻意设计的 |
| DSH | npm 插件，必须背 Node（110MB 起） | 生态大，体积代价大 |
| **我们** | 声明型 skill（`SKILL.md` → `use_skill`）+ MCP 双向 | 39MB |

我们选了「声明型 skill + MCP」而不是「插件宿主」，这是正确的取舍，**不要为了生态改**。唯一可补的是 §4 的 App Card（按包名挂知识卡），复用现有 `use_skill` 通道即可。

## 10. 验证判别力

### 我们的问题

交付线在仓库副本上做了变异实测，**5/5 全绿或 SKIP**：

| 变异 | 结果 |
|---|---|
| `shouldSkipDialog` 对 shell/app_manage/git_write 直接放行 | 22/22 仍绿（行为段 SKIP） |
| `sensitiveReadRoot` 首行 `return null` | SKIP |
| MCP `?: false` → `?: true`（审批缺失＝放行） | A9 仍 PASS |
| 删掉 `BoundedBody.kt` | 7/0 全绿 |
| `CrashLogger.hasUnseen = false` | 42/42 仍绿 |

也就是说：**今天把「审批缺失就放行」提交上去，CI 大概率还是绿的。**

### 谁撞过

这不是 Agent 特有的问题，是测试工程的老问题——**mutation testing** 就是为此而生的：不问你写了多少断言，问「把实现改坏，测试会不会红」。业界做法（PIT / Stryker / 自建 mutant runner）都是同一套：选关键变异 → 跑测试 → 统计 kill rate。

### 所以我们的做法

不引入工具链（Kotlin 的 PIT 生态不成熟、CI 只有 19–24 分钟预算），**自建 20 条 mutant**：

- 每条 = 一处 `sed` 替换 + 一个期望变红的脚本；
- 只覆盖 10 个关键守卫（审批、出站、路径、MCP 鉴权、截断标记…）；
- CI 必跑，**不通过就红**，不允许 SKIP 计为通过（这一条比 mutant 本身更重要）。

成本 3–4 人日。这是 v4 的 P0 第一位——**在绿是假绿的状态下做重构，每次「红→绿」都可能是把断言改到能通过**。

## 14. 我不确定的

1. **批次级 Rule of Two 的误报率**——没有真机数据。缓解：先只拦「敏感根读取 + 可外发」，不做全量 provenance。
2. **动作回执 600ms 是否够**——千元机上可能偏短，需在真机矩阵标定（`docs/qa/真机矩阵-v1.md` 加一条）。
3. **TTL 30 分钟是否合适**——纯拍脑袋，没有用户数据。可先做成配置项，观察一周再定死。
4. **OpenHands 删 Controller 的教训是否适用于我们**——它的 Controller 是"多一层转发"，我们的 Runtime 若只做许可与代次号，职责更实。但如果实现中发现它开始管审批和装配，就该按 OpenHands 的做法砍掉。
5. **Mobile-Agent-v3 / droidrun 的具体实现细节**——只读了公开文档与行为描述，未读源码（许可与"不抄袭"原则），结论停在"机制层面"。
