# DSH 手机端生态实况 · 2026-11-18

> 结论先说：**「把 DSH 装进手机 + 一键装插件」不是设想，是已经跑出七种实现的成熟玩法。**
> 手机端插件可用率有实测数据：热门 50 个插件里 **42 个直接可用、6 个小改可用、2 个不可用**。
> 但没有任何一个方案把「Android 原生能力」和「DSH 插件生态」同时占住 —— 这正是 Polaris 的空位。

## 2. 「一键装插件」到底怎么成立的

不是靠改插件，是靠**把 Node 运行时搬进手机**。三条实现路径：

1. **JNI 内嵌 libnode**（DSH-Android）：Node 24 编译成 arm64 `.so`，App 内起服务。插件是标准 npm 包，`require` 到的 `node:fs`/`node:path` 全都在。
2. **proot/rootfs 跑完整 Ubuntu**（DSHA、dsh-Go）：连 `apt`、PTY、需要编译的原生模块都能用，兼容性最高，代价是 1 GB 级空间 + 启动慢。
3. **Termux 快照**（dsh-mobile-apk）：把 Termux 环境打进 APK 解压即用。

**结论：插件之所以「改一点就能用」，是因为运行环境根本没变**，只是换了个 CPU 和一层壳。

## 3. 硬数据：插件在手机上到底能不能用

`fish-pocket` 按下载量抽了社区前 50 个第三方插件，在 iOS 引擎上逐个走完「安装 → 启用 → 冷启动 → 卸载」：

| 结果 | 数量 |
|---|---:|
| 直接可用 | **42** |
| 允许/跳过安装脚本、指定版本或重启后可用 | 6 |
| 暂不可用 | 2 |

> 84% 零改动，96% 小改可用。注意这是在一个**被替换过底层**（just-bash / Worker / libgit2）的引擎上测的，比原版 Node 更苛刻 —— 说明兼容层做得出来。
> 该统计只验证「能被引擎加载」，功能未逐个试用。

## 4. 对 Polaris 的五条判断

1. **生态确实能拿，但拿的是「逻辑」不是「界面」。** 逻辑插件（工具、记忆、检索、Bot）随 Node 一起搬；界面插件在手机上全废，所以才有 E 类适配层和 fish-pocket 的 SwiftUI 重写。
2. **拿生态 = 背一个 Node 运行时。** 最省的 DSH-Android 也要 110 MB 包 + 500 MB 空间；proot 路线 1 GB 起。Polaris 现在 release 39 MB，这一步会让体积翻三倍以上。
3. **他们的空位是「真机」。** DSH 手机端操作手机全靠无障碍 + Shizuku/ADB，Android 14 才敢上虚拟屏；Polaris 的 `ui_tree`/`ui_tap`/`app_launch`/`device_notifications` 是原生一等公民。
4. **反过来输出更划算。** 把 Polaris 45 个工具包成 **MCP server**，让电脑/手机上的 DSH 通过 MCP 调用手机能力 —— 我们不用背 Node，他们拿到唯一缺的那块。
5. **不要照抄 AGPL/GPL 项目的代码。** `dsh-Go` 是 AGPL-3.0、`DSHBox` 是 GPL-3.0，抄一行就传染；`DSH-Android`（Apache-2.0）、`DSHA`/`kelai141`（MIT）才是可参考的。

## 5. 风险清单

| 风险 | 说明 |
|---|---|
| 体积与低端机 | proot 路线在 4 GB 内存机上是灾难；DSH-Android 的 110 MB 是下限 |
| 后台存活 | 内嵌引擎需常驻通知 + 自启动白名单，否则插件定时器停摆（DSH-Android 默认任务后 5 分钟停引擎） |
| 商店合规 | 用无障碍 + 读通知 + 读短信，Google Play 保护机制会误判（DSH-Android README 已明确提示侧载） |
| 安全边界 | 宿主审批可被 `dsh-purge` 一类插件拆除；Polaris 的 `ApprovalTier` + `EgressGuard` 是硬门禁，别为了兼容性把它降级成提示词 |
| 许可传染 | AGPL/GPL 项目仅可读思路，不可复制实现 |
