## 0. 一页结论

**v4 只做三件事，并且把 v3 的一件大事明确判死。**

| # | v4 要做 | 一句话 | 人日 |
|---|---|---|---|
| 1 | **运行时：两级并发** | 不是「单线程 FIFO」，是「turn 级排队 + backend 级许可」 | 6–9 |
| 2 | **同意：票据化** | `Ask` 返回 `Boolean` 是万恶之源；补 `Ticket/Channel/Scope/Expiry` 四个类型 | 5–7 |
| 3 | **验证：先修判别力** | 实测 5/5 关键断言在「删掉实现」后仍然绿或 SKIP | 3–5 |

| # | v4 明确**不做** | 理由 |
|---|---|---|
| A | `UiItem → TurnEvent` 全量迁移 | 真实编译面只有 3 个穷尽 `when`，28 处里 15 处是 `is` 谓词；成本 15–25 人日，收益接近 0 |
| B | `CapabilitySpec` 数据化 | 加第 3 类能力要动 6 处 `when` + 30 条枚举断言；改用 `Map` 注入 10 行拿到 80% 收益 |
| C | `core` 物理拆三模块 | 与 A 强耦合；A 不做，C 就是「为了拆而拆」 |

**一句话**：v3 诊断对了「没有所有者」，但把**并发模型**写错了（与子代理 3 路并行直接冲突），
也**低估了验证体系已经失效**这件事。v4 修正这两处，其余沿用。

## 2. 五条判断

### 判断一：运行时缺的不是「所有者」，是**两级并发模型**

「一个所有者」这句话前半对、后半错。对的部分：三个入口各自 `new` loop，参数各异，必须收。
错的部分：把所有回合压成一条串行队列，等于用架构解决一个不存在的性能问题，同时制造一个真实的产品问题。

现状的真实危害不是「并发太高」，而是**没有资源边界**：

| 危害 | 现状 | 证据 |
|---|---|---|
| 两份 loop 同时写同一份 `registry` 与检查点 | 无互斥 | `RealAgentLoop.kt:284`（注释即是自证） |
| 本地推理被两个回合交错 prefill | 无信号量 | `LocalLlamaClient` 单实例、无 `withPermit` |
| 取消权不在 Task 上 | 桌宠只能拆窗 | `PetOverlay.kt:336`；主界面靠 `isRunning`（`ChatViewModel.kt:1589`） |
| 冷启动两条路径互不知情 | `recoverInterruptedJournal` 与 `autoResumeIfPossible` 并行发起 | `RealAgentLoop.kt:1109`、`:462` |

**结论**：`AgentRuntime` 的价值是「资源许可 + 代次号 + 取消权」，不是「串行化一切」。

### 判断二：同意契约缺的是**票据类型**，不是通道

`Consent.Ask` 的签名是 `suspend (tool, args) -> Boolean`（`Consent.kt:69`）。`Decision` 虽然
定义了四种结果（`Allowed/Denied/Unavailable/Failed`），但**在通道边界就被压回布尔**：

- 桌宠把 `TIMEOUT` 与 `CANCELLED` 都渲染成「用户拒绝」（`PetApproval.kt:81-92`）——
  用户明明没看见卡，工具结果却写「用户拒绝了该操作」；
- 「记住这次授权」发生在契约**之外**（`ChatViewModel.kt:1751,1788` + `ApprovalScope.kt:211`），
  于是 MCP 与桌宠要么各写一份，要么干脆没有；
- 守卫收的是裸 lambda（`EgressGuard.kt:45`），桌宠只能硬编码 `{ false }`（`PetAgentSession.kt:180`），
  MCP 仍是可空 `McpApprover` 且用 `runBlocking` 等、无超时（`McpServerHost.kt:76,397`）。

**结论**：不是「加一个 Channel 字段」的问题，是「把裁决、作用域、有效期收敛成一个可存储、可撤销的值」的问题。

### 判断三：工具面缺的是**排序权归属**

现在有**五份手写工具清单**，彼此的先后顺序互不知情：

| 清单 | 数量 | 位置 | 是否经过统一排序 |
|---|---|---|---|
| `ToolCatalog` | 57 | `ToolCatalog.kt:104` | 基准 |
| 主界面注册序 | 54 次调用 → 57 | `ChatViewModel.kt:906` | 经 `CapabilityManifest.sort` |
| 桌宠 | 5 | `PetAgentSession.kt:144-150` | 自排 |
| 子代理白名单 | 15 | `SubAgentLogic.kt:59` | 自排 |
| MCP `NEVER_EXPOSED` | 6 | `McpTier.kt` | 自排 |
| MCP `McpToolset` | 7 | `McpToolset.kt:58` | **第二份手写顺序** |

而 `tools/list` 用的是插入序（`McpServerHost.kt:349`），**绕过了** `CapabilityManifest.sort`。
工具表顺序影响 KV 前缀（`ToolCatalog.kt:68-70` 已写明），所以「谁有权决定顺序」必须唯一。

### 判断四：验证体系的判别力已经接近零——**这是 v4 的第一优先级**

交付线在仓库副本上做了一次变异实测（删实现 / 反转判定），结果：

| 脚本 | 类型 | 变异 | 结果 |
|---|---|---|---|
| `run-arch-guard` | 静态棘轮 | 删 `BoundedBody.kt` | **仍全绿**（7/0） |
| `run-approval-tier` | 静态 22 + 行为门控 | `shouldSkipDialog` 对 shell/app_manage/git_write 直接 `return true` | **22/22 仍绿**（行为段 SKIP） |
| `run-wiring` | 纯文本 | `CrashLogger.hasUnseen = false` | **42/42 仍绿** |
| `run-mcp-host` | 静态 9 + 行为 | `?: false` → `?: true`（审批缺失＝放行） | **A9 仍 PASS** |
| `run-shell-read-boundary` | 纯行为 | `sensitiveReadRoot` 首行 `return null`（相册全放开） | **SKIP（rc=3）** |

**5/5 在默认开发机上是「绿或 SKIP」。** 也就是说：今天把「审批缺失就放行」这种最致命的改动提交上去，
CI 大概率仍然绿。这不是个别脚本的问题，是三个机制叠出来的：

1. **`[B]` 段缺 kotlinc 就 `exit 3`**，把**已经跑完的静态段**一起作废（83/150 脚本可走到 `exit 3`）；
2. **断言匹配源码文本**：531 处 `grep -q`，1729 条文本断言分布在 67 个文件；删空文件后
   `if ! grep` 恒真（40 处 `hasnt` + 7 处 `if ! grep`）；
3. **门禁 5 在 `SKIP>0` 时不比基线**（`gate.sh:146`），只剩门禁 6 的登记册，而登记册已满额。

**结论**：在这个状态下做 P1 重构是危险的——重构会大量改文本，断言会大面积变红，
每一次「红→绿」都可能是「把断言改到能通过」而不是「行为恢复」。**先修判别力，再动结构。**

### 判断五：数据层的问题不是「UI 模型耦合」，是**完整性**

v3 说「存事件不存 UI 模型」。但 `ConversationShard` **已经只存 `turns`**，`messages` 是
`ConversationBranch.flatten` 现算的（`ConversationShard.kt:31,41`）——**80% 的收益已经在手**。

真正的问题在写入侧，而且比我在上一轮审查里判断的更严重：

```kotlin
// ConversationStore.kt:62
private const val MAX_FIELD_CHARS = 4000
```

- 它对 user / assistant / tool / reasoning **一律** `take(4000)`（`:181/:188/:193/:203/:206`），**无标记**；
- `buildPriorMessages()` 直接从 store 读历史（`ChatViewModel.kt:2673`）——
  所以**同一会话的下一轮上下文就已经是截断版**，不只是「重启后」；
- 归档路径同样截断（`:758`），导出 `.md` 同样截断。

后果：模型自己上一轮写的一份长方案，下一轮它只记得前 4000 字，然后基于断掉的半句继续推理。
这是**上下文静默损坏**，不是显示问题。

### 3.2 运行时：一个所有者 + 两级并发

```kotlin
package com.beichen.polaris.runtime

enum class Source { Main, Pet, SubAgent, AutoResume, Mcp }

data class Quota(val maxSteps: Int, val maxTokens: Int, val deadlineMs: Long)

data class TaskSpec(
    val session: String,
    val source: Source,
    val input: String,
    val tools: ToolView,          // 只能做减法，见 §3.4
    val consent: Consent,         // 无默认值：必须表态
    val quota: Quota,             // 无默认值：不允许「不限量」
)

interface TurnHandle {
    val generation: Long
    val events: Flow<TurnEvent>
    fun cancel(reason: String)
}

interface AgentRuntime {
    /** 入队即返回。同 (session, source) 去重：后来的同键任务合并为「替换」而不是排队。 */
    fun submit(spec: TaskSpec): TurnHandle

    /** 唯一的资源闸：同一 backend 的并发回合数由此控制。子代理不再自建并发，改为借。 */
    suspend fun <T> withPermit(backend: String, block: suspend () -> T): T

    companion object { fun of(): AgentRuntime }
}
```

**两级并发，不是一级**：

| 层 | 管什么 | 粒度 | 默认值 | 依据 |
|---|---|---|---|---|
| 队列层 | 同一会话/入口的先后 | `(session, source)` FIFO | — | 「同一个人不会同时说两句话」 |
| 许可层 | 同一后端的资源争用 | `backend`（`local` / `cloud` / `terminal`） | `local=1`、`cloud=2`、`terminal=1` | 本地推理交错 prefill 会互相拖死；云端限流由 429 退避兜底 |

- **子代理**：保留 3 路并行（`SubAgentLogic.kt:33`），但每一路必须 `withPermit("cloud")`，
  且各自 `Quota` 从父级扣减（`maxSteps` / token 双向记账）。
- **代次号**：`cancel()` 先自增 `generation` 再 `Job.cancel`，迟到的事件按代次丢弃——
  这比 `isRunning` 布尔可靠，因为布尔无法表达「第 2 回合已开始、第 1 回合的迟到事件还在流里」。
- **桌宠的「停」**：`TurnHandle.cancel("user")`，不再是拆窗（`PetOverlay.kt:336`）。
- **冷启动续跑**：`AutoResume` 降级为「往队列里提交一个 `source=AutoResume` 的 Task」，
  与 `recoverInterruptedJournal` 合并成一条路径（今天两条互不知情，见 `RealAgentLoop.kt:1109/:462`）。

**四条硬不变量**（都能 grep 验证）：

1. `RealAgentLoop(` 在生产代码中**只出现 1 次**，且位于 `runtime/` 内（现 3 次）。
2. `ui` / `pet` / `entry` 不得 `import ...agent.RealAgentLoop` 或 `ToolRegistry`（现 2 处）。
3. 任何 `TaskSpec(` 字面量必须含 `quota = ` 与 `consent = `（类型强制，无默认值）。
4. 进程内只有一个 `Semaphore` 实例；`SubAgentRunner` 不许自带并发限制器。

### 3.3 同意契约 v2：从「问一句」到「票据」

```kotlin
package com.beichen.polaris.core

enum class Channel { Dialog, Bubble, Notification, Headless }
enum class Risk { ReadOnly, Write, Egress, Privileged }
enum class Scope { Once, Session, Timed, Persistent }

data class ConsentRequest(
    val tool: String,
    val argsDigest: String,      // 判定用的规范化摘要，不是前 500 字
    val display: ConsentDisplay, // 摘要 + 全文引用，截断必须标注
    val scope: Scope,
    val channel: Channel,
    val risk: Risk,
)

/** 一次授权就是一个值：可存储、可撤销、可过期、可审计。 */
data class ConsentTicket(
    val granted: Boolean,
    val scope: Scope,
    val issuedAt: Long,
    val expiresAt: Long?,        // Once → null；Timed → now+N；Persistent → null + 可撤销
    val channel: Channel,
    val key: String,             // 作用域键，如 "shell_read:/sdcard/DCIM"
)

interface ConsentBroker {
    suspend fun request(req: ConsentRequest): ConsentTicket
    fun allows(req: ConsentRequest): Boolean   // 纯查询，不弹窗
    fun revokeAll()
}
```

四条规则：

1. **`Ask` 的返回值从 `Boolean` 改成 `ConsentTicket`**。`Denied` / `Timeout` / `Cancelled` / `Failed`
   四种结果必须在类型上可分——今天桌宠把「超时」渲染成「用户拒绝」（`PetApproval.kt:81-92`），
   这是在教用户一件假事。
2. **票据存储归 broker，不归 App 层**。今天白名单在 `ApprovalWhitelistStore.kt:26` 的内存里，
   MCP 和桌宠拿不到，于是要么重写要么没有。
3. **`Channel.Headless` 必须有显式策略**，不能靠 `Deny("没有审批按钮")` 兜底：
   - 后台续跑：只读白名单 + 禁外发 + 禁提权，越界即 `Unavailable`（不是 `Denied`）；
   - MCP 外部客户端：按 `McpTier` 映射，`DANGEROUS` 档必须回到手机侧出卡（M2 要做的就是这个）；
   - 桌宠：气泡卡 + 45s 超时（已实现），但**超时要显示成「没来得及确认」**，不是「你拒绝了」。
4. **判定与展示同源**。主路径已修（`ApprovalPreview` + `ChatViewModel.kt:1768`），
   但桌宠**重新引入了同一个缺陷**：`PetApproval.summarize` 只取一个字段并 `take(120)`，
   无省略标记（`PetApproval.kt:130-137`）。这是缺陷复发，不是文档漂移。

### 3.4 工具组装：Source 产出，View 选择，Assembler 排序

单一接口做不到——「谁能造出工具」和「谁看得见工具」是两个正交维度。

```kotlin
interface ToolSource {                      // 拥有实现
    val id: String
    fun names(): Set<String>                // 无序；排序权不下放
    fun create(name: String, deps: ToolDeps): AgentTool?
}

fun interface ToolView {                    // 只做减法
    fun select(all: List<AgentTool>): List<AgentTool>
}

object ToolAssembler {
    fun compose(sources: List<ToolSource>, deps: ToolDeps, view: ToolView): List<AgentTool> =
        CapabilityManifest.sort(            // ← 顺序的唯一真源
            sources.flatMap { s -> s.names().mapNotNull { s.create(it, deps) } }
        ).let(view::select)
}
```

五个消费者 = **1 份 Source 集 + 5 个 View**：

| 消费者 | View | 规模 |
|---|---|---|
| 主界面 | `All` | 57 |
| 桌宠 | `PetView`（只读 + `app_launch` 确认） | 5 |
| 子代理 | `SubsetView(父级 ∩ NO_SIDE_EFFECT)` | 15 |
| MCP 只读档 | `TierView(STANDARD, M1)` | 7 |
| MCP 写档（M2） | `TierView(STANDARD, M2)` | 待定 |

配套三条：

- **`McpTier.NEVER_EXPOSED` 下沉为 `CatalogTool.externalExposure` 字段**，否则第 7 个隐藏工具

### 3.5 数据：先修完整性，暂不动模型

**不做** `UiItem → TurnEvent`（理由见 §7）。只做三件小事：

1. **截断必须可见**。`toMsgRecord` 里 `take(n)` 后若 `length == n`，追加
   `\n…（已截断，原文 ${originalLen} 字，仅落盘前 ${n} 字）`。
   这一步不改格式、不改读路径，1 小时，立刻消掉「看起来话说一半」。
2. **正文与工具结果分级**。目标格式：

   ```
   conversations.d/<id>.json        # turns：user/assistant 正文 ≤ 32K，工具结果 ≤ 2K
   conversations.d/<id>.body.jsonl  # 超长正文/工具结果，一行一条，append-only
   ```

   `MsgRecord` 增加 `bodyRef` / `bodyLen` / `truncated` 三个带默认值的字段（前向兼容，
   `ConversationShard` 的手写解析已经支持缺字段兜底）。单次 flush 字节量降 5–20 倍，
   同时把「一次回答 20 次 fsync」压到 1–3 次。
3. **写者唯一**。今天主界面与桌宠各存一份（`pet/history.json` vs `conversations.d/`），
   **不要合并文件**（生命周期不同），只合并**读视图**：`conversation_search` 同时查两处。

### 3.6 验证：四层，但顺序反了

v3 的顺序是 L1 静态 → L2 行为 → L3 真机。**v4 在最前面加一层 L0，并且它是 P0。**

| 层 | 守什么 | 规模 | 耗时 | 何时跑 |
|---|---|---|---|---|
| **L0 变异** | **断言本身有效**：删实现必须变红 | 20 条关键守卫 | 5–8 min | CI 必跑 |
| L1 静态契约 | 分层、装配不变量、禁止模式 | ~30 条 | <30s | pre-commit |
| L2 JVM 行为 | 决策表、并发、账本、投影 | ~90 条（JUnit） | <60s | 本地 + CI |
| L3 真机矩阵 | 悬浮窗 / 键盘 / 磁贴 / 权限撤销 / 省电 | ~40 条 | 夜间 | 发版前 |

**L0 的判据**：CI 里对每条关键守卫做一次「注释掉实现 → 必须红」。
任何一条没红，构建失败。这条做完，531 处文本断言的价值才开始成立。

**L1 的两条新检查**：
- `code_grep`（先剥 `//`、`*`、`#` 行首注释再匹配）成为唯一允许的文本断言入口；
- `arch-baseline.txt` 每一行豁免必须带「日期 + 理由 + 谁批的」，且 CI 比对历史只增不减。

**L2 的迁移清单**（三个纯函数，无 Android 依赖，当前只被 grep 覆盖）：

| 模块 | 迁移成本 | 能拦住什么 |
|---|---|---|
| `ApprovalTier.shouldSkipDialog / normalize` | 2h | AUTO 档放行 shell / app_manage / git_write |
| `ApprovalDeadline.awaitApprovalDecision` | 1.5h | 超时永久挂起、取消被吞成拒绝 |
| `ToolBudget.resolve` | 1h | 1s 下限与回合上限夹紧失效 |

`app/build.gradle.kts` 已声明 `testImplementation("junit:junit:4.13.2")`，`core/src/test` 是空的——
基础设施现成，缺的只是把这三块搬进去。

## 8. 需要拍板的五件事

1. **并发默认值**：云端 `maxInflight` 取 2 还是 3？取 3 与子代理并行对齐、体验最好，但同一账号的
   429 概率上升；取 1 则必须同时砍掉子代理并行（产品倒退）。
2. **`Scope.Persistent` 要不要开**：桌面端可以「永久允许读 /sdcard/DCIM」，手机端一旦开了，
   用户就再也不会看到弹窗。建议**只开 `Session` 与 `Timed(5m)`**。
3. **分级落盘何时做**：P0 只加截断标记（0.5 人日），`body.jsonl` 推迟到「单会话 > 5 MB」触发。
   是否接受这个延迟？
4. **MCP 写档（M2）与 `Consent v2` 的先后**：建议**先 v2 再 M2**——M2 是契约的第一个外部消费者，
   形状错了改起来是双倍成本；但 M2 也是检验形状的最好机会。二选一。
5. **真机矩阵的机型**：现有结论全部来自模拟器。国产 ROM 的「后台弹出界面」二次权限会让审批卡
   根本不出现（表现为写工具静默变拒绝），这一条**只有真机测得出**。
