# 声音克隆（A：导入自己的声音）实现报告

日期：2026-11-15
前置：`docs/archive/reports/音色选择-实现报告-2026-11-15.md`（C 已完成：内置 22kHz + 在线占位）

## 一句话

用户录一句 12 秒以内的话，应用把它存成一条可选音色；之后桌宠和朗读都用**他自己的声音**说话。全程离线，参考音频不出设备。

## 为什么不是「上传到云端克隆再下载回来」

| 方案 | 能不能用 | 为什么不用 |
|---|---|---|
| ElevenLabs / 豆包 / MiniMax 云端克隆 | 能，效果最好 | 要把用户的声音上传到别人服务器；要 key、要钱、要联网。用户明确要「自己的声音」，不该顺带把生物特征交出去 |
| OpenAI TTS | **不能** | 只有 13 个内置音色，**不支持上传音频克隆**。`gpt-4o-mini-tts` 的 `instructions` 只能控语气 |
| 本地 ZipVoice | 能，离线 | 体积大（155MB）、比内置音色慢。换来的是「不上传、不联网、不花钱」 |

选第三条。理由不是「开源更好」，是**声音是生物识别级别的数据**，一旦上传就收不回来。

## 技术选型与两个必须同版本的东西

ZipVoice（`sherpa-onnx-zipvoice-distill-int8-zh-en-emilia`）是「零样本」克隆：
不训练、不微调，合成时把参考音频当作说话人条件喂进去。

要让它跑起来，**Kotlin API 与原生 `.so` 必须同为 v1.13.x**：

- v1.12.4 的 `Tts.kt` 里没有 `OfflineTtsZipVoiceModelConfig`，也没有
  `GenerationConfig.referenceAudio`——零样本克隆的那两个参数根本不存在；
- 这些 data class 是 JNI 反序列化契约，原生层按字段顺序取值。跨版本混用，
  报错只有一句 `Invalid OfflineTtsConfig`，看不出缺的是哪个字段。

所以本轮把运行时从 v1.12.4 升到 **v1.13.8**，`Tts.kt` 整份照搬（含未用到的模型族）。
「只留用到的几个 data class」省不了多少行，却会让下一次升级变成逐字段比对。

## 落地的东西

### core（可被 harness 独立验证）

| 文件 | 作用 |
|---|---|
| `voice/VoiceCatalog.kt` | `VoiceKind` 加 `CLONE`——与 `LOCAL` 都是本地合成，但失败面不同 |
| `voice/VoiceAvailability.kt` | 回落链的输入事实：有网 / 内置模型 / 克隆模型 / 参考音频，四个独立布尔 |
| `voice/VoicePlan.kt` | 克隆链：克隆 → 本地 → 系统；新增 `VoiceSkip.REFERENCE_MISSING` |

**为什么 `VoiceAvailability` 是一个结构体而不是几个布尔参数**：三个布尔并排传，
调用方几乎必然写错顺序，而错了**不会编译失败**——都是 `false` 时链看起来「正常地」
一路退到系统引擎，日志写「模型未就绪」，实际原因却是没网。把名字写进字段，这类错误不再可能。

**为什么 `REFERENCE_MISSING` 要单列**：克隆要「模型在」+「参考音频在」两样。
缺任何一个都发不出声，但用户该做的事完全不同——前者是重装/查存储，后者是重新录一句。
合成一个「不可用」，界面就只能说「用不了」，用户会反复点。

### app（音频与界面）

| 文件 | 作用 |
|---|---|
| `audio/tts/ZipVoiceEngine.kt` | 克隆合成；`generateWithConfig(text, referenceAudio, referenceText, numSteps=4)` |
| `audio/tts/CloneVoiceStore.kt` | 克隆音色的增删查；`filesDir/tts/clone/<id>/{ref.wav,ref.txt,label.txt}` |
| `audio/tts/VoiceRecorder.kt` | AudioRecord 24kHz 采集，12 秒硬上限，实时电平 |
| `audio/tts/VoiceSampleIo.kt` | WAV 读写、首尾静音裁剪、线性重采样兜底 |
| `audio/tts/TtsAssetInstaller.kt` | 两套模型共用的 assets 展开（逐文件比长度、可续传） |
| `ui/VoiceCloneScreen.kt` | 录音页：固定参考文本 + 电平条 + 倒计时 + 保存后自动试听 |

**为什么参考文本写死在屏幕上**：ZipVoice 的参考文本必须与音频**逐字对应**。
用户不知道这条规则就会自由发挥或读一半改口，结果是「像但发闷」，而他完全不知道为什么。

**为什么录音有 12 秒硬上限**：`开始/停止` 看着自由，实际最常发生的是一次录三分钟、
后半段全是空气声。参考音频混进长静音，模型会把这口气学进去，合成时每句都拖尾。

**为什么要裁首尾静音**：同上。阈值取相对峰值的 −35dB（跟环境噪声走），两侧留 120ms 余量，
避免削掉字头字尾的辅音。

**为什么录音前要先停播报**：`speaker.stopForRecording()`。开麦时如果自己还在说话，
录进去的就是上一句机器音——而且听不出来，只会觉得「克隆出来有杂音」。
这个「停」放在 `TextSpeaker` 而不是界面里，因为它持有播报态与租约。

**为什么参考文本用 `AtomicJsonFile.write` 落盘**：内容和 JSON 无关，用它是为了**原子替换**。
直接 `writeText` 写到一半被杀，会留下一个空文本 + 完整的 ref.wav，
下次读到的就是「音频在、文本空」——克隆直接失效，且看不出为什么。

| Python 侧跑通合成 | **通过**：两个不同参考音频（男/女）各两句，全部成功；采样率 24000；峰值 24486/27206（不是静音） |
| **真机出声** | **未验**——本镜像无音频设备，见 P17 |

### 本轮被架构守卫挡下的两处（都是真问题）

1. `readWav` 用了 `file.readBytes()`——参考音频该多大是已知的（12 秒 24kHz ≈ 576KB），
   一个被替换的坏文件能把这行 OOM 掉，而它跑在合成路径上。改走 `BoundedBody.readBytes(4MB)`。
2. `CloneVoiceStore` 直接 `writeText`——见上「为什么用 AtomicJsonFile」。

### 实测数据（服务器 4 核 CPU，int8 模型）

| 参考音频 | 文本 | 音频时长 | 合成耗时 | RTF |
|---|---|---|---|---|
| 6.06s 男声 | 16 字 | 3.12s | 1.57s | 0.50 |
| 6.06s 男声 | 23 字 | 6.19s | 1.94s | 0.31 |
| 6.84s 女声 | 16 字 | 3.66s | 1.69s | 0.46 |
| 6.84s 女声 | 23 字 | 6.39s | 2.70s | 0.42 |

引擎初始化 0.93–1.15 秒（之后常驻）。作为对照，内置 matcha 在同机的 RTF 约 0.05——
**克隆慢约 8 倍**。手机上两者都再慢 2–3 倍，所以「说 6 秒的话，等 4–6 秒」是准确的预期。

试听样本已挂到试听站（`clone_demo_*.mp3`），用官方示例的两个真人录音做参考。

## 代价，说实话

| 项 | 数值 | 说明 |
|---|---|---|
| ZipVoice 模型 | 104 MB（int8） | 随包 |
| 24kHz 声码器 | 51 MB | 随包 |
| APK 总量 | **约 360 MB**（仅 arm64） | 内置 matcha 139MB + 克隆 196MB + 运行时 31MB + 其余 |
| 首次合成 | 初始化 2–4 秒 | 之后常驻 |
| 单句合成 | 比内置音色慢约 8 倍（RTF 0.3–0.5 vs 0.05） | 每次都要重读参考音频——这就是「零样本」的代价 |
| 安装后占用 | 再 +335MB（模型展开到 filesDir） | assets 里一份、filesDir 里一份 |

**瘦身的唯一办法**：砍掉内置 matcha（125MB），默认音色改成「一段随包的参考音频 + ZipVoice」。
代价是默认音色也变慢、且需要一段合法授权的参考音频。本轮没做，留作可选。

## 边界与合规

- 只提示用户克隆**自己**的声音。《民法典》第 1023 条对声音权有明确规定（参照肖像权保护）。
- 参考音频存应用私有目录，卸载即删，不上传、不给第三方。
- 不上传这一条不是「暂时没做」，是**设计约束**：写进代码注释，也被断言 A10 盯着。
