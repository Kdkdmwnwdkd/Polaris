## 做了什么

进程被系统杀掉之后，下次打开 App，**助手自己把上次没做完的事接着做完**，
不用用户记得「我还有个任务」，也不用他打字说「继续」。

## 为什么不是新写一套

动手前先查了已有能力，结论是**能力全齐，只差最后一步没人推**：

| 已有 | 位置 | 作用 |
|---|---|---|
| 前台服务保活 | `AgentRunService` | 防「系统回收」，防不了「进程真被杀」 |
| 运行态落盘 | `AgentRunStateStore` | 记住做到第几步、做过哪些工具 |
| 冷启动对账 | `reconcile()` | `running` → `interrupted` |
| 续跑上下文 | `buildResumeContext()` | 用户说「继续」时拼进度摘要 |
| 孤儿调用提示 | `TurnJournal` | 提示「某个写操作可能已生效，别重做」 |

所以本轮**没有改动任何一条既有判据**，只加了两样东西：一张新的判定表，
和一个「代用户说『继续』」的触发器。

## 关键实现

| 位置 | 做了什么 | 为什么不能省 |
|---|---|---|
| `core/agent/AutoResumePolicy.kt`（新，214 行） | 判定表：11 种理由 → 三态（跑 / 只提示 / 静默） | 每次判定都对应一次真实请求；纯函数才能被 harness 逐条断言 |
| `ChatViewModel.autoResumeIfPossible` | 取状态 → 裁决 → 代发「继续」 | 复用 `send()`，续跑上下文/历史/前台服务/落盘/打断仲裁一处都不用重写 |
| `runStateReady`（`CompletableDeferred`） | 把对账结论从第 991 行的 init 搬到类体末尾那个 init | 前者跑在 IO 线程，会读到尚未初始化的 `_activeConversationId`——2026-11-09 模拟器 NPE 就是这么来的 |
| `AgentRunState.autoResumeAttempts`（新字段） | 熔断计数随状态落盘 | `send()` 里的 `save` 会整体覆盖状态，不带它则每轮把计数清零，「一跑就被杀」的任务会被无限重试 |
| 设置 → 通用 → 自动续跑 | 默认开，可关 | 它每次触发都是一次真实请求，必须让用户能关 |

## 两个必须记住的性质

1. **它是重放，不是恢复执行栈。** 进程死了，协程的函数帧、局部变量、等待中的 IO 全没了；
   能恢复的只有已落盘的对话历史。所以它**可能重复已完成的副作用**——
   靠既有 R1 孤儿调用提示兜底（那段提示照样注入这一轮，因为走同一个 `send()`）。
2. **只在当前会话自动跑**，不自动切会话；无模型 / 会话已删 / 中断超 24 小时都不跑，
   只给一句说明为什么（不是沉默——沉默会让人以为功能坏了）。
3. **用户正在输入框里打字时也不跑**（`INPUT_BUSY`）。自动续跑要往输入框写「继续」，
   而聊天页输入框是自动聚焦的——那会把敲了一半的字整个清掉。这是数据丢失，
   比不自动续跑严重得多。这个洞是复核 diff 时才发现的，第一版没有它。

## 遗留

真机三条（P14），验的是**触发时机**——模拟器上很难稳定制造「进程被杀」，
而这正是本功能的触发条件。判定逻辑本身已被 41 条断言钉死。
