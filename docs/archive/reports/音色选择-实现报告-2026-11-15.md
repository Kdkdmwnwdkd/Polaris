# 音色选择（C 阶段）实现报告 —— 2026-11-15

> 目标：让桌宠与朗读「听起来像个人」，并且这个声音是用户自己选的。
> 结论先说：**本地 22kHz 这一档做完了，在线那一档没做——不是没时间，是不该做。**

---

## 1. 为什么先做本地那一档

用户在两轮试听后选了「图1（22kHz 本地）+ 图2（在线神经音色）」。落地时两者的处境完全不同：

| | 本地 22kHz | 在线 6 音色 |
|---|---|---|
| 依赖 | 一个 72MB 模型，随包 | 一个服务端接口 |
| 断网 | 照常说 | 直接没有 |
| 失败方式 | 立即可见（模型没装） | **静默**（转两秒，没声音） |
| 当前能否合法接通 | 能 | 需要服务端 key |

所以顺序是：先把本地这一档做扎实，在线留好插槽。

---

## 2. 在线音色为什么没接：一次实测

试听站里那 6 个音色（晓晓/晓伊/云希/云健/云扬/晓北）来自微软 Edge 的网页版朗读接口，
零注册、免费。2026-11-15 在本机实测：

```
旧令牌 + 旧版本号   → 403
标准 SHA-256 令牌   → 403
当前 edge-tts 令牌  → 200（能合成）
```

也就是说，这个接口已经上了防滥用校验：令牌不再是「时间片 + 客户端令牌」的普通 SHA-256，
而是一套**刻意混淆的混合哈希**（上游 `edge_tts/drm.py` 里重写了 SHA-256 的常量表）。
它能用，但：

1. 服务端改一次常量，6 个音色**同时**失效；
2. 失效的表现和「网络不好」完全一样——用户只会说「又没声音了」；
3. 它不是给第三方客户端用的接口，把它做成产品的一部分，等于把「什么时候坏」交给别人。

**决定：不把逆向接口写进 APK。** 6 个音色在页面上如实列出并标注「需 key」，
而不是灰掉不说、也不是假装能用。

> 要接的话，正路是 Azure Speech（同一批音色、同一个人声，官方接口，免费额度够个人用）
> 或火山/讯飞的在线 TTS——都需要用户填一次 key。这一段留到用户决定后再做。

## 3. 落地了什么

### 3.1 目录与回落链（`core/voice`，零 Android 依赖）

- `VoiceCatalog`：8 条音色（6 在线 + 1 本地 + 1 系统），id 与供应商音色名分开存。
  供应商改名字不影响用户存的选择。
- `VoicePlan`：从用户选的音色开始逐级往下退。
  - 选在线 → 在线 → 本地 → 系统
  - 选本地 → 本地 → 系统（**不偷偷联网**：他选本地就是要离线）
  - 选系统 → 就用系统（不替他升级）
  - 不变量：链永不为空、链尾永远是系统、不重复、跳过原因只由入参事实决定。

### 3.2 合成与播放（`app/audio/tts`）

- `LocalVoiceEngine`：sherpa-onnx + `matcha-icefall-zh-baker` + `vocos-22khz-univ`。
  模型放 assets，首次使用时展开到 `filesDir`（逐文件比长度，中途被杀能续）。
- `PcmPlayer`：AudioTrack `MODE_STATIC` 整段播放，用 `setNotificationMarkerPosition`
  等「真的放完了」——尾音被吞的代价是仲裁器以为还在说话。
- `VoiceSpeech`：路由 + 回落 + 原因留痕（`lastDemotion`）。
- `TextSpeaker`：**所有播报的唯一出口**。合成失败退系统引擎，试听也走这一条路
  （否则用户试听时点麦克风会录进机器音）。

### 3.3 界面（`VoiceStyleScreen`）

- 三组：本地 / 在线（标明未启用）/ 系统。
- 每条可**试听**——音色是听出来的，不是看名字看出来的。
- 试听不改用户的选择（走 `prepareFor`，不做「临时改存储再改回来」）。
- 「上次实际用的不是首选」一栏：回落必须能被看见，否则用户只会觉得设置没生效。

## 4. 验证到什么程度

| 项 | 结果 |
|---|---|
| 音色目录与回落链行为断言 | **40 条全过**（17 目录 + 15 回落 + 8 结构）`scripts/qa/run-voice-style-verification.sh` |
| 架构守卫 | 7 通过 / 0 失败（`AppScaffold` 1548 → 1552，理由写进基线） |
| `:app:compileDebugKotlin` | 通过 |
| 逆向接口静态扫描 | 全仓无 `speech.platform.bing.com` / `Sec-MS-GEC` |
| **真机出声** | **未验**。本镜像无音频设备，`AudioTrack` 只能靠真机 |

真机要验的四件事（见 `docs/ops/DEVICE-VERIFICATION-PENDING.md` P16）：

1. 首次朗读时模型展开（约 72MB，预期 2–5 秒）后出声，采样率应为 22050；
2. 音色页每条试听都有声，切「系统语音」后声音明显变化（8kHz 那台机器应能听出差别）；
3. 播报中点麦克风：立刻静音，且录音里没有机器音；
4. 拔网线/飞行模式：本地音色照常，无提示、不卡顿。

## 5. 已知边界（不藏着）

1. **单说话人**：matcha-icefall-zh-baker 只有一个女声，`sid` 恒为 0。
   想要多个本地音色，得再放一个模型（每个 +70MB），不是参数能解决的。
2. **不流水线**：整段合成再播。第一声的延迟 ≈ 合成耗时（实测约 0.3–0.6 秒/句）。
   长回答会被切成一句一句合成，但还没做「边合成边播」。
3. **内存**：模型常驻约 150–200MB（onnx 权重 + 运行时）。低端机（<3GB）可能被系统回收，
   表现是「说两句后没声音，重进恢复」——真机上要专门看一眼。
4. **展开占用**：assets 一份 + filesDir 一份，共约 145MB 存储。
   后续可改成「assets 里存 tar.bz2，首次解压后删包」省一半。

## 6. 下一步（A 阶段）

用户要的 A 是「导入自己的声音」。技术路线已经定了：ZipVoice（本地零样本克隆，
104MB + 51MB 声码器，参考音频 5–10 秒 + 准确文本）。它跑在**同一套 sherpa-onnx 运行时**上——
这一轮把运行时、播放、回落都铺好了，A 只需要换一个 `OfflineTts` 配置与多一步「录音采样」。

真正的未知不是代码，是**像不像**：这件事只能用户在自己手机上听完再判断。
