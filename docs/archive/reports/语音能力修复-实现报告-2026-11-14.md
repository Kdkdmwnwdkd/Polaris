> 用户反馈：**「桌宠那个还没好啊，我语音的话，不管是桌宠也好，还是我本身语音输入，它都没有搞好」**

> 真机清单 [`docs/ops/DEVICE-VERIFICATION-PENDING.md`](../../ops/DEVICE-VERIFICATION-PENDING.md) 的 P15 段

## 一句话

桌宠和聊天页的语音**同时不能用**，不是两个 bug，是**五个缺陷叠在一起**，
而它们在用户眼里长得一模一样——都是「按了没反应」。

第一轮（白天）把这些定位出来、修掉，并给「为什么不能用」装上了诊断与回归手段。

**第二轮（当晚，真机日志到手）推翻了其中最关键的那个猜测**：
不是没装识别服务，而是**装了两个、默认那个不认中文**。
第一轮的修法让「为什么不能用」变得可读，第二轮的修法让**它真的能用**。
两轮都在下面，按时间顺序。

## 为什么之前查不出来

前四轮验的是「App 侧链路」，用的是**桩识别服务**：桩能证明代码接线对，
**证明不了真机上能不能识别**。而真机上失败的原因分属五个不同的层，
每一层的现象都一样。

真正难的地方在于：**这五个原因里，有四个在代码里长得一模一样**
（都是 `if (!available) { toast("识别失败") }`），只有对着 AOSP 源码逐条查，
才能把它们分开。

## 查证：对着 AOSP 源码，不靠印象

| 曾经的疑问 | 查证结果 | 出处 |
|---|---|---|
| `isRecognitionAvailable` 是不是要求识别服务声明 `CATEGORY_DEFAULT`？ | **不是**。它走 `queryIntentServices(SERVICE_INTERFACE, 0)`，flags 是 0，不带 `MATCH_DEFAULT_ONLY` | `android/speech/SpeechRecognizer.java:392` |
| 那缺 `<queries>` 会不会导致查不到服务？ | 本 App `targetSdk = 28`（不是 30+），**不受 package visibility 限制**，当前无影响。但清单已补上声明，为将来升 targetSdk 预留 | `app/build.gradle.kts:125` |
| 引擎到底是怎么被选中的？ | 读 `Settings.Secure.VOICE_RECOGNITION_SERVICE`。**它为空时绑定直接失败**，应用侧只看到笼统的 `ERROR_CLIENT` | `SpeechRecognizer.java:970` |
| 识别服务会检查调用方的麦克风权限吗？ | **会**。没有就回 `ERROR_INSUFFICIENT_PERMISSIONS` | `RecognitionService.java:155` |
| `checkRecognitionSupport` 能提前问语言支持吗？ | 是**实例方法 + 异步回调**（要 Intent + Executor + Callback），且要先连上引擎——做不成同步探测 | `SpeechRecognizer.java:625` |

> 两条流传很广的结论被证伪：`CATEGORY_DEFAULT` 那条是 TTS 的坑；
> `<queries>` 那条在 `targetSdk=28` 下当前不成立（但为将来补了声明）。

## 找到的五个真缺陷（第六条是当天补的，第一条当天被推翻）

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | ~~聊天页语音输入没有任何麦克风权限申请入口~~ **← 误诊，已撤销** | —— | 见下节「一次自我纠错」 |
| 2 | 两条入口各自判断「能不能识别」，各自写文案 | 桌宠说「没有语音识别服务」、聊天页可能说「有服务」，用户以为其中一边坏了 | 收敛到 `core/voice/SpeechCapabilityPolicy`，两条路共用同一套结论 |

| 5 | 桌宠缺权限时只提示「去系统设置」，但桌宠是悬浮窗、**没有 Activity，弹不了权限框** | 用户得自己去设置里找这个 App、找权限项、点开 | 提示改成可点，一键跳本应用的系统权限页 |
| 6 | 聊天页**没查系统识别页存不存在**（旧代码等 `launch` 抛异常才回一句笼统的话） | 把「没有识别页」说成「没有识别服务」，用户去装错的东西 | 提前查 `ACTION_RECOGNIZE_SPEECH` 的处理方 |

## 一次自我纠错：把「谁来录音」写进类型

这一天里最要紧的一件事，是**推翻了我自己写下的第 1 条**。

推理链是：「聊天页没有麦克风权限申请入口 → 只用聊天页的用户永远拿不到权限 →
识别不出东西 → 所以要当场申请权限」。前三步都对，只有**第一步的前提是错的**：
聊天页走系统识别页，**录音发生在系统进程里**，我们的 `RECORD_AUDIO` 跟它无关。

依据（对着 AOSP android-34 源码逐条查）：

| # | 事实 | 出处 |
|---|---|---|
| 1 | `RecognitionService` 校验的是 `getAttributionContextForCaller().getAttributionSource()`——**调用 `SpeechRecognizer` 的那个 App** 的录音归属，不是「谁发了 Intent」 | `RecognitionService.java:826` |
| 2 | `SpeechRecognizer.startListening` 传的是 `mContext.getAttributionSource()`，而 `mContext` 是 `createSpeechRecognizer(context)` 的那个 context。走系统识别页时，创建识别器的是系统语音助手 | `SpeechRecognizer.java:759` |
| 3 | 框架自己的 `SearchView` 启动这个 Intent 时，`EXTRA_CALLING_PACKAGE` 填的是**系统搜索 Activity** 的组件名，不是嵌入它的第三方 App。第三方 App 用 SearchView 的语音搜索从不申请录音权限——最硬的旁证 | `SearchView.java:1684` |
| 4 | 项目自己在 W-30 就写过：「直接用各家 ROM 自带的识别服务（`RecognizerIntent`，**不需要任何权限声明**）」 | `scripts/qa/W30-NOTES.md:35` |

于是把「谁来录音」变成了判定输入的一部分：

```kotlin
enum class VoicePath {
    SelfRecorded,   // 桌宠：自己录音 → 我们的麦克风权限是硬前置
    SystemPage,     // 聊天页：系统页录音 → 我们的权限与它无关
}
```

**为什么必须写进类型而不是写成注释**：写成注释，下一个人（或三个月后的我）
会照着改回去。写成类型之后，「系统页路径 + 我们没权限 → **不拦**」这条被
harness 的 B10 钉死了，改不动。

> 这条纠错的代价是真实的：按误诊实现的话，聊天页会被自己的权限拦截挡住，
> 用户看到的还是「语音没反应」——**而且这次是我们自己挡的**。
> 拦住一条本来能用的路，比不拦更糟。

## 本轮最要紧的设计：把「出路」从散文变成类型

原先「这个失败该怎么办」只存在于文案里：「去系统设置给北辰打开麦克风后重试」。
要验证这句话可不可执行，只能查「文案里含不含『系统设置』」——
而这种断言**守不住行为**：把话术从 A 文件搬到 B 文件它照样绿，
把「系统设置」改成「设置页」它就红了，哪怕用户拿到的话还是一样有用。

> 这不是假设：断言体检（`scripts/qa/assertion-census.py`）第一次跑本轮的新 harness，
> 就判了 7 条文本断言超标——**正是我自己写的**。守卫生效了，于是照着它的规矩改。

于是把出路抽成枚举 `SpeechRemedy`（去授权 / 去选默认引擎 / 装服务 / 换语言 / 查网络 /
腾出麦克风 / 重试 / 带码上报）：

- **判定结果自带出路**：`SpeechCapability.Unavailable` 带 `remedy` 字段，
  文案与出路由同一张表（`specFor`）产出，**不可能分叉**。
- **harness 断言的是判定结果**，不是文案长相：
  「缺麦克风权限 → remedy 必须是 `GrantMicPermission`」。
- **UI 不再按魔法字符串分流**：桌宠「一键跳权限页」原来写的是 `code == "no_permission"`。
  字符串写错一个字母**不会编译报错**，只会静默地不再跳权限页——正是「按了没反应」
  这一类最难查的问题。现在按枚举分流，结构断言钉住这件事。

顺带修掉一个**行为不一致**：桌宠原先自己先判麦克风权限、缺权限就先报权限，
而判定表的顺序是「先说缺服务」。两条路因此可能给出不同结论。现在桌宠不再自己判，
一律走判定表。

## 两个必须记住的坑

1. **`::openAppPermissionSettings` 这种可调用引用，写在带花括号的 if 分支里会让 Kotlin 编译器崩**
   （Internal compiler error，`ReflectionReferencesGenerator` NPE，已复现）。
   必须写成单行 if 表达式。
2. **判定顺序的理由不能写反**。core 里那段注释原本在论证「先查权限」，
   而代码是「先查服务」——注释与代码矛盾，且**两边都自洽**，所以谁也发现不了。
   现在注释说的是真话：没有识别服务时，麦克风权限给不给都用不上，
   先要一个用不上的权限既白费隐私又不解决问题。

几条结构断言值得单独说：

- **A9（不许拿权限去拦）**：聊天页的代码里不许出现 `permission.RECORD_AUDIO` /
  `micGranted` / `micPermission` / `RequestPermission()`。这条把上面那次纠错钉死了——
  谁再想加回那个拦截，CI 会直接红。查的是**代码引用**而不是文字出现，
  因为注释里说明「我们不需要这个权限」是应该写的。
- **A13（常量脱钩）**：core 为了保持零 Android 依赖复制了一份 AOSP 错误码常量。
  复制会被 AOSP 改号悄悄打穿（症状是「网络超时」被翻译成「没听清」，且永远没人发现）。
  A13 拿 `android.jar` 的真实常量值逐个比对，改号即红。
  这条断言**做了反向变异验证**：把 `const val CLIENT = 5` 改成 `55`，立刻报
  「ERROR_CLIENT(AOSP=5,core=55)」；改回去恢复通过。
- **A15/A15b/A16（路径维度）**：两条入口都声明了路径，且路径维度住在 core 判定表里，
  而不是散在调用点。散在调用点的后果是：改一条路径的要求要改两个文件，
  而漏改的那个不会报错——只是那条路的行为悄悄变了。

修 `r14_coverage.py` 的 B3 误报时也做了**双向变异验证**：把 `vm.micGranted`
改成 `vm.micGrantedTypo` 仍能抓到；插入 `Manifest.permission.RECORD_AUDIO.isNotBlank()`
不再误报——确保没有把守卫改弱。

## 还剩什么（真机 10 分钟）

# 第二轮：真机日志到手之后（当晚）

## 起因

第一轮结尾写着「真机识别这一步我验不了」。用户当晚把 731 包（第一轮修复版）
的真机日志贴了过来。**日志推翻了我的核心猜测**。

## 三行关键事实

```
21:46:11.525 [SpeechProbe] 识别服务 2 个：com.google.android.tts/…GoogleTTSRecognitionService、
                                        com.qualcomm.qti.voiceai.speech/…SpeechRecognitionService
21:46:11.527 [SpeechProbe] 语音能力检查通过（路径=SystemPage，引擎已选=true，语言支持=null）
21:46:37.376 [PetVoice] 识别失败 code=12 → 语音识别服务不支持当前语言，换个系统语言试试
```

| 事实 | 推翻了什么 |
|---|---|
| 识别服务 **2 个** | 我猜的「国产 ROM 没 GMS、所以没识别服务」——错了 |
| 引擎已选 = **true** | 「系统没选默认引擎」也不是原因 |
| 语言支持 = **null** | 判定表缺这一维，于是**放行了** |
| code = **12** | `ERROR_LANGUAGE_NOT_SUPPORTED`：引擎自己说「我不认这个语言」 |

判定层没错，是**判定层拿不到那一维的信息**。

## 我第一轮的判断错在哪

第一轮我在 `isLanguageSupported()` 里写了「语言支持交给引擎错误码回报」，
还为此写了三条理由（异步 API 造不成同步探测、错误码是权威答案、不值得搭链路）。
三条理由都成立，**结论却是错的**——因为它们只回答了「能不能提前知道」，
没回答「知道了之后能不能做点什么」。

真实代价是：用户按下去、说一句话、被引擎拒绝，只拿到一句「不支持」。
而设备上**明明还装着另一个能识别中文的引擎**。
能在本地解决的事，被我推成了用户的问题。

**教训**：判断「这个信息值不值得拿」时，不能只看拿的成本，
还要看**拿到之后能不能改变结果**。这里能——所以第一轮的成本收益算错了。

## 根因

系统默认引擎是 `com.google.android.tts` 里的 `GoogleTTSRecognitionService`：
Google TTS 包自带的识别服务，**要单独下载中文离线包才会认中文**。
同一台机器上还装着 `com.qualcomm.qti.voiceai.speech`（高通语音），
很可能认中文——但 App 既没问过它，也没法把识别指向它。

## 修复

| 位置 | 做了什么 | 为什么必须 |
|---|---|---|
| `core/voice/RecognitionEngine.kt`（新） | `EngineCapability` / `EngineFit` / `EngineSelector` / `LanguageTag` | 挑错引擎**不报错**，只表现为「语音还是不能用」——必须能被 JVM 逐条断言 |
| `SpeechProbe.probeEngines()` | 对每个识别服务调 `checkRecognitionSupport`，问「当前语言你认不认」 | 这是唯一能提前问出语言支持的办法，且不占麦克风。每引擎 800ms 超时兜底 |
| `PetVoice.createRecognizer()` | `createSpeechRecognizer(ctx, componentName)` **指定引擎** | AOSP 官方为「指定服务」提供的入口。只记录选择不指定的话，日志会说谎 |
| `PetOverlay` / `ChatScreen` | 各自启动时探一次（结果进**进程级**缓存） | 长按时再探要多等几百毫秒；只用聊天页的用户也得有结论 |
| `SpeechRemedy.SwitchEngine`（新） | 「不支持当前语言」的出路从 `ChangeLanguage` 改成换引擎 | 换系统语言要把整台手机变成另一种语言，只为用一次语音——代价完全不对等 |
| `LanguageTag` | 按主语言比较，认 `cmn` / `zh_CN` / `zh-Hans-CN` | 引擎回报中文有四种写法。用 `==` 比会把 `cmn-Hans-CN` 判成不支持，然后让用户去换系统语言——**而它完全能识别** |
| `VoiceDiagnostics` | 报告里加「各引擎对 zh-CN 的支持」段，逐个标适配度并给出「当前应使用」 | 「识别服务 2 个」「引擎已选」这两条看着都正常，问题是哪个引擎认中文 |

## 三个设计决定

**1. 默认引擎能用就不换。**
`EngineSelector.pick()` 第一条规则是「默认引擎 ready 就保留」，哪怕另一个是离线包。
换引擎会改变识别质量与断句习惯，用户没要求换，我们不该自作主张——
只在默认那个不能用时才动手。

**2. 空探测结果不等于「不支持」。**
`languageVerdict()` 对 `null` 和 `emptyList()` 都返回 `null`（不下结论）。
空表的真实含义是「**没问到**」（系统低于 13、查询不到服务），不是「都不支持」。
混为一谈会让低版本系统上的用户每次都被拦住，而那台设备可能好得很。
C13/C14 两条断言钉死这件事。

**3. 探测结果做成进程级缓存，不是实例字段。**
桌宠探完、用户到设置里点「语音诊断」（new 一个 probe）——如果按实例存，那一刻就是空的，
而那恰恰是最需要看到结果的时刻。

C8 是它的反面：默认能用就不许换。两条一起钉，才挡得住「为了修 bug 到处乱换引擎」。

# 第七轮（2026-11-14 23:10 真机诊断报告）

P16 未通过。用户回传的诊断报告推翻了上一轮的一个隐含假设。

## 报告说了什么

```
识别服务数量：2
  · com.google.android.tts/…GoogleTTSRecognitionService
  · com.qualcomm.qti.voiceai.speech/…SpeechRecognitionService
系统默认识别引擎：com.google.android.tts/…GoogleTTSRecognitionService

—— 各引擎对 zh-CN 的支持 ——
  · com.qualcomm.qti.voiceai.speech/…SpeechRecognitionService
      不支持当前语言
  当前应使用：没有能用的
```

识别服务 **2** 个，引擎清单 **1** 个。少的是默认引擎——也就是唯一可能认中文的那个。

## 根因：把「没问到」当「没有这一项」

`probeEngines` 在超时或引擎报错时执行 `oneDone(null)`，把该项从结果里**删掉**。

删掉之后，`EngineSelector.pick` 只看到 Qualcomm（明确不支持）→ 返回 null →
`languageVerdict` 给 `false` → 桌宠被拦、聊天页也被判「不支持中文」。

而真相是：我们从未问过那个最该问的引擎。

上一轮其实已经写下这条规则——

> 空表不能当成「都不支持」：它的真实含义是「没问到」。

但那条规则只在**整张表**为空时生效。**单个引擎**这一层没有对应的概念，
于是同一个错误小一个粒度又犯了一次。这是本轮最该记住的一条：

> 一条原则如果只在聚合层成立、在单项层不成立，那它就不是原则，只是巧合。

## 三件一并处理的可疑点

| 项 | 问题 | 处理 |
|---|---|---|
| 800ms 超时 | 那是「服务热着」的数字。冷启动要先 bind 服务再初始化识别器，Google TTS 就死在这个窗口里 | 2500ms。探测全程在后台（桌宠启动时探、不阻塞长按），多等 1.7 秒换「不误判」划算 |
| `EXTRA_PREFER_OFFLINE = true` | 是 *prefer*，但厂商常当 *require*：没装当前语言离线包时直接回 `code=12`，不退回在线 | 删掉。走离线还是在线的决定还给引擎 |
| 聊天页被语言判定误伤 | 系统识别页自己能换语言、自己下包 | 语言维只在 `SelfRecorded` 路径算数 |

第二条最值得说：它可能是**比探测器更直接**的原因。
真机日志里「每按一次就 code=12」与「prefer offline 被当成 require」的行为完全吻合，
而这条 extra 从一开始就没有必要——一次识别几百 KB 流量，比「用不了」便宜得多。

## 改了什么

| 文件 | 改动 |
|---|---|
| `core/voice/RecognitionEngine.kt` | `EngineCapability.probed`；`EngineFit.Unknown`；`isDefinitelyUnsupported` |
| `core/voice/SpeechCapabilityPolicy.kt` | 语言维限定在 `VoicePath.SelfRecorded` |
| `app/audio/SpeechProbe.kt` | 失败项保留为 `probed=false`；超时 2500ms；`force`；四个语言列表原样落日志 |
| `app/audio/VoiceDiagnostics.kt` | 显示未应答项；`buildReportAsync` 强制重探；日志与报告同源 |
| `app/pet/PetVoice.kt` | 删 `EXTRA_PREFER_OFFLINE`；`refreshEngine` 区分「没引擎」与「没问到」 |
| `app/ui/SettingsScreen.kt` | 诊断入口异步化，点击先提示 |

## 一个设计决定

**「没问到」必须是第三种答案，而不是布尔值的第三种取值。**

把它塞进 `Unsupported` 是最省事的，但那样就永久失去了「值得再问一次」这个信息。
所以它是一档独立的 `EngineFit.Unknown`，并且带 `isDefinitelyUnsupported = false`——
区别落在**类型**上。写成 `describe(fit).contains("不支持")` 的话，
改个措辞断言就红了，而判错档位时它可能照样绿。

## 验证

| 手段 | 结果 |
|---|---|
| `run-speech-capability-verification.sh` | **118 通过 / 0 失败**（26 + 48 + 16 + 11 + 12 + 5） |
| 全量回归 | PASS=144 SKIP=1 FAIL=0 |
| `assertion-census.py` | 1729，只减不增（新增全是行为断言） |
| APK 反验 | 加分文案 2 条；反证 `android.speech.extra.PREFER_OFFLINE` 已消失 |

E4 是照着这份报告写的那一幕：

> 默认引擎未应答 + 另一个明确不支持中文 → 仍选默认，且 `languageVerdict == true`。

它同时钉住了「不能因为一次超时就把用户的语音判死」和「不能为了有得选就乱换引擎」。

## 判据（P17，5 分钟）

| 判据 | 通过 | 不通过的含义 |
|---|---|---|
| **P17-1** 设置 → 语音诊断（先别开桌宠） | 引擎清单是 **2** 项，Google TTS 那行标「仅在线可用」或「没问到」 | 仍 1 项 → 强制重探没生效 |
| **P17-2** 同一份报告的「当前应使用」 | 不是「没有能用的」（「未应答，先按系统默认试一次」也算通过） | 两个都标「不支持」→ 这台机器确实没有中文识别包，报告结论是**对的** |
| **P17-3** 桌宠长按说「现在几点」 | 识别出文字并自动发送 | 仍 code=12 → 发日志里 `引擎 xxx 回答 zh-CN：…` 那几行，那是引擎的原话 |
| **P17-4** 聊天页点麦克风 | 弹出系统识别页并能识别中文 | 弹不出 → 与语言判定无关，看报告最后两行 |

> 这一轮把 P16-1 的判据改掉了。原来写的是「当前应使用 ≠ Google TTS」，
> 隐含假设「设备上一定还有另一个能用的引擎」——真机上没有。
> 正确的判据是「事实摆全」：清单不能少项，结论要和清单对得上。
> 若两个引擎确实都不认中文，「没有能用的」就是正确答案，那时该做的是下中文包，
> 而不是继续改代码。

# 第八轮（2026-11-14 23:50 三张真机截图）

用户按上一轮的话去操作，回传三张截图。结论只有一句：

> **我们一直在指路一个这台机器上不存在的页面。**

「默认应用」列表里是桌面、短信、相机、浏览器、电话、图库、邮件、音乐、视频。
没有「语音识别」。他点进去看到的是「文字转语音输出」——TTS，不是识别。

系统把 `VOICE_RECOGNITION_SERVICE` 自己写了默认值（Google TTS），
但不提供修改入口。所以「换一个服务」这句话，在这台机器上是死路。

## 为什么前几轮没发现

因为诊断报告里那一行是绿的：`系统默认识别引擎：com.google.android.tts/…`。
它证明「设置了」，我们从没验证过「用户能不能改」。
**一个值存在，和一个值可改，是两件事。**

这和第五轮那次误判是同一种错误：把「有」当成了「能用」。

## 改法：把选择做进 App

`createSpeechRecognizer(ctx, component)` 本来就是官方给应用指定引擎的入口。
能指定，就不该要求用户去翻一个可能不存在的系统页面。

新增「语音识别」页：列出本机所有引擎及状态，点一下即指定。
桌宠的「去换引擎」直达这一页——不是设置页顶部，因为用户刚被拒绝一次，
再让他往下滑六组会直接放弃。

| 文件 | 改动 |
|---|---|
| `ui/VoiceEngineScreen.kt`（新） | 引擎单选列表 + 两句原理说明 + 生成诊断 |
| `ui/AppScaffold.kt` | 路由 `VOICE`；`initialRoute` / `onRouteConsumed` 一次性导航 |
| `MainActivity.kt` | `EXTRA_DEST`；`onNewIntent` 也消费 |
| `audio/VoiceEngineStore.kt`（新） | 记住选择，空 = 自动 |
| `pet/PetVoice.kt` | 用户选择 > 自动探测 |
| `pet/PetOverlay.kt` | 换引擎直达应用内页 |
| `core/voice/EngineLabel` | 引擎中文名；畸形输入也不返回空串 |
| 三处文案 | 去掉「默认应用」，改指「设置 → 语音识别」 |

## 两个决定

**1. 用户的选择高于自动探测。**
自动那套解决的是「不知道该选什么」。一旦用户点了某个引擎，再让探测盖掉他，
就是「App 觉得自己更懂」——而且界面显示与实际使用会不一致，那是最难查的一类 bug。
A27 钉的就是这一条。

**2. 引擎必须有中文名。**
`com.qualcomm.qti.voiceai.speech/…SpeechRecognitionService` 没法选。
命名规则写成纯函数放 core，是因为这类逻辑错了不报错——只会让用户在一串
看不懂的字符串里瞎点。
