> 目标：把 P12 剩下的 6 条（静音阈值 / Android 14 录音 / 朗读打断 / ducking / 他应用占麦 / 录音中拖动）收掉。

## 一、又是同一类问题：没有引擎，就以为功能坏了

前两轮每次走到「朗读」这一步，日志都只有一行：

```
WARN [PetOverlay] 桌宠朗读失败：系统 TTS 未就绪（设备可能没有语音引擎，或引擎初始化超时）
```

AOSP 镜像里没有任何 TTS 引擎，`TextToSpeech` 的 `OnInitListener` 回调 `ERROR`，代码如实报「未就绪」。
这行日志是对的，但它把后面 4 条判据（P12-5/6、P13-4 的朗读部分、P11-5 的朗读部分）全部堵住了。

补法和上一轮的桩识别服务同源：写一个 200 行的 `com.beichen.debug.tts`，继承 `TextToSpeechService`，
按文本长度吐**等长的静音 PCM**（1 字 220ms，上限 12 秒）。

为什么是静音而不是真声音：模拟器没有声卡，出真音也没人听得见；但 PCM 的**长度**决定了
`AudioTrack` 的播放时长，而播放时长决定 `onDone` 何时回调、`speaking` 何时回落 ——
这恰恰是仲裁逻辑依赖的东西。音质、语速、多语言这些，仍然只能真机。

### 装上去之后仍然报「未就绪」，卡了三处

| # | 现象 | 真因 | 证据 |
|---|---|---|---|
| 1 | 装好、`tts_default_synth` 也设了，`cmd package query-services -a android.intent.action.TTS_SERVICE` 能查到，但 App 里依然秒失败 | **`intent-filter` 少了 `<category android:name="android.intent.category.DEFAULT"/>`**。`TextToSpeech` 内部用 `queryIntentServices(..., MATCH_DEFAULT_ONLY)` 找引擎，没有 DEFAULT 就返回空 —— 而且**不打印任何日志**，`dispatchOnInit(ERROR)` 静默收场 | 补上 category 后立刻 `onLoadLanguage` / `onIsLanguageAvailable` 全来了 |
| 2 | 补 category 之前还试过「去掉 `android:permission="BIND_TTS_SERVICE"`」，仍然失败 | 权限不是原因；但顺手确认了：**客户端绑定引擎不需要该权限**（系统只在 `bindService` 时按 service 声明的 permission 校验） | 去掉后 `query-services` 里 `permission=null`，行为不变 |
| 3 | 装完 `am startservice` 报 `Error: app is in background uid null` | 新装的包 `stopped=true`，系统拒绝启动它的服务，`bindService` 直接失败 | `dumpsys package` 里 `stopped=true notLaunched=true`；加一个空 Activity 用 `am start` 拉起一次后变 `stopped=false` |

第 1 条值得单独记一笔：**这是「功能静默失效」的典型形态** —— 配置看起来全对，日志一条没有，
只能靠读 AOSP 源码里的 `MATCH_DEFAULT_ONLY` 才能想到。真机上偶尔也会遇到（用户装了引擎但没生效），
所以 `TextSpeaker` 报「系统 TTS 未就绪」时，下一步该查的是 DEFAULT category，而不是语音包。

## 三、新增 5 条结论

### P12-5 朗读中长按 → 立刻停 + 开始录音 ✅

在朗读第 4.96 秒（总长 6.82 秒）时长按形象：

```
04:08:37.533  StubTTS  onSynthesizeText len=31 -> 6820ms        ← 开始念
04:08:42.463  [Voice]   Speak 被抢占（朗读）→ Capture
04:08:42.473  [Voice]   播报被 Capture 抢占，停止出声
04:08:42.491  StubTTS   done written=204800/300080               ← 68% 处硬停，剩下的没喂
04:08:42.502  StubTTS   onStop
04:08:42.569  [Voice]   迟到的释放被忽略：Speak#4（当前 Capture#5，被抢占）
04:08:44.877  [Voice]   Capture#5 释放（语音输入结束）
04:08:45.094  [AgentLoop] 开始运行，输入：… 拖动时说的话（历史 3 条）
```

三个细节都能对上设计意图：

- **停得够狠**：不是「下一句 FLUSH 掉」，是当前这句在 68% 处被截断（`204800/300080`）；
- **抢得够快**：从抢占日志到 `onStop` 相差 39ms；
- **迟到回调被挡住**：`迟到的释放被忽略：Speak#4（当前 Capture#5，被抢占）` —— 这正是
  `TextSpeaker.currentUtteranceId` 那句比对存在的理由，本轮第一次看到它真的拦住了一次。

### P12-6 ducking ✅（含一条对判据说法的修正）

判据原文写「失败时最可能的原因：`TextSpeaker` 没申请到音频焦点（部分 ROM 不实现 ducking）」。
实测发现**机制和这个描述不一样**，而且对实现是好事：

对端（一个持 `USAGE_MEDIA` + `AUDIOFOCUS_GAIN` 放正弦波的 app）**从头到尾没收到任何 focus 回调**，
但 `dumpsys audio` 的事件日志里写得很清楚：

```
04:10:49:167 ducking (strong) player piid:543 uid/pid:10147/5187 skip ramp:false
04:10:56:295 unducking piid:543
```

也就是 **Android 12+ 由系统直接做 duck**（`GAIN_TRANSIENT_MAY_DUCK` 的请求方不再依赖对端响应
`LOSS_TRANSIENT_CAN_DUCK`），所以「对端没回调」不是失败，而是新行为。
两点结论：

1. 压低与恢复都发生了，且与朗读起止对齐（49.167 ↔ 朗读开始，56.295 ↔ `Speak#10 释放`）；
2. `TextSpeaker` 的 `focusListener` 只处理 `LOSS` / `LOSS_TRANSIENT`、**故意不处理 `CAN_DUCK`**
   —— 这个选择是对的：duck 由系统管，应用侧再压一次会把音量叠成 0.04。

判据里那句「部分 ROM 不实现 ducking」应改为「Android 12 以下依赖对端响应，12+ 由系统代做」。

### P12-7 他应用占麦 ✅

对端用 `AudioRecord(MIC)` 持续录音（`read n=1600 rms=3`，通道开着、无声），
再长按形象：

```
04:12:04.558  [PetVoice] 麦克风被拒：audio_external_busy / 另一个应用正在录音
```

气泡顶部同时出现红字「**另一个应用正在录音**」（截图 `p12-7-bubble.png`）。
识别引擎压根没被拉起（`StubSTT` 无任何日志）—— **在进入识别之前就拦下了**，这正是判据要的
「不是『识别失败』」。

### P12-8 录音期间拖动 ✅

桩设 `delay=9000`，长按进入聆听后立刻从 `(678,860)` 拖到 `(250,500)`：

```
Frames: parent … frame=[636,817][720,901]    ← 拖动前
Frames: parent … frame=[636,690][720,774]    ← 拖动后（上移 127px，横向仍贴边）
03:55:20.698  [Voice] Capture#1 释放（语音输入结束）   ← 9 秒后正常结束，没被手势打断
03:55:27.728  [AgentLoop] 开始运行，输入：… 拖动时说的话
```

横向不动是因为实现就是「贴边 + 只允许垂直移动」，不是没跟上。
录音没断、9 秒后照常发送、回合跑完（`9687ms，31 字`）。

### P12-3 停顿不中断 ⚠️ 只到 App 侧

桩设 `delay=7000`（模拟「说完停 2 秒，6~7 秒后引擎才给结果」）：

```
04:13:17.382  StubSTT  onStartListening … delay=7000
04:13:24.390  [Voice] Capture#13 释放（语音输入结束）
```

中间整整 7 秒，租约一直持有，没有任何提前释放或 `cancel`。加上代码里确实没有静音计时器，
可以说「**App 侧不存在 2 秒静音中断**」。但「两句都识别得出来」取决于引擎的 VAD，
这一半仍然只能在真机上用真实语音验。

## 五、顺带复查：system prompt 重复仍在

上一轮报过的 `PetAgentSession.kt:141` 问题，这轮 15 次请求里又出现两次：

```
req5   n=5 sys=2  ['system','system','user','assistant','user']
req10  n=5 sys=2  ['system','system','user','assistant','user']
req12+ n=5 sys=1  ['system','assistant','user','assistant','user']
```

规律没变：**每个新进程里「第一次带历史」的那次请求会带两个 system**，之后被 `takeLast` 把旧 system 挤掉，
看起来又正常了。修法仍是那一行：

```kotlin
history.addAll(messages.filterNot { it is SystemMessage }.takeLast(MAX_HISTORY))
```

另外从 `req12` 起，历史窗口滑动后第一条变成 `assistant`（最早的 `user` 被裁掉），
语义上可以接受，但如果要严格「成对裁剪」，得按 2 的倍数裁。

`messages` 就能收口（假端点的日志格式见第三节）。
