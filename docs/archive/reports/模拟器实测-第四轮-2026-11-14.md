# 模拟器实测 · 第四轮（2026-11-14）

> 目标：把最后一条「必须真机」的 **P12-4** 收掉（Android 14 后台麦克风）。
> 结果：**环境没撑住，一条新行为结论都没拿到**。改用静态判定把 P12-4 拆成两问，
> 顺带修好了沙箱的网络通道。

---

## 一、开场先修环境：CA 证书与 DNS 都丢了

沙箱根文件系统被重置过一次：`/var/tmp` 空、Android SDK 不在、`/workspace` 的文件还在。
两个副作用比丢 SDK 更隐蔽：

| 现象 | 真因 | 修法 |
|---|---|---|
| `curl https://github.com` 返回 `000`，`git clone` 挂起 | `/etc/ssl/certs/ca-certificates.crt` **不存在**（`curl: (77) error setting certificate file`），所有 TLS 都验不过 | `cp $(python3 -c 'import certifi;print(certifi.where())') /etc/ssl/certs/ca-certificates.crt` |
| 证书修好后仍然 `000`，但 `140.82.121.4:443` 是通的 | `github.com` 被解析到 `57.155.223.240`（污染地址），不是真实 IP | `/etc/hosts` 写死 `140.82.121.4 github.com` / `140.82.121.6 api.github.com` |
| `clone` 能连但只有 5 MB/10 分钟 | `codeload` 限速（~72 KB/s），`--filter=blob:none` 也要拉全部 tree | **改用 `https://gh-proxy.com/https://github.com/...`，33 MB 仓库秒回** |

最后一条是仓库里 `docs/ops/网络通道与加速指南.md` 早就写过的，只是这次连 CA 证书也没了，
表现得像"网络全断"。下次遇到 `curl 000`，先看 exit code：**77 是证书，28 是超时**，
两者要分开查。

## 二、重建模拟器：装得回来，跑不动

| 步骤 | 耗时 | 备注 |
|---|---|---|
| `cmdline-tools` + `platform-tools` + `emulator` + `system-images;android-34;google_apis;x86_64` | 2 分 07 秒 | 147 MB + ~1.3 GB，`dl.google.com` 速度正常 |
| 建 AVD（pixel_5 骨架，720×1280，4 核 3 GB） | 秒级 | 无 `/dev/kvm`，只能 `-accel off` |
| 冷启动到 `sys.boot_completed=1` | **约 8 分钟** | 期间 `pm`/`window` 服务反复"找不到" |
| `adb install` 两个包（桩 STT 12 KB、应用 23 MB） | **222 秒 / 205 秒** | TCG 下 dex2oat + PackageManager 极慢 |

装完、启动服务、进程起来了，但**桌面还没出来就全崩了**。

## 三、为什么没跑成：system_server 被 watchdog 反复杀

```
/data/system/dropbox$ ls | grep -c watchdog
10
system_server_watchdog@1794639652442.txt.gz   07:00
system_server_watchdog@1794639888161.txt.gz   07:04
system_server_watchdog@1794641014803.txt.gz   07:23
```

dump 里的现场：

```
----- Output from /proc/pressure/cpu -----
some avg10=58.53 avg60=55.33 avg300=56.33 total=1030480360
CPU usage: 158% 1355/system_server: 66% user + 92% kernel
```

CPU 压力长期 58%，system_server 自己吃掉 1.5 核还喂不饱 watchdog 的心跳。
表现是一串 `DeadSystemException`、`Broken pipe`、`cmd: Can't find service: package`，
然后 zygote 重启，一切从头来。停掉 GMS / quicksearchbox / `com.google.android.as`
（`pm disable-user`）之后压力没降多少——瓶颈是单核性能，不是后台任务。

**这跟第三轮的 keyguard 卡死是同一个根因**：没有 KVM 的 TCG 跑不动 Android 14 的
system_server。第三次能验完 5 条，是运气好赶在两次 watchdog 之间；这次开局就撞上。

## 四、改用静态判定：P12-4 到底在判什么

既然跑不起来，就把能静态判的判掉。三条硬事实，全部有出处：

| # | 事实 | 出处 |
|---|---|---|
| 1 | `targetSdk = 28`，且是**故意的**（Android 10+ 对 targetSdk≥29 禁止从应用数据目录 `execve`，proot 容器就废了；Termux 同理） | `app/build.gradle.kts:119-125`、APK `uses-sdk` |
| 2 | `PetOverlayService` 在 API 34+ 传 `FOREGROUND_SERVICE_TYPE_SPECIAL_USE`（`0x40000000`），manifest 里也只有 `specialUse` + `<property PROPERTY_SPECIAL_USE_FGS_SUBTYPE>` | 源码 `startAsForeground()`；APK 字节码 `const/high16 v1, 1073741824` + manifest xmltree |
| 3 | 应用**不自己录音**：三个 dex 全扫，`AudioRecord` / `MediaRecorder` 零调用；语音走 `SpeechRecognizer.startListening`，录音在识别引擎进程里做 | `androguard` 全量扫描 |

推论：

- Android 14 的「FGS 类型必须匹配实际能力」检查只对 `targetSdk ≥ 34` 强制，**本应用不触发**；
- 第一轮抓到的 `Foreground service started from background can not have ... microphone access`
  确实存在（它按 `uidState` 判，不看 targetSdk），但它清的是 **Polaris 自己**的 while-in-use 权限，
  而 Polaris 自己不用麦克风；
- 真正录音的是引擎（Google 语音服务 / 桩 STT），权限和音频策略作用在**引擎的 uid** 上。

所以之前 spec 里那句"重建后第一次长按说话会说不出话"**在静态层面站不住**。
但它也不能反过来判绿——"引擎会不会把调用方 uid 带进 attribution"是实现细节，
AOSP 的 `RecognitionService` 和各家引擎做法不一样。这一条只能真机看。

## 五、P12-4 拆成两问

| 问 | 判定 | 成本 |
|---|---|---|
| **4a** 用户主动唤起（长按/磁贴）后能不能录到音 | 与 P12-2 完全同一条路径，P12-2 过了就是过了，**不必单独验** | 0 |
| **4b** 服务被系统自愈重建后能不能录到音 | 真机 1 分钟，二选一 | 1 分钟 |

4b 的验法（已写进清单）：

```bash
adb logcat -c
adb shell am kill com.beichen.polaris
sleep 45                                       # 等 START_STICKY 重建，看悬浮窗自己回来
adb logcat -d | grep "can not have microphone access"    # 只记录，不判定
# 长按形象说「现在几点」
adb logcat -d | grep -E "PetVoice|StubSTT|PetService"
```

- 识别出文字 → **通过**，说明引擎录音不受 Polaris 的 FGS 权限影响；
- 报 `ERROR_AUDIO` / 没反应 / 只提示「没听清」→ **不通过**，且现有文案会误导用户，
  那时才需要改（两条路：把 FGS 类型补上 microphone 与 targetSdk 的矛盾无解；
  或者重建后不自动进可语音态，让用户点一次磁贴/通知再说话）。

## 六、这轮没做成的与下次

- **没验到的**：P12-4b 本身。模拟器音频不可信这条依然成立，但现在它已经不是"唯一必须真机"，
  而是"真机上 1 分钟能收口的一问"。
- **下次开模拟器前先看两件事**：`ls /dev/kvm`（没有就别指望 Android 14）、
  `/proc/pressure/cpu`（`some avg10 > 40%` 说明 watchdog 迟早来）。
- **环境也会骗人**：第三轮 keyguard 起不来、这轮 system_server 反复被杀，两次都不是应用的问题。
  不查 dropbox 和 pressure，很容易记成「桌宠把系统搞崩了」。
