# 端上可行性：手机上真正能跑的是什么

> 2026-11-13。承接 [10-agent-mechanisms](10-agent-mechanisms-2026-11-13.md) 与 [11-deepseek-harness](11-deepseek-harness-2026-11-13.md)。
> 起因是一句质疑：「调研的项目大多跑在电脑上」。这个质疑成立，本文把已核验的项目按**运行位置**重新切片，
> 划出端上（装机即用）与 PC 侧（adb 控制）的能力边界，以及由此决定的取舍。

---

## 一、结论先行

1. **star 最高的「手机 Agent」大多不是手机应用。** 它们是电脑上的 Python 程序，通过 adb/USB 控制手机。
   目标是跑 benchmark 出论文，不是做产品。
2. **真正端上装机即用的，star 普遍低一个数量级**，但机制更贴近「日常能用」——因为它们必须自己解决权限、后台、功耗。
3. **我们已经站在端上这一侧。** 这不是妥协，是位置优势：端上能拿到 PC 侧永远拿不到的数据（通知、传感器、剪贴板、电量）。
4. 端上有**六条硬约束**。任何「把电脑上那个功能搬过来」的想法，先过这六条，过不了就改形态，不要硬搬。

---

## 三、为什么 B 类的 star 最高

三个原因，全部与研究场景有关，与产品体验无关：

1. **可复现性**。论文要一键跑 AndroidWorld / Mobile-Bench，必须由 PC 统一编排、统一记录、统一重放。
   端上跑没法保证「同一台机器、同一版本、同一初始状态」。
2. **权限成本为零**。adb 的 `input tap` / `uiautomator dump` 不需要用户点授权、不需要开无障碍、
   不会被 ROM 杀后台、不需要前台服务通知。研究阶段这是最省事的路径。
3. **模型随便用**。评测调云端大模型，PC 侧没有延迟和成本顾虑，一个 turn 调十次也无所谓。

**这三条在产品上一条都不成立**：

> 用户不会为了用一个手机助手，去装 adb、开 USB 调试、插着线连电脑。

所以 B 类的代码可以读、设计可以借，**运行形态不能搬**。搬过来就是把产品做成开发工具。

## 四、端上六条硬约束

这是「能不能在手机上做」的真实边界。每条都给出具体的系统行为，不是泛泛而谈。

| # | 约束 | 具体限制 | 对我们的意味 |
|---|---|---|---|
| 1 | **权限不是自带的** | 无障碍需用户手动进设置开启；Shizuku 每次重启要重连；悬浮窗单独授权；Android 13+ 通知权限运行时申请 | 首次使用必须做引导页 + 状态自检，任何功能都不能假设「已经有权限」 |
| 2 | **后台会被掐** | Android 12 禁止从后台启动前台服务（除豁免）；Android 14 强制声明 `foregroundServiceType` 并校验；Android 15 `dataSync` 类型限 6 小时/24 小时；Doze + 厂商清理 | 长任务必须能断点续跑，不能假设「一直活着」。跑之前先查电量与充电状态 |
| 3 | **算力只有云的零头** | 端上现实区间 1B~4B 量化模型；4B int4 在旗舰 SoC 约 10~15 tok/s，7B 勉强但明显发热掉电 | 本地模型只做分类、抽取、唤醒判定这类**短输出**任务；规划仍走云 |
| 4 | **不能注入别人的进程** | 没有 hook、没有 root 注入；只有无障碍读节点树 + 截图 OCR + 模拟点击 | UI 树拿不到的信息（自绘界面、WebView 内部、游戏）只能靠视觉兜底 |
| 5 | **常驻是有价格的** | 关键词唤醒常驻约 64 MB 内存、冷加载约 4.6 秒（见 10 号文档 Movo issue #11 实测） | 唤醒默认关；开了要能在设置里看到内存占用 |
| 6 | **麦克风/摄像头后台受限** | Android 11 起一次性授权；后台访问麦克风需前台服务 + 常驻通知；部分 ROM 直接静音后台录音 | 语音能力必须挂在可见的前台服务上，用户随时知道「它在听」 |

### 由约束推出的三条设计原则

- **渐进授权**：功能触发时才要权限，不要一进 App 就弹一堆。
- **失败可见**：权限被撤、服务被杀、麦克风被抢，都要在界面上说清楚「为什么不行」，不能静默失败。
- **可降级**：端上做不了的交给云，云做不了的交给用户确认。任何一步断了，流程要能退化而不是崩。

## 五、端上独有、PC 侧永远拿不到的

这是反向清单——**我们比 B 类多的东西**：

| 能力 | 为什么 PC 侧没有 |
|---|---|
| `NotificationListenerService` 读通知 | adb 只能 `dumpsys notification` 拉快照，拿不到实时流，也不合规 |
| 剪贴板 / 传感器 / 位置 / 日历 / 通讯录 | 需要端上运行时权限，PC 侧无从获取 |
| 电量、网络、充电、屏幕亮灭状态 | 端上可据此做省电策略（如只在充电时跑记忆整理） |
| 免 USB、免调试、随时可用 | B 类的前提就是这根线 |
| 应用内自升级闭环 | 我们改自己代码 → CI → 应用内下载安装，这条 B 类项目没有 |

**结论**：不要去补 B 类的短板（全自动点屏），要放大端上的长板（常驻感知 + 主动触发 + 自升级）。

## 六、可行性矩阵

按「端上能不能做 / 代价多大 / 值不值得」排：

| 功能 | 端上可行度 | 主要代价 | 建议 |
|---|---|---|---|
| 回复打断仲裁 | 高 | 无，纯代码 | **做**（半天） |
| 麦克风四条件仲裁 | 高 | 需前台服务常驻 | **做**（1 天） |
| 工具守卫链 + 3 个接缝 | 高 | 无，纯代码 | **做**（2 天，越晚越贵） |
| 桌宠悬浮窗（透明 WebView + Live2D） | 高 | 悬浮窗授权 + 常驻内存 | **做**（3 天，先静态形象） |
| 执行后反思（屏幕变了吗） | 高 | 每步多一次截图比对 | **做**（1 天，显著降低静默失败） |
| 记忆「做梦」离线整理 | 高 | 用 WorkManager 约束「充电 + 空闲」 | **做**（3 天） |
| 关键词唤醒 | 中 | 常驻 64 MB、冷启 4.6 s | 默认关，设置里可选开 |
| 本地小模型（意图分类/抽取） | 中 | 300 MB~2 GB 模型、发热 | 可选，按机型判断 |
| 虚拟屏幕后台执行 | 中低 | 需 Shizuku，重启重连，适配面窄 | 后期单独立项 |
| 端上大模型做规划（7B+） | 低 | 速度、发热、内存三项全不划算 | **不做** |
| 全自动点屏跑长链任务（B 类那种） | 低 | 无障碍树信息不足，长链路必断，出错无法归因 | **不做全自动，做半自动 + 人工确认点** |

## 七、B 类里值得借的三个设计（借设计，不借形态）

| 来源 | 设计 | 为什么端上更需要 |
|---|---|---|
| mobilerun | 把能力拆成 `inspect / tap / swipe / type / plan` 独立工具，而不是一个万能 `execute` | 端上每步都可能失败，工具粒度粗就无法定位是哪一步坏的 |
| Mobile-Agent | 每步执行后做 reflection：判断「屏幕变了吗」，没变就换策略 | 无障碍点击**经常静默成功但没生效**，不比对就会一路错到底 |
| PhoneUse | 端上 App 对外暴露 MCP / Skill 契约，而不是自己独占控制权 | 与我们已有的 Skill 体系同向，可以让外部 agent 复用我们的端上能力 |

## 八、路线

不做「把电脑项目搬到手机」，做**端上原生**。顺序按「依赖关系 × 成本」排：

| 步 | 内容 | 成本 | 为什么这个顺序 |
|---|---|---|---|
| 1 | 3 个接缝（`before-user-message` / `before-tool-call` / `after-assistant-message`）+ 守卫链 | 2 天 | 后面所有功能都挂在这上面，越晚做返工越大 |
| 2 | 麦克风仲裁 `MicClaim` + 回复打断仲裁 | 1.5 天 | 桌宠和语音的前置；不做的话接个电话回来语音就哑 |
| 3 | 桌宠悬浮窗（透明 WebView，先静态形象） | 3 天 | 用户可感知的形态，先跑通窗口与生命周期 |
| 4 | 执行后反思（截图比对） | 1 天 | 提升所有自动化任务的成功率，独立于桌宠 |
| 5 | 权限引导页 + 状态自检 | 1 天 | 把约束 1 变成可解释的界面语言 |
| 6 | 关键词唤醒（默认关） | 3 天 | 依赖 2 的仲裁，且要处理常驻成本 |

第 1 步做完，第 2~4 步可以并行。前 5 步合计约 8~9 天，全部不引入新依赖、不需要 root、不需要 Shizuku。
