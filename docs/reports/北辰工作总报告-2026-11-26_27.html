三、主线：为什么「思考与工具」总是分成两层

用户前后发了六七次截图和视频，说法一次比一次具体：

「思考还有工具的调度，在运行的时候还是分为两层的，只有在最后才合在一起。」
「思考完之后调度工具，再自己思考——图 1 图 2 都是这样，不像我们。」

前四次修改都只修到一半。真正的原因一层包一层。

第 1 次：段被三处各自推算（1.917 前半）

「哪些条目属于同一次 run」这个判断散在三个地方：渲染、折叠状态、正文归属。三处各算一遍，边界永远对不齐。

→ 改法：segmentAt 成为唯一区间来源，traceAt 一次返回 (run, ownership, drawBody)，调用方没法只问一半。

分成两个函数问过一次，后果是段首的思考被两边都判成「别人负责」，整段过程在界面上凭空消失。

第 2 次：「墙」判错了两次（1.917 后半）

段靠什么断开？

判据 后果
只收相邻的 Tool 正文一插进来就断成两块
把「有正文的助手」当墙 误伤同一条消息里的「先说一句 + 调工具」——这是最常见的真实形态
墙只有用户消息（现在） 天然断开，其余全归一段

第 3 次：真正的原因不在渲染，在输入（1.918）

前两次修完，现象还在。因为段算的是 List<UiItem>，而流式期间的思考根本不在这个列表里——它活在 reasoningDraft 这个临时变量，正文活在 streamDraft，落库那一刻才写进去。

所以「跑的时候两层、跑完才合」不是渲染 bug，是数据不同源。

→ 改法：withLiveDraft(messages, streamDraft, reasoningDraft) 把草稿作为虚拟末项接在列表末尾，一起参与段计算。落库只是「虚拟项换成真实项」，位置不动。

第 4 次：思考只剩最后一条（1.919）

根因在存储与事件两层：

  1. 收尾那句 if (msg.content.isNotBlank()) 才落库——中间步「只想没答」，content 是空的，连 reasoning 一起被丢掉；
  2. 就算落了，appendToTurns 对助手消息一律收进 variants（变体），一轮 N 个变体，界面只显示选中的那条。

→ 改法：新增 AgentEvent.AssistantStep，loop 在派发工具之前把这一步交出去；trace 才是它的正确去处（定义本来就是「回答之前的过程，保序」）。

顺序很关键：先派工具再发事件，思考就永远排在工具后面，链是断的。

第 5 次：中间那段正文被当变体（1.920 / 1.921）

「说一句 → 接着调工具 → 再说」——那句中间正文有内容，于是走了「变体」分支 → 界面消失，下一轮模型也读不到自己说过的话。

判据还是错的：content.isBlank() 判的是「有没有文字」，我们要判的是「是不是本轮最终回答」。这件事只有调用方知道。

→ 改法：appendMessage(..., asTrace: Boolean = false)，由收尾循环按 msg !== lastAnswer 显式声明；默认值 false，5 个 harness 零改动。

第 6 次：一轮里出现了两个「回答」（1.923）

1.921 之后，用户看到的最后一种错形态是：一轮里两个气泡、中间夹着思考——「我说了一句进展，它把这句当成了最终回答」。

→ 改法：answerAt() 定义唯一化 = 本轮最后一条有正文的助手；其余有正文的步一律变成流里的「说明」（标题「说明」、摘要首行、全文进详情），正文不进变体。

这就是 1.923 那一版。它编译失败，故事见下一节。

四、做错了什么

这一段是这份报告里最该被记住的部分。

1. 我把「跑完自动折回」当成了正确行为

1.92x 之前，一段过程跑完会自动折成「2 次工具调用」一行。我以为这是「清爽」，写完还写进注释。

用户的原话是：「合起来就看不见了。」

代价：一整轮返工，改判据、改断言、改文案。现在的规则是——带思考的流跑完保持展开（那正是他要看的东西，一步一行并不长），只有「全是工具、一句思考都没有」的流才自动收起。

教训：折叠的价值是「不打扰」，但过程透明才是这个产品的卖点。默认收起等于把卖点藏起来。

2. 本地绿，不等于能编译

1.923 推上去，CI 第一件事就挂了：

e: TraceFlow.kt:263:43 Smart cast to 'String' is impossible, because
   'm.reasoning' is a public API property declared in different module

TraceFlow.kt 在 :app，UiItem 在 :core。R06 harness 是把 core 和 app 合成一次编译跑的，跨模块的可见性规则根本没生效——本地 43 条全绿，CI 一行就红。

代价：一次构建（约 21 分钟）+ 一次重推。

现在的规矩：改了跨模块属性访问，本地 R06 绿不算数，必须过一遍 AGP 编译。

3. 断言写死了旧行为，把门禁顶红

1.924 修完编译，QA 门禁红：PASS=169，基线 170。

原因：Hotfix11Verification 的 U10 断言写的是 if (!active && !touchedByUser)——这是旧折回规则的字面复刻。代码按新意图改了，断言没跟。

这里有个取舍：不能为了让门禁变绿去删断言（那是掩盖），也不能让代码迁就断言（那是倒退）。正确做法是断言跟随意图重写，守同一条语义。1.924 就是这么过的。

4. 同一件事断言了两遍

1.925 加「单行思考也要折回」的守卫，写完发现和 1066 行那条重复——census 从 632 变 633，而 census 的规矩是只减不增。

代价：这一版直接取消，重来。

教训：加断言之前先 grep 一遍语义，别只 grep 字面。

5. 我把用户的参照系认错了三次

用户发三张图对比，说「图 1 图 2 是对的，图 3 是错的」。我花了两轮去猜「图 2 是谁家产品」，还问「这是你们的产品吗」。

用户的回答一次比一次重：

「我说的，你是你自己这个应用 WorkBuddy。」
「是你脑子有问题吗？图 2 是 WorkBuddy，是你自己，不是我们的。」

我把「用户拿什么当标准」当成了需要澄清的问题，其实他就是说：别人都长这样，我们不长这样。

教训：用户给参照物时，不要先考证参照物是谁，先看形状差在哪。

6. 文献是用户催了才去查的

改到第四轮，用户说：「看一下网上找一下资料啊，文献啊，特别是开源社区这些地方。」

查完才发现方向一直是对的，但因为没有依据，每一轮都只能靠猜，猜一次改一次。查证花了不到半小时，省下的返工至少两轮。

现在的规矩：形态类问题（「别人怎么排的」）先查再做，别拿自己的审美当共识。

7. 优先级判断错过一次

中途用户让我「把做过什么写成文档发到摊位」，我埋头写文档，用户下一句是：「先别管这个仓库文档了……你正文思考都夹在正文的回复里面了。」

教训：界面还错着的时候，写文档是逃避。

五、做对了什么（可以复用的）

  1. 只取约束，不抄实现。 查完 Anthropic / OpenAI / Vercel / Hermes 四家，结论只有一条：思考、工具、正文必须是同一条有序序列里的同级项。grep "AI SDK|UIMessage" --include=*.kt app/ core/ → 0 处；依赖表里没有 agent 或 chat-UI 库。北辰自己的东西（variants + selectedIndex、TraceRun 段归属）一个没动。
  2. 一个判据只有一处定义。 段= segmentAt，回答= answerAt，归属= traceOwnership，三者全是派生。三处各算一次，是这一轮所有「整段消失」的根。
  3. 变异测试。 每条断言都要能被一句代码改动杀死：草稿不并入 → 2 红；段不算思考在跑 → 1 红；中间思考当变体 → 3 红；忽略 asTrace → 1 红；退回正文当墙 → 5 红。杀不死的断言等于没写。
  4. 帧级取证。 用户发视频说「挂了」，我不看缩略图，拉原文件按时间点抽帧：640×1422 / 10.11s / 302 帧。结论是「没崩、没白屏、链在长」——这才排除掉「闪退」这个方向。
  5. 行数冻结。 三个巨型文件全程没破线，新逻辑一律进新文件（TraceFlow.kt 372 行、ChatToolTrace.kt 434 行）。

行为

  • 思考与工具按发生顺序交替在同一条竖线上；
  • 跑完不折回（带思考的流），过程一直可见；
  • 一轮只有一个回答气泡，途中说的话变成流里的一步；
  • 流式中草稿并入段，不再出现「上面一叠工具、下面单挂思考」；
  • 普通问答（1 条助手、无工具）不折流，思考仍是正文上方一行，与 ChatGPT 的 Thought for 5s 同形。
