三、六个问题，逐个说清

A. 「装上了，但进不去」

最初看到的现象：用户发来视频——打开就是闪退，或者进去一瞬间又回桌面；偶尔能进，进去后会话全没了。

第一轮判断错了：以为是启动期某个 IO 出错，加了 StartupGuard（1.911）做兜底——连续 3 次启动失败就把 agent_run_state.json / drafts.json / run-journal 挪开重试。这一层现在仍然有用，但它只是止血，不是根因。

第二步：证据不足。诊断包里「最近崩溃报告（Java）」是空的，写着「本机还没发生过 Java 崩溃」——但应用明明刚崩过。于是 1.914 补了 javaCrashSection：读最近 3 份 Java 崩溃全文（每份限 6000 字符），过一遍脱敏再进包。同时把「启动失败直接死」改成 StartupRescueScreen：异常原文可复制，给两条自救路（清运行态 / 导出日志）。

拿到崩溃报告后，根因一目了然：

JsonDecodingException: Unexpected EOF at path: $
JSON input: ....." width="7" height="11"/>\n    <rect x="322" y="215"
  at ConversationStoreKt.parseToolArgs(ConversationStore.kt:376)
  at ConversationProjection.<init>(...)
  at ChatViewModel.<init>(ChatViewModel.kt:990)

十次 Caused by 一模一样。某次绘图工具的参数带了一大段 SVG，超过 4000 字符，被 take(MAX_FIELD_CHARS) 切断 → 半截 JSON 落盘。文件本身是合法 JSON 字符串，所有校验都过得去，所以看不出问题；但每次启动读会话时 parseToolArgs 必炸，而它跑在 ViewModel 的构造里 → 组合期抛异常 → 直接闪退。

「有时能进」的解释也在日志里：store.write conversations bytes=235——读失败后会话被重建，代价是会话说没就没了。

修法（1.915）：

  • 写：encodeToolArgs 超长不再切字符串，改存合法占位 {"__note":"参数过长，已省略（原文 N 字符）","__chars":N,"__keys":"..."}；
  • 读：parseToolArgs 补上「解析本身失败」这道门——runCatching { Json.parseToJsonElement(raw) }.getOrNull() ?: JsonObject(emptyMap())。

原来注释写着「容错」，实际只挡了第三道（类型不对），第一道（解析失败）根本没有门。这类「注释比代码善良」的地方最危险。

B. 「连复制导出那个键都没了」

现象是一条报错接一条报错，用户想复制都复制不到。

真因不在按钮被删了：崩溃区块默认是展开的，一块就能吃掉大半屏，底部那行「复制 / 导出 / 重试」被顶到屏幕外。改法（1.912）：崩溃区块默认折叠，折叠行里常驻「复制全部」，横幅上也补一个复制入口——报错的第一需求是能把它拿出来。

C. 「崩溃记录删不掉」

两个原因叠在一起：

  1. 「清空崩溃记录」写在 if (blockOpen) 里面，还排在 10 条记录之后——折叠态根本不存在这个按钮；
  2. 操作行的「删除」只删日志文件，不动崩溃记录。

改法（1.916）：折叠行常驻 复制全部 | 清空 | 展开（10），清空加二次确认；操作行文案改成「删除日志」，名实相符。

D. 生图 404

MediaRegistry 原来构造 OpenAIMediaProvider(store.loadMediaKey("openai"), store.load().baseUrl)——媒体借用了主对话的 baseUrl。用户主对话配的是 deepseek，于是出图请求打到 api.deepseek.com/v1/images/generations，404。

改法（1.916）：

  • ConfigStore 加 KEY_MEDIA_BASE_PREFIX = "media_base_"，saveMediaBaseUrl/loadMediaBaseUrl（空串走 remove，不留空串，否则会拼出相对路径）；
  • Provider 加 DEFAULT_BASE_URL、统一去尾斜杠；404/401 的错误信息里写出当前端点，下次一眼能看出打错了地方；
  • MediaScreen 只在选 openai 时显示 Base URL 输入框，切换供应商时用 LaunchedEffect(selected?.id) 同步。

这块只改了端点归属，没在真机上验证过出图。用户当时说「生图先不管」，优先级让给了思考链。留待下一轮。

E. 主线：思考与工具为什么总是两层

这是花时间最多的一件事，前后改了 5 次，前 4 次都只修到一半——值得完整记下来。

现象（用户三次拍照对比）：别的产品是 思考 → 调工具 → 思考 → 调工具 → 回答 交替的一条链；北辰是上面一堆工具卡，下面单独挂一个「思考中」，只有一轮结束、落库之后才合成一条，而且合成的结果里思考永远在最下面。

E1. 段被三处各自推算（1.917 前半）

原来「属于同一次 run 的条目」这个判断散在三个地方：渲染、折叠状态、正文归属。三处各算一遍，边界永远对不齐——一处认为「到工具为止」，另一处认为「含后续工具」，视觉上就是断成两块。

改法：segmentAt 成为唯一区间来源，TraceSlot(run, ownership) 一次问全（画不画流 + 正文归谁）。分成两个函数问过一次，后果是段首的思考被两边都判成「别人负责」，整段消失。

E2. 「墙」判错了三次（1.917 后半）

段靠什么断开？三次尝试：

判据 后果
while (next is Tool) 只收相邻 正文一插进来就断成两块
收所有过程条目，但把「有正文的助手」当墙 误伤同轮「正文 + tool_call」（模型先说一句再调工具，很常见）
墙只有用户消息（现在） isProcessEntry(User) == false，天然断开，其余全归一段

同时 traceOwnership 的 TAIL 规则从「必须在段尾」放宽为「有正文就是 TAIL」——段中间的正文也自己渲染，否则「再查一次」这种中途汇报会消失。

E3. 真正的原因：输入里没有它（1.918）

E1/E2 修完，现象还在。因为段算的是 List<UiItem>，而流式期间的思考根本不在这个列表里——它活在 reasoningDraft 这个临时变量，正文活在 streamDraft。落库那一刻才写进 messages，段这才「看见」它。

所以「跑的时候两层、跑完才合」不是渲染 bug，是数据不同源。

改法：withLiveDraft(messages, streamDraft, reasoningDraft) 把草稿作为虚拟末项接在列表末尾，一起参与段计算。草稿那一步于是自然落在流尾（state=RUNNING、标题「思考中」），草稿本身只留正文；落库只是「虚拟项换成真实项」，位置不动。

E4. 思考只剩最后一条（1.919）

E3 之后仍是「跑完只剩一条思考，且排在所有工具之后」。根因在存储与事件两层：

  1. 回合收尾那句 if (msg.content.isNotBlank()) 才落库——中间步是「只想没答」，content 是空的，连 reasoning 一起被丢掉；
  2. 即便落了，appendToTurns 对 ROLE_ASSISTANT 一律收进 variants（变体），于是一轮 N 个变体，界面只显示选中的那条。

正确的去处是 TurnRecord.trace——它的定义本来就是「最终回答之前的过程，保序」。

改法：

  • 新增 AgentEvent.AssistantStep：loop 在派发工具之前把这一步的思考交出去（顺序反了，思考永远排在工具后面，链就是断的）；
  • appendToTurns：content 空、有 reasoning 的 assistant 进 trace；空到底的照旧丢弃（不凭空多一条）；
  • ChatViewModel 收到就投影 + 落盘。

E5. 中间那段正文被当变体（1.920/1.921）

还剩一种形态：「说一句 → 接着调工具 → 再说」。那句中间正文有内容，于是走了「变体」分支 → 界面消失、flatten 不带它 → 下一轮模型读不到自己说过的话。

根因还是判据：content.isBlank() 判的是「有没有文字」，可我们要判的是「是不是本轮最终回答」。这件事只有调用方知道（收尾时手里有 lastAnswer），存储层猜不出来。

改法：appendMessage(..., asTrace: Boolean = false) 显式声明「这条是过程」，有正文也进 trace，停在它发生的位置；收尾循环按 msg !== lastAnswer 判定；默认值 false，旧调用点（含 5 个 harness）零改动。

1.920 就是在这一步把 CI 判红的：Hotfix11Verification 里 P11/P12/Y3 是字面串匹配，append(...) 多了参数后锚点对不上，整条 harness 判 FAIL（PASS=169 < 基线 170）→ 无产物。1.921 把三处断言改成「跟随新签名，但仍守原语义」才放行。

四、业界依据：我们对着什么改的

结论只有一条，三家说的其实是同一件事：思考、工具、正文必须是同一条有序序列里的同级项，不是「消息一个桶、工具一个桶」。

来源 它说什么
Anthropic · extended thinking + tool use thinking / text / tool_use / tool_result 是同级内容块，「按生成顺序拼接后回传」
Anthropic · interleaved thinking 官方给了对照：无交错是 [thinking]+[tool_use] → [text]；有交错是每段工具结果之后再想一次
OpenAI · Responses 推理指南 output 是 items 数组，reasoning 与 function_call 同级，「请保留这些项的原始顺序」
Vercel AI SDK v6 UIMessage.parts = TextPart / ReasoningPart / ToolPart / StepStartPart 一条有序数组
NousResearch/hermes-agent #41266 反例：thinking 塞 reasoning_details、tool 塞 tool_calls，丢了相对位置，重组后变 [所有 thinking][text][所有 tool] → 每轮 400

我们原来的做法（variants + trace 两个桶、按 content.isBlank() 分流）正是那个反例的形状。

没有抄代码：grep "AI SDK|UIMessage" --include=*.kt app/ core/ → 0 处；依赖表里只有 Compose、OkHttp、kotlinx.serialization、Shizuku、MLKit、Rhino；Anthropic 这个词全仓只出现在 ModelListFetcher 的 anthropic-version 请求头（连 Claude 端点必须带的协议头）。

取的是约束（顺序必须保、块必须同级），没取实现。北辰自己的东西一个没动：variants + selectedIndex 的变体切换三家都没有；TraceRun + TraceOwnership 的段归属、9330 条序列穷举验证，别人没有对应物。

九、三条教训

  1. 注释说「容错」的地方，去数一数到底有几道门。 parseToolArgs 注释写了容错，实际只挡类型不对，解析失败直接抛——一个应用就这么被一条 4 KB 的 SVG 锁死了。
  2. 判据要判「语义」，不要判「写法」。 G3 把 viewModel<ChatViewModel>() 当唯一正确写法，带参数的创建被判成「没创建」；content.isBlank() 判「有没有字」却被用来判「是不是回答」。两次都是判据错，不是代码错。
  3. 界面上的「合在一起」，先问数据是不是同一份。 渲染层改了三轮都不对，因为流式期间的数据根本不在被渲染的那个列表里。同一份输入，才谈得上同一个形状。
