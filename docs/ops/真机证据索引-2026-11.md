## 二、从日志里读出的七条

### 1. 租约回收每 30 秒空转一次（174 次）

1.861（11-23 17:12）和 1.866（11-24 09:53）两份诊断包里，同一条日志重复出现：

```
INFO [Lease] 租约 container:alpine 空闲 1394 分钟，执行回收
INFO [Lease] 租约 container:alpine 空闲 1395 分钟，执行回收      ← 30 秒后
... 共 174 次，空闲时长单调递增到 1407，从不回落
```

两份合计 174 次 / 135 次。**空闲时长只涨不回落**，说明：
要么从来没回收成功（容器一直有会话），要么回收成功了但租约没被移除。

这正是 `AgentKit-架构方案-v2-2026-11-06.md` 里记的 B-8「终端租约双闸互斥，实际永不回收」，
当时标了 ✔ 已修。**从这两份真机日志看，症状还在**——至少是「修了但还会刷」。
判断不了是"该回收却没收"还是"收了但没更新状态"，这需要一台真机连上去看。

### 2. 每一轮都打一遍模型配置（60–86 次/份）

```
INFO [Chat] 主客户端 provider=deepseek model=deepseek-chat base=https://api.deepseek.com/v1
```

每份诊断包里 60–86 条。Key 已脱敏，但 **provider + model + base URL 是明文**，
而且它是每轮都打、不是启动打一次。

两个问题：日志噪音（300 行窗口被它吃掉一部分，真正的错误更容易被顶出去），
以及 base URL 属于部署信息，不该进可导出的诊断包。

### 3. `http_request` 单步卡 30 秒

1.874（11-24 19:26）里有两条：

```
WARN [Tool] ← http_request ERROR 30433ms
WARN [Tool] ← http_request ERROR 30382ms
```

**30433ms** 这个数说明工具侧的超时上限约 30 秒，而且撞上了。跑一个手机任务，
其中一步静默卡 30 秒，用户体感就是"它死机了"。§11.14 那条「超时不算错误」在这里有实证：
这两条是 `WARN` 而不是"失败步"，界面上大概率什么都没显示。

### 4. 单独发文件 / 单独发图（用户口述，11-24）

> "单纯的文件或者说是图片，他是不让发的"

对应 `Polaris-真机自测-10分钟.md` 的 A 组（附件链），A1 只发图、A2 只发文件。
说明当时是"必须带文字才能发"。这一组被排成最高优先级，因为它只经过 CI 和一次真机点测。

### 5. 输入框有字时，麦克风图标消失（用户口述，11-24）

用户的最终判断是**不改**：

> "我觉得弄不弄都可以的，因为现在感觉就挺好的。因为本来打字了的话我就不需要麦克风了。"

这是一条**被用户否决的修改**，值得记——否则下次又会有人"优化"回去。

### 6. 待发照片跟着话题跑（用户口述，11-24）

> "我现在的照片文件，会跟着我的变话题转到另外一个话题去"

**已修，但复验结论没有回来**——A3 那个 ★ 项至今没有打勾记录。

### 7. 诊断包"三个包合并成一个"（用户口述，11-23）

> "三个包合并成一个了……他有一个就是说你只接受他这一个格式的"

用户按路径去找导出文件，只看到一个。这是导出链路的命名或打包问题，
会影响"出事了能不能把证据交出来"——也就是可回放交付的最后一米。
