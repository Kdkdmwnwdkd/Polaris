# 可选组件按需下载（2026-11-16）

## 起因

用户连着两条反馈：

> 「内存都 300 多了，开始的时候我们才 30 多」
> 「IRIDIS 就是那种很多都要下才有的，下装包的话就是一个很小的壳……你要什么就自己下，
> 而不是全部下好再给你。况且安装包太大的话，下的也慢」

第一条是**装完之后**的占用（模型 + 本体），第二条是**安装包**本身。两件事要分开修：

- 装完之后的占用 → 语音页摊开「占了多大」，逐笔可删（同日上一个提交）。
- 安装包 → 把「不是人人都要」的东西全部搬出去，包内只留引擎与代码。

## 先纠正一个前提：IRIDIS 的壳也不小

查了 IRIDIS（GitHub `WWRJ3321/IRIDIS`，Kotlin，Apache-2.0）的实际数据：

| | IRIDIS v2.5.0 | 本项目 1.752 → 1.753 |
|---|---|---|
| 安装包 | 标准版 **61.9MB**（老芯片版 75.4MB） | 47.7MB → 约 42MB |
| 推理引擎 | llama.cpp / MNN / LiteRT-LM / GenieX **全部随包** | llama / onnxruntime / sherpa / MLKit 随包 |
| 模型 | 2–7GB，应用内下载（魔搭 / hf-mirror / HF 自动测速） | 24–196MB，应用内下载 |
| 其他按需 | 语音包、翻译包、QNN 运行库 | 容器 rootfs、Shizuku 安装包 |

结论：**IRIDIS 的「按需」指的是模型与数据包，不是引擎。** 它的 61.9MB 就是证据——
四套引擎的 `.so` 一个都没拆。所以「壳」这个词在 Android 上有上限，见下节。

## 为什么引擎 .so 不能按需下载

这不是取舍问题，是平台限制：Android 的链接器只允许从 **APK 的 `lib/<abi>/`** 与系统目录
加载 `.so`（classloader-namespace）。把 `.so` 下载到 `filesDir` 再 `System.load(path)`
会失败：

```
dlopen failed: "/data/user/0/<pkg>/files/x.so" is not accessible for the namespace
"classloader-namespace"
```

要绕开只有两条路，都不适合现在做：

1. 包内留一个 bootstrap `.so`，用 `android_dlopen_ext(ANDROID_DLEXT_USE_LIBRARY_FD)` 从
   文件描述符加载真正的库。技术上可行，但需要写原生 bootstrap + 逐机型验证，
   失败的表现是「本地模型直接崩」。
2. 把引擎做成 split APK / dynamic feature，运行时用 `PackageInstaller` 装一次。
   要用户过一次系统安装框，且签名、split 一致性都得维护。

IRIDIS 两条都没走。本项目同样不走，理由一致：收益（约 15MB 压缩后）不值得拿
「本地大模型的稳定性」去换。

## 这一轮真做了什么

把两张**纯数据**资产搬出安装包（它们不需要被 dlopen，只是文件）：

| 资产 | 原位置 | 现在 | 包体收益 |
|---|---|---|---|
| Alpine rootfs | `assets/containers/alpine.tar`（8.2MB，已入库） | `rootfs-alpine.zip`（gzip 后 3MB） | 约 3MB 压缩后 |
| Shizuku 安装包 | `assets/shizuku.apk`（2.5MB，CI 拉取） | `shizuku.zip` | 约 2.5MB |

### 代码位置

- **`core/.../model/`**：`ModelSpec` / `ModelDownloader` / `ModelZip` / `StorageReport`
  从 `app` 模块移到 `core`。理由是容器（core）也要用同一套下载器，而 core 不能反向依赖 app。
  包名不变（`com.beichen.polaris.model`），所以 app 侧 import 一行都不用改。
- `ModelSpec` 从「四套语音模型」扩成「六套可选内容」，`Kind` 加 `CONTAINER` / `TOOL`。
- `StorageReport.ofKind()` / `bytesOfKind()`：语音页只算 ASR+TTS，容器与 Shizuku 不混进去
  （否则用户会以为语音又偷偷多下了东西）。
- `RootfsManager`：
  - `archiveFile()` = `filesDir/rootfs/<id>/<assetName>`，与 `ModelSpec.RootfsAlpine` 同一定义。
  - `isDownloaded()` / `hasArchive()`：未下载时 `ensureExtracted` 明确返回 null，由界面给下载入口。
  - `listAvailable()` 改成「内置清单 + assets 扫描」：归档已不在 assets 里，
    照旧枚举会让 Alpine 从界面上消失，用户连下载入口都找不到。
  - `openRootfs()` 顺序是**先磁盘、后 assets**：反过来调试包里那份旧归档会永远盖住下载的新版。
- `ContainerScreen`：卡片三态（点击下载 / 点击解压 / 已就绪），下载带百分比；
  已解压的发行版列表下方有「删除」，同时清归档（避免「显示未下载但磁盘上还躺着 3MB」）。
- `ShizukuInstaller`：`NO_BUNDLED_APK` → `NEED_DOWNLOAD`，从
  `filesDir/tools/shizuku/shizuku.apk` 拷到 `cacheDir/shizuku/` 再走 FileProvider
  （FileProvider 只授权了 cacheDir 那条路径）。
- `PermissionFacade.downloadShizuku()`：下 2.5MB，下完提示「再点一次」。
  不做「下完自动拉安装器」——系统安装框本来就要确认一次，再叠几秒网络等待，用户会分不清。

### CI

- `Fetch Shizuku APK` 改为落到 `/tmp/optional/`，不再进 `assets`。
- `Publish voice model assets` 增发 `rootfs-alpine.zip`（`gzip -9` 后打包）与 `shizuku.zip`；
  清单 `model-manifest.txt` 动态收集实际存在的 zip（Shizuku 拉不到就跳过，不写清单，
  App 点安装会直接退官方页，而不是对着 404 猜）。
- 包体守卫新增：`assets/shizuku.apk` 或 `assets/containers` 存在即构建失败。
- `scripts/assets/containers/alpine.tar`：归档源留在仓库里（不进 APK），供 CI 打包。

### 门禁

- `run-offline-asr-verification.sh`：E1 覆盖六套；新增 **[G] 容器与 Shizuku** 六条
  （路径对齐 / 先磁盘后 assets / 未下载明确拒绝 / 不再从 assets 读 / 源码 assets 干净 / CI 发布）。
- `verify-apk-features.py`：W13 从「Shizuku 在包内」反转为「不在包内」，
  并断言下载器与安装器类仍在（搬资产 ≠ 删功能）。

## 包体账

| | 1.752 | 1.753 |
|---|---|---|
| 安装包 | 47.7MB | 约 42MB |
| 其中 lib/* | 25.1MB | 25.1MB（引擎，拆不掉） |
| 其中 dex | 14.0MB | 14.0MB |
| 其中 assets | 7.4MB | 约 1.7MB |

想再小只能动 `lib/*`（25MB）与 `dex`（14MB），两条路都在上面「为什么 .so 不能按需」里写过。
