# 云端构建验证：在 x86_64 服务器上把 146 条 harness 跑成全绿

> 2026-11-16 ｜ 一台 4 核 / 8GB 的 x86_64 云服务器 ｜ 结论：**PASS=146 SKIP=0 FAIL=0，GATE PASS 6/6**

这份记录解决一个具体问题：**没有真机、也没有模拟器的时候，这个仓库还能验到什么程度**。
答案是：除「必须真实设备」那一类（见 `DEVICE-VERIFICATION-PENDING.md`），**其余全部能验，且能验到与 CI 等价**。

### 唯一硬伤：`/dev/kvm` 是空壳

```
$ emulator -accel-check
accel: 12
Could not open /dev/kvm : No such device
```

CPU 有 `svm` 标志，但内核没加载 kvm 模块，`systemd-detect-virt` 返回 `kvm` —— **这台机器本身就是一台 KVM 虚拟机，宿主机没开嵌套虚拟化**。`/dev/kvm` 那个 `crw-rw-rw-` 节点是透传进来的空壳，权限 666 也打不开。

x86_64 的 Android 镜像强制要求硬件加速，绕不过去；ARM 镜像走 TCG 能起，但 4 核全指令翻译下 `system_server` 会被 watchdog 反复杀，没有验证价值。

## 3. 六轮：从 13 红到 0 红

| 轮次 | 条件 | PASS | SKIP | FAIL |
|---|---|---|---|---|
| 1 | 只有源码，无 AGP 产物 | 122 | 11 | **13** |
| 2 | `assembleDebug` 跑通（`-PnoNative=true`） | 144 | 1 | **1** |

| 4 | 修 STALE 后重跑 | 145 | 0 | **1** |
| 5 | 修 Vulkan 断言后重跑 | 145 | 0 | **1** |
| 6 | — | **146** | **0** | **0** ｜ GATE PASS |

### 第 1 轮那 13 个红：不是代码问题

这 13 个 harness 都用 `qa_classpath` 找 Gradle 产物。没有产物时它们退化成「只编译自己列出的源文件」，
于是跨文件的 `internal` 引用（`MdBlock`、`Ed25519`）报 `unresolved reference`——**看着像代码坏了**。

编一次就降到 1 个。

### 剩下的那 1 个：构建前置步骤缺失

```
llama.cpp 源码不在仓库（CMakeLists 明确要求先跑 scripts/fetch-llama.sh）
  → 只能 -PnoNative=true
  → 该开关把 jniLibs 里的 .so 全排掉
  → APK 只剩 2 个 .so
  → 离线识别 C3「打包的 .so 不含流式识别符号」红
```

而 C3 查的 `libsherpa-onnx-jni.so` 由 `scripts/qa/fetch-tts-assets.py` 放入 jniLibs，
CI 里是构建前的一步（`POLARIS_MODELS=0`，只装运行时、不下权重）。补上这一步，C3 转绿，离线识别 32/32。

## 4. 顺带修掉的三个守卫缺陷

这三个都不是「代码坏了」，而是**守卫自己会误报**——误报比漏报更贵，因为它教人忽略红灯。

### 4.1 STALE 检查扫到了第三方源码树

`qa_classes_stale` 用 `find app/src/main -name '*.kt' -newer <最新 class>` 判产物是否过期。
而 `app/src/main/cpp/llama.cpp` 是拉下来的第三方源码树，**里面有 `examples/llama.android` 的示例 `.kt`**，
它们从不参与本模块编译，但 `fetch-llama.sh` 会把 mtime 刷成最新。

后果：任何按 CI 顺序（先 fetch 再构建）且 Kotlin 走增量编译的机器，都会被判 `ENV STALE`，
而 gate 给的修法（`./gradlew compileDebugKotlin`）**根本修不掉它**——下次 fetch 又刷一遍。

改法：`find` 时 `-path "$src/cpp" -prune`。

### 4.2 Vulkan 产物断言缺少「本次构建是否开了 Vulkan」

CI 装了 glslc，`.so` 会链 `libvulkan.so`；本机没有 glslc，`CMakeLists` **刻意**静默降级成 CPU-only
（这是设计，Android Studio 里就该能编过）。此时断言「产物必须链 libvulkan」必然红，
而 FAIL 文案「GGML_VULKAN 开了但后端被链接器丢掉」会把排查引向链接器——**这台机器压根没有链接器可怪**。

改法：读 CMake 自己的 `CMakeCache.txt` 判 `GGML_VULKAN:BOOL`（**事实**），而不是仓库里写的 `set(... ON)`（**意图**）。
CI 上 Cache 是 ON 就照跑断言；若 CI 漏装 glslc，`AK_REQUIRE_VULKAN` 会让 CMake 当场 FATAL，走不到这一步。

反向验证（把 Cache 临时改成 ON）：4 条断言立刻回来 → 证明没有被永久关掉。

### 4.3 `unzip -l | grep -q` 在 pipefail 下假 SKIP（最隐蔽）

脚本开着 `set -uo pipefail`。`grep -q` 一命中就退出，`unzip` 吃 SIGPIPE，整条管道判非零：

```bash
if ! unzip -l "$APK" | grep -q "lib/arm64-v8a/"; then
    echo "  SKIP  APK 不含 arm64-v8a"     # ← 包明明含，却跳到 SKIP
```

于是「含 arm64 的包」被判定成「不含」，整段产物断言静默跳过，`SUMMARY` 变成 `FAIL=0`，
run-all 判 PASS —— **这就是第 3 轮绿、第 4 轮红的原因**：同一个包、同一台机器，差异只取决于
`grep` 是否抢在 `unzip` 写完之前退出。

改法：清单先落盘再 grep。全仓同类高危写法（`unzip|strings|nm|readelf|cat|find` 接 `| grep -q`）扫描后只剩这一处，其余 140 处左侧都是小输出，风险可忽略。

### 4.4 基线数字滞后

`harness-baseline.txt` 的注释从 143 段起一直在写，但末尾那行数字停在 `142`（卡了三天），
门禁 5 长期提示「PASS 高于基线」——提示多了就等于没提示。已对齐到 146。

## 5. 一条偶发，记录在案

`run-t01-probe2.sh` 的 R7「streamChat 取消窗口有界」在第 5 轮红了一次，失败信息是 `t.message = null`
（抛的是无消息的 `CancellationException`，不是断言失败）。同一轮没有改任何 Kotlin 代码。

核实：**独立连跑 3 次全过（7/7）**；第 6 轮全量也过。判定为时序抖动，非回归。
若以后反复出现，方向是给这条加一次重试或放宽 `delay(300)` 窗口，而不是改被测的取消链。

## 6. 可复现步骤

```bash
# 0. 前置（本机缺 pip 时先 apt install python3-requests）
export ANDROID_HOME=/data/home/android-sdk ANDROID_SDK_ROOT=$ANDROID_HOME

# 1. 两个「不进仓库」的依赖
./scripts/fetch-llama.sh git                            # llama.cpp v0.7.0，commit 校验
POLARIS_MODELS=0 python3 scripts/qa/fetch-tts-assets.py # 只装 sherpa 运行时 .so

# 2. 构建（不要加 -PnoNative，否则 jniLibs 会被排掉）
./gradlew :app:assembleDebug --no-daemon

# 3. 验
bash scripts/qa/run-all.sh app/build/outputs/apk/debug/app-debug.apk | tee /tmp/qa.log
bash scripts/qa/gate.sh /tmp/qa.log        # 期望 GATE PASS
```

第 3 步里会把 APK 路径传进去很重要：不传的话 `run-apk-verification` 与 Vulkan 产物段都会 SKIP。
