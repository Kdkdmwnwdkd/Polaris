# 真机验证：审批弹窗与消息 key（2026-11-11）

> 前几轮的所有结论都建立在「服务器能验的一律在服务器验掉」之上。这一轮换到真实设备
> （云端 x86_64 模拟器，API 30）跑同一批改动，两个缺陷立刻现形——都是**单元测试与
> JVM harness 结构上抓不到**的那一类：一个关于「界面此刻在哪个页面」，一个关于
> 「Compose 的 key 撞了会怎样」。

## 环境与手法

| | |
|---|---|
| 设备 | 云端模拟器 API 30 / x86_64，`-no-window -accel off -gpu swiftshader_indirect` |
| 模型 | 本机 mock 端点（`10.0.2.2:8899`），按触发词返回指定工具调用 |

| 操作 | `adb shell input tap` |

**一条被推翻的旧结论**：`docs/ops/DEVICE-VERIFICATION-PENDING.md` 记着「触摸设备被禁用，
`input tap` 完全不生效」。本轮实测**点击有效**（点开抽屉、进控制台、点审批按钮全部成功）。
旧结论至少在当前的 `-no-window + swiftshader` 配置下不成立——它的代价很大：过去几轮
所有验证都被迫绕开 UI，只能读日志推断「弹窗大概弹了」。这一条需要更正。

## 缺陷一（F16）：审批弹窗挂在「对话」页里

### 现象

在**控制台页**触发一次需要审批的工具调用，日志是这样：

```
07:29:28.667 tool.start  tool=device_notifications args={"packages":["com.android.shell"]}
07:29:58.689 WARN [Approval] device_notifications 拒绝
07:29:58.749 tool.end   code=approval_denied dur=30079ms      ← 正好 30 秒超时
```

同一时刻 `uiautomator dump` 的内容只有控制台页的文字，**没有任何弹窗**。用户视角是
「任务跑了一下，然后什么都没发生」；日志视角是「审批超时自动拒绝」。两个都对，
合起来才是完整缺陷：**闸门在，但看不见的闸门等于被自动关上**。

### 根因

`ApprovalDialog` 的挂载写在 `ChatScreen` 的组件树里：

```kotlin
// ChatScreen.kt（修前）
val request = pendingApproval
...
if (currentApproval != null) ApprovalDialog(request = currentApproval, ...)
```

只有「对话」这一页被组合时才渲染。而审批请求是**异步到达**的：

- 定时任务/通知入口触发的回合，用户可能停在上次用的任何页面；
- 冷启动时若 `guideSeen` 未落盘，`AppScaffold` 会主动把路由切到「权限引导」页
  ——**第一次用定时任务的用户，必然踩到这条**；
- 用户一边跑任务一边翻日志/设置，同样中招。

### 修法

挂载点搬到 `ApprovalHost`，由 `AgentKitApp` 在 `AppScaffold` **之外**调用：

```kotlin
AgentKitTheme(...) {
    AppScaffold(...)
    ApprovalHost(vm = vm)   // 与路由无关
}
```

审批是全局模态事件，不是某个页面的附属 UI。`ChatScreen` 里那段连同 `pendingApproval`
一起删掉（避免两处渲染 = 双弹窗、各自倒计时、点一次只回一个 `CompletableDeferred`）。

### 真机复验（同一台机器，覆盖安装）

停在**权限引导页**触发指名读取，弹窗正常出现：

```
确认执行危险操作
Agent 正在请求操控你的手机，执行后不可撤销。

device_notifications
{"packages":["com.android.shell"]}
来源：本次对话直接调用
☐ 本次会话不再询问读取通知（com.android.shell）
                    [拒绝]  [允许执行]
                     30 秒后自动拒绝
```

点「允许执行」→ `[Approval] device_notifications 允许` → `code=notifications_ok`。

## 缺陷二（F17）：工具调用 id 复用直接把对话页打崩

### 现象

修好 F16 后再触发，应用**崩溃**：

```
java.lang.IllegalArgumentException: Key "t:call_mock_1" was already used.
If you are using LazyColumn/Row please make sure you provide a unique key for each item.
    at androidx.compose.foundation.lazy.LazyListMeasuredItemProvider.getAndMeasure(...)
    at com.beichen.polaris.ui.ChatScreenKt...
```

mock 端点每次回同一个 `call_mock_1`，同一会话出现三次工具调用 → 三张卡同一个 key。

### 为什么不是「mock 的问题」

`uiKey` 的注释已经写过这个坑，但只兜住了一半：

```kotlin
is UiItem.Tool -> "t:" + call.id.ifEmpty { "@$index" }   // 只管空 id
```

**没管「非空但重复」**。而 id 不是本地产的——它从供应商回来：

- 中转站/兼容层常见固定 id；
- 本地 llama.cpp 自造 id，格式统一、容易撞；
- 重试与分支（reask）会把同一条 `tool_call` 复制成两份；
- 历史会话合并、导入也会。

后果不是渲染错乱，是**整个对话页崩掉**：用户连历史都打不开。

### 修法

唯一性是**整表**性质，就该由整表来保证：

```kotlin
fun List<UiItem>.uiKeySeq(): List<String> {
    val seen = HashSet<String>(size)
    return mapIndexed { index, item ->
        val key = item.uiKey(index)
        if (seen.add(key)) key else "$key@dup$index"
    }
}
```

- 首次出现**保持原样**（`t:<id>`）——稳定身份不变，滚动位置与展开态不丢；
- 重复出现追加 `@dup<下标>`——下标在同一张表内唯一，兜底成立。

`uiKey` 本身不动：它的语义（单条 → 一个 key）是对的，错的是「假设全局唯一」。

## 缺陷三（F18）：自己发的通知被自己读回

### 现象

验证 F15 时用**全量**模式读通知，返回四条，其中三条是 App 自己：

```json
{"package":"com.beichen.polaris","title":"Agent 正在执行","text":"notifyall"}
{"package":"com.beichen.polaris","title":"Agent 正在执行","text":"notify"}
{"package":"com.android.shell","title":"建行","text":"尾号1234账户支出500元"}
{"package":"com.beichen.polaris","title":"Agent 正在执行","text":"notify"}
```

两个后果：

1. **回环**：Agent 发通知 → 自己的监听器收下 → 被 `device_notifications` 读回 → 进模型
   上下文。不是外部泄漏，但它占掉「最近通知」的 12 个名额，把真正的用户通知挤出去。
2. **正文是用户输入**：那条通知的正文是定时任务的 `prompt` 原文
   （`WorkflowNotifier` 里 `setContentText(workflow.prompt.take(80))`）。锁屏默认展示
   通知内容（除非用户手动开「隐藏敏感内容」），于是「把工行卡余额截图发我」这类任务
   就挂在锁屏上。

### 修法

沿用 F11 的原则：**出口过滤要求每个出口都写对，入口拒绝只需一处**。

```kotlin
// NotificationIntake.kt（零依赖，可 JVM 验）
fun shouldIngest(packageName: String, selfPackage: String): Boolean {
    if (packageName.isBlank()) return false        // 来源不明
    if (selfPackage.isBlank()) return true         // 判据不完整时别把通知全吞掉
    return packageName != selfPackage              // 自己发的不收
}
```

```kotlin
// WorkflowNotifier.kt
.setContentText("点此开始执行")   // 原来是 workflow.prompt.take(80)
```

BigTextStyle 那个出口也一并去掉（只改 `setContentText` 的话，展开通知照样能看到全文）。

### 真机复验

同一操作（全量读），修前 4 条含 3 条自己的通知，修后：

```
共捕获 1 条通知（全部应用；按时间倒序）
{"package":"com.android.shell","title":"建行","text":"尾号1234账户支出500元"}
```

## 顺带证实的（上一轮 F11 / F15）

同一台设备、同一次会话，把 F11 与 F15 的判据各自落到真机上：

| 判据 | 实测 |
|---|---|
| F11 自动注入不含正文 | 请求里是 `- 最近通知：北辰（2 分钟前）`，投递的 `SECRET_NOTIF_BODY_9F3A` **一次都没出现** |
| F15 指名读只返回该应用 | `{"packages":["com.android.shell"]}` → `共捕获 1 条通知（来源限于 com.android.shell）` |
| F15 全量读返回全部 | `{}` → `共捕获 4 条通知（全部应用）`，含 3 条 `com.beichen.polaris` + 1 条 `com.android.shell` |
| F15 两档钩子文案确实不同 | 指名：「本次会话不再询问读取通知（com.android.shell）」；全量：「该操作每次都会单独确认」 |

同一个 Store、同一会话，指名 1 条 / 全量 4 条 —— **过滤不是只改了文案**。
