# 工作区外读取边界：让「沙箱」对 shell 也成立

**日期**：2026-11-10　**基线**：`071d4ac`
**对应审计遗留项**：容器（proot）/ 无线调试 / 无障碍三条高权限后端「无路径限制」

---

## 一、问题是什么

文件工具是有边界的：`read_file` / `write_file` 都走 `PathGuard`，`/etc/passwd` 与
`../..` 一律拒绝，越界写还带自动备份。但那道边界只对**文件工具**成立。

`shell_run` 里一条 `cat` 就整条绕过去了，三条通道都是：

| 通道 | 为什么能绕 |
|---|---|
| proot 容器 | `ProotRunner.prootOptions` 里有 `-b /sdcard`，把整块共享存储 bind 进容器，还带 `--root-id`（容器内 uid 0） |
| 无线调试 / Shizuku | uid 2000，`/sdcard` 与部分 `/data` 直接可读 |
| 本机 user shell | cwd 在 `filesDir`，但绝对路径畅通无阻 |

于是一条提示注入就够：`cat /sdcard/DCIM/Camera/*.jpg` 把相册读进上下文。
而**读本身拦不住**——Agent 的本职就是读文件，`read_file` 免审批正是这个意思；
真正的问题不是「它读了」，而是「读的是相册，用户没被问过」。

外发那一侧上一轮已经堵上（`http_request` 纳入审批，按域名记）；
这一轮补的是入口那一侧。

## 二、为什么判据放在审批层，不放在三个后端里

三个后端各写一份路径检查，等于同一把尺子抄三遍，且写错的概率与份数成正比。
更关键的是**后端不是用户能表达同意的地方**：proot 的启动参数里没有「用户同意读相册」
这一项，审批链才有。

所以判据落在 `ShellCommandRules`（纯函数）+ `ApprovalScope`（授权键）：

```
只读命令 ──┬─ 读的是工作区内的相对路径 → 不问（与修前一致）
           ├─ 读的是受保护目录的绝对路径 → 问一次，按**目录**记住
           └─ 其它只读 → 不问
写命令 / 重定向 / 包装器 / 命令替换 → 每次都问（F2 那一档，未变）
```

一处改动，四条通道同时生效——**这正是把边界定在审批层的收益**。

## 三、受保护的是哪些目录

```
/sdcard  /storage  /mnt/media_rw  /mnt/user  /mnt/runtime
/data/media  /data/data  /data/user  /data/misc  /data/system  /data/app
```

**只收用户数据**。`/proc`、`/sys`、`/system`、`/data/local/tmp` 一律不收：
读它们不泄露用户内容，收进来只会把「看一眼 CPU 型号」也变成弹窗，
最后又训练出闭眼点允许的习惯——那正是 F1/F2 两轮一直在还的债。

判定只看**只读段里的绝对路径**：

- 相对路径不触发。本机 cwd 是 `filesDir`、容器 cwd 是 `/root`，
  `cat ../../../sdcard/x` 这种写法到不了 `/sdcard`（跨挂载点，`..` 上不去）；
- 写命令不归这一档（`cp` / `rm` / `tee` 另有判据，且多半不可记忆）。

## 四、三个细节，每个都有反例在背后

**1. 先规范化再判定。**
`cat /sdcard/../data/data/x/y` 字面上在 `/sdcard` 下，实际读的是别的应用的私有目录。
若按字面量算键，用户同意的是「相册」，放行的却是「微信数据」。
所以 `..`、`.`、重复分隔符先折叠，再匹配前缀。

**2. 前缀必须带目录边界。**
`/sdcardevil/x.jpg` 字符串上以 `/sdcard` 开头，目录上跟 `/sdcard` 毫无关系——
和 `PathGuard` 里那条注释记的 `agent_workspace_evil` 是同一个坑。

**3. 同意粒度是「根 + 第一层子目录」。**
`/sdcard/DCIM/a.jpg` → 记住 `/sdcard/DCIM`；换到 `/sdcard/Download` 重问。

- 按**文件**记：统计一个下载目录要弹十几次窗，用户会闭眼点允许；
- 按**根**记：一次点击放行整个相册，授权的实际范围远大于字面意思（F1 的老毛病）；
- 折中的这一档，正好是「用户脑子里以为自己在同意的东西」。

## 五、不变量（写在 harness 里，改坏就红）

| 不变量 | 为什么 |
|---|---|
| 同意过 `shell` 组 ≠ 同意读相册 | 修前 `sessionAllowed` 只有 `shell` 一个键，用户为 `npm install` 勾一次，相册就永久敞开——这条就是 F7 本身 |
| 带重定向的读仍「每次都问」 | 否则 `echo x > /sdcard/a` 能复用「读 /sdcard/a」的授权，写入被洗白 |
| 提权身份优先于读档 | `identity=shizuku` 连 `ls` 都要问，读档不能把它降级成可记忆 |
| 换目录必须重问 | 代码顺序若被「优化」，最容易丢的就是这条 |

## 六、代价

- 读共享存储里的文件会多一次确认（**每个目录一次**，不是每次）；
- `/data/data` 下**包括本应用自己的目录**也会问一次——那里放着 `shared_prefs`，
  正是 API Key 所在，问一次是对的；
- 系统信息类命令（`getprop` / `ps` / `df`）不受影响，harness 里有回归断言盯着。

## 七、没有做的事

| 项 | 为什么 |
|---|---|
| 后端内部的路径隔离（chroot / 挂载收窄） | 会直接砍掉容器与宿主交换文件的能力（`-b /sdcard` 是刚需），且改的是启动参数，出错的代价是容器整个起不来。审批层已经拿到同样的收益，先不动 |
| 无障碍后端的路径限制 | 无障碍不是文件通道——它的能力面是「点屏幕」。那一条的风险在别处（点了什么），上一轮的 `identity` 分档与逐次确认已覆盖，不需要路径判据 |
| 读白名单（用户自定义允许目录） | 需要设置页 UI 与持久化，`ModelConfigScreen` 已冻结在 2469 行上限。当前「按目录记住」已经能覆盖高频路径 |
