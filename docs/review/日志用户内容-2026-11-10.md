# 审计 F12：日志里的用户内容会随诊断包外发

**日期**：2026-11-10
**范围**：`core/AgentLogger.kt`、`core/LogRedaction.kt`（新）、`ui/ChatViewModel.kt`、`browser/BrowserHost.kt`
**PR**：[#13 日志用户内容](https://github.com/Kdkdmwnwdkd/Polaris/pull/13)

---

## 一、缺陷

`AgentLogger` 是磁盘日志的唯一写入口。而「导出诊断包」会把日志尾部 300 行原样打包，
交给用户去发给开发者。所以：**日志里写了什么，用户求助时就会带出去什么。**

它本来有两道防线：

| 防线 | 做法 | 状态 |
|---|---|---|
| `sanitize()` | 正则掩码 `sk-` / `Bearer` / `token=` / `password=` | 有效 |
| `sensitiveTools` | 命中名单的工具，入参与结果**只记长度** | **手写 7 项，漏了大半** |

第二道的问题在于：**「哪个工具的入参与输出会带用户数据」这件事，`ToolCatalog` 已经用 `approval` 字段回答过一遍了。** 两张表各自维护，结果必然是静默不同步：

| 工具 | 为什么敏感 | 修前在名单里？ |
|---|---|---|
| `ocr_image` | 屏幕文字全文（F9b 刚认定与 `ui_screenshot` 同档） | ✗ |
| `shell_run` | 输出是**任意内容**：`cat` 出来的文件、`env` 打出来的环境变量 | ✗ |
| `shell_background` | 同上 | ✗ |
| `container_toolchain` | 同上 | ✗ |
| `write_file` / `edit_file` | 参数是文件内容的前 300 字符 | ✗ |
| `ui_tree` | 屏幕上的文字 | ✗ |

另外还有几处**绕过名单、直接往日志里写用户内容**：

```kotlin
AgentLogger.i("Chat", "用户发送：${text.take(120)}")                       // 用户打的字
AgentLogger.i("Chat", "用户拒绝了计划 $planId：${reason.take(80)}")          // 拒绝理由
AgentLogger.i("Chat", "用户回答了提问：${choice.take(80)}")                  // 弹窗自由输入
AgentLogger.i("Memory", "自动记住（...）：${c.content.take(80)}")            // 记忆正文
AgentLogger.d(TAG, "页面加载完成：${url?.take(120)}")                       // ?code= 授权码
```

最后一条尤其典型：OAuth 回调、分享链接、图床签名全都是 `?code=` / `?access_token=` 形态。
一条「页面加载完成」的 DEBUG 日志，足够把授权码带出本机。

## 二、这类缺陷的形态

它不报错、不崩溃、不拖慢。日志看起来完全正常，只是「多记了一点」。

没有人会在 code review 时说「这里不对劲」——`"用户发送：${text.take(120)}"` 读起来就是在记日志，
而且**是有意设计的**：排查问题时确实想知道用户发了什么。

唯一的后果发生在用户点「导出诊断包」求助的那一刻：**为了求救而泄露**。

## 三、修法

### 1. 白名单派生自真源

```kotlin
val sensitiveTools: Set<String> =
    ToolCatalog.tools.filter { it.approval != null }.map { it.name }.toSet() + EXTRA_SENSITIVE
```

`EXTRA_SENSITIVE` 只留 4 个（不需审批但输出仍不该落盘）：`read_file`、`device_foreground_app`、
`web_snapshot`、`web_eval`。

**派生为主、补充为辅**：前者会随真源长大，后者不会。

判据刻意选「需审批即脱敏」，不去逐个甄别「这个工具的输出敏不敏感」。代价是 `ui_tap` 的日志
会变成「结果已脱敏(长度=18)」，少了一点诊断信息；换来一条**没有例外可钻**的边界。
例外集一旦开口，下一个工具就会掉进去——这正是修前那张 7 项名单的死法。

### 2. 用户内容改成只记长度

```kotlin
AgentLogger.i("Chat", "用户发送 ${text.length} 字" + ...)
AgentLogger.i("Chat", "用户拒绝了计划 $planId（理由 ${reason.length} 字）")
AgentLogger.i("Chat", "用户回答了提问（${choice.length} 字）")
AgentLogger.i("Memory", "自动记住（${c.kind}，重要度 ${c.salience}，${c.content.length} 字）")
```

元数据（`kind` / `salience` / 长度 / 条数）全保留——那才是诊断要看的；正文去掉。

### 3. URL 脱敏

```kotlin
fun redactUrl(url: String): String = url.substringBefore('?').substringBefore('#')
```

保留 `scheme://host/path` 已足够回答「打开了哪个页面」。

### 4. 判据搬到零依赖文件

`AgentLogger` 自己不 import android，但它通过 `ConfigSanitizer → ModelConfig → SkillProtocol`
（后者 import `android.content.Context`）把 Android 拖进了整条编译链。于是「哪些字段该打码」
这个纯判断只能在设备上验证，CI 里只有一个 grep。

新建 `core/LogRedaction.kt` 承载判据（与 `ToolCatalog` 一样零依赖），`AgentLogger` 保留同名
转发方法，调用点一个都不用改。**能被行为验证的判据才是有判据。**

这与 F11 把 `DeviceContext` 从 `DeviceContextStore` 里搬出来是同一个动作：
把「决定什么能出去」的那一小段，从不编译不过的文件里摘出来。

## 四、不变量（写进 harness，改坏就红）

1. `ToolCatalog` 里每个 `approval != null` 的工具都算敏感（`A1`，数量由真源决定，写死会脆）；
2. 修前漏网的那 7 个工具逐个点名（`A2`）——只验「数量对上了」不够，派生逻辑被改成
   `take(1)` 之类的花招也能让 A1 绿；
3. 正常工具**不**被脱敏（`B1`：`calculator` / `web_search` / `ask_user` / `speak` / …）——
   反方向断言。只验「坏东西没了」的 harness 会奖励「全蒙上」；
4. 补充集里的名字必须真实存在于 `ToolCatalog`（`C1`）——手写名单最常见的错是拼错一个字母，
   而后果是**静默失效**；
5. 既有的凭据掩码仍有效（`D1`~`D6`）；
6. URL 脱敏保留主机与路径、不保留 query 值（`E1`~`E6c`）。

## 六、没做的事

1. **不改 `sanitize()` 的正则**：它能抓的是「长得像凭据的东西」，抓不了「这是用户的聊天内容」。
   两类问题形态不同，各用各的手段——正则管形态，名单管来源。
2. **不在导出时二次过滤**：又是「出口过滤 vs 不收集」的老问题。诊断导出已经做了 Key 替换
   （`W7` 钉住），但那是**已知字段**；用户内容没有固定形态，只能靠源头不写。
3. **不删 `Chat` 标签的日志**：`"用户发送 N 字"` 仍然有用——排查「模型没反应」时，
   先要确认消息到底发出去了没有。长度足够回答这个。
4. **`apiTrace` 的逻辑没动**：它记的是 Key 的指纹（长度 + 头尾各几位），不记全文，
   本身是对的；只是它在 `ConfigSanitizer` 那条链上，本地编不了，所以本轮的 harness
   不覆盖它。这是环境限制，不是判断。

## 七、两轮的共同点

F11 与 F12 修的是同一件事的两个面：

> **凡是自动发生的、用户看不见的数据流动，都不该携带内容。**

F11 是「通知正文自动进上下文」，F12 是「用户内容自动进磁盘日志」。
两次的修法也一样：不是「在出口加过滤」，而是**让那一层根本装不下**——
`NotificationSummary` 没有 content 字段，`sensitiveTools` 从真源派生而不是手写。

出口过滤的问题在于它要求「每个出口都写对」；不收集只要求「一处写对」。
前者是纪律，后者是结构。
