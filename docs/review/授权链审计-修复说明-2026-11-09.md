## 关键取舍

1. **没有把 shell 改成"每次都问"**。那会让 `npm install` 这类正常命令也每次弹窗，
   用户很快就会养成闭眼点允许的肌肉记忆——R-08 修这个问题的初衷会反弹回去。
   现在保留"可记忆"，但把可记忆范围从「除黑名单外的一切」缩成「只读命令 + 构建/查询白名单」。
2. **网络按域名记忆**，不是每次必问。正常查资料只在首次访问某域名时问一次；
   把数据发去一个新域名必须过一次人——这正好卡住外泄链的关键一步（攻击者域名是新域）。
3. **提权命令不看命令内容**。`ls` 换了 uid 2000 能看的东西完全不同，权限才是风险变量。
4. **MCP 一律不可记忆**。外部服务器提供的工具，用户没法评估"这一类操作"的边界。

| D | 22 | 包装器（`busybox`/`toybox`/`env`/`nohup`/`timeout`/`xargs`/`eval`/`command`）、命令替换（`$()`/反引号）、重定向、`cp`、解释器（`python -c`/`node -e`/`sed -i`/`awk`）、`tree -o`/`sort -o` 一律不可记忆；反向确认 16 条日常命令仍可记忆；「记住 `npm install` 之后 D 组一条都不放行」 |

选择「加在既有 R08 里」而不是新建 `run-*.sh` 的原因：这 38 条验的是**同一个不变量**
（一次授权的作用域），拆成新 harness 会让 R-08 的判据分散在两处，而 R-08 的教训正是
「判据散在多个地方，改一处漏一处」。代价是该 runner 单次耗时略增（仍是一次编译）。

## 行为变化：技能脚本不再能直接外发 HTTP

`http_request` 声明 `needsApproval = true` 之后，`SkillExecutor.invoke` 的第三道门
（「需要人工确认的工具，脚本不得代调用」，`SkillExecutor.kt:347`）对它也生效了。
也就是说 `agent.http(...)` 现在会返回 `script_approval_denied`，而不是真的发请求。

这不是遗漏，是这条设计的必然结果：脚本跑在 Rhino 的非挂起线程里，审批是 suspend 的，
脚本内弹窗只能靠 `runBlocking`，用户不点就永久占线程、`SCRIPT_TIMEOUT` 也中断不了。
所以「脚本不得代弹审批」只能是拒绝。

影响面已核实：内置的 `weather` 是 **prompt 形态**（无 `entry`），它由模型在主对话里
直接调 `http_request`，走正常审批，不受影响；`wordcount` 只在注释里提到 `agent.http`。
当前没有任何 packaged 脚本技能依赖这条通道。

代价与后续：第三方脚本技能若确实需要网络，正确做法是在 manifest 的 `permissions`
里声明域名白名单（`"network": ["api.example.com"]`），由 `SkillExecutor` 按域名放行、
不弹窗；这需要新增一层「技能级域名约束」，本次未做——在做出那层之前，
**拒绝**比「静默允许脚本把任意内容发到任意地址」更符合当前证据。
