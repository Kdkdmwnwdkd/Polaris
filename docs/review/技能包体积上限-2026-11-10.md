# 技能包体积上限：同一个动作，两条入口两套规矩（W-57）

> 市场下载有 8MB 上限、20 秒读超时、60 秒整通上限；本地导入是 `readBytes()`，什么都没有。

**基线**：`d495601`（main，PR #10 合并后）
**对应问题**：本地 zip 导入（URL / SAF）没有体积上限，`OutOfMemoryError` 直接把 App 崩掉

## 一、问题

技能包有三个入口，其中两个是**直接读流**：

```kotlin
// 从 URL 导入
val bytes = URL(url).openStream().use { it.readBytes() }

// 从本机选择文件（SAF）
val bytes = app.contentResolver.openInputStream(uri)?.use { it.readBytes() }
```

`readBytes()` 会把整份内容铺进内存，没有任何上限。而：

- `OutOfMemoryError` 是 **Error 不是 Exception**，`runCatching` 抓不住 ——
  这条缺陷的表现不是「导入失败：内存不足」，是**进程没了**；
- 分块传输与 `content://` 常常**没有 `Content-Length`**，所以「先看长度」这条判据
  在这两条路上根本不成立，只能边读边计数；
- `URL.openStream()` 没有超时，也没有长度预判，而且**绕开统一 HTTP 客户端**
  （`run-http-client-single-source` 这条既有约定）——同一个 App 里两套网络规矩。

对比市场那条路（`MarketClient`）已有的三道限制：

| 限制 | 市场 | 本地导入（修前） |
|---|---|---|
| 协议白名单（只允许 http/https） | 有 | 无（`URL` 支持任意 scheme，含 `file:`） |
| 体积上限（8MB，先看 header 再边读边计数） | 有 | **无** |
| 超时（20s 读 / 60s 整通） | 有 | **无** |

同一个动作（取一个 zip 交给 `installZip`），两条入口两套规矩。这和上一轮 F9b
是同一族形态：**判据写在一处，另一条路没走它**。

## 二、做法

### 2.1 一个受限读取器，三处共用

新增 `core/skill/SkillPackage.kt`（纯 `java.io`，不拖 Android，可独立编译）：

```kotlin
object SkillPackage {
    const val MAX_ZIP_BYTES: Int = 8 * 1024 * 1024

    /** 边读边计数，超限立刻中止（不是读完再检查——那时内存已经吃满了）。 */
    fun readCapped(input: InputStream, what: String, limit: Int = MAX_ZIP_BYTES): ByteArray

    /** 已知大小时（Content-Length / File.length / 内存里的数组）的预判。 */
    fun requireWithin(declared: Long, what: String, limit: Int = MAX_ZIP_BYTES)
}
```

两条判据都要，不能只留一条：

- 只做预判 → 分块传输没有长度，声称 1KB 也能吐 1GB；
- 只做边读边计数 → 大包会先被完整下载一遍才被拒，白耗流量与时间。

### 2.2 URL 入口改走市场客户端

`MarketClient.fetchPackage(url)`：先过 `MarketRules.validHttpUrl`（协议白名单），
再用同一条 `getBytes(url, MAX_PACKAGE_BYTES)`（8MB + 20s/60s）。不新开客户端，
是尊重「统一 HTTP 出口」这条既有约定——谁开第二条路，谁就绕过了那三道限制。

不复用 `downloadPlugin`：那条要对索引声明的 `sha256` 校验，用户手输的地址没有哈希可对。

### 2.3 兜底放在落盘口，不放在入口

`installZip` 是唯一会真正解压落盘的地方，体积判据也放在这里：

```kotlin
SkillPackage.requireWithin(zipBytes.size.toLong(), "技能包")
```

将来多一个入口（分享 Intent、MCP 拉包、深链）忘了加流式上限，也不会一路走进解压循环。
这和审批闸门放在 `ToolExecutor`（而不是每个工具自己判断）是同一个思路：**纵深防御要落在
绕不过去的那一层**。

顺带的好处：`ChatViewModel` 是行数冻结文件，兜底放仓库而不是放 VM，一行都不用加。

## 三、不变量（写进 harness，改坏就红）

1. 等于上限放行、超一字节中止（边界不能提前一格，也不能晚一格）；
2. 分块流不带长度也必须能截住；
3. `readCapped` 不关闭调用方的流（二层 `use` 会二次关闭）；
4. `requireWithin(-1)` 不预判失败（未知长度不是「超限」）；
5. `SkillPackage.MAX_ZIP_BYTES == MarketRules.MAX_PACKAGE_BYTES`；
6. `installZip` 里有兜底、`fetchPackage` 先过协议白名单、VM 里不再有裸 `readBytes()`。

## 四、验证

| 项 | 结果 |
|---|---|
| 新增 runner | `run-skill-package-limit-verification.sh`（13 行为 + 6 接线） |
| 变异 ①：把上限判断放宽一倍 | A2/D1 变红，退出码 1 |
| 变异 ②：删掉 `installZip` 兜底 + 跳过协议白名单 | W4/W5 变红，退出码 1 |
| 变异 ③：上限改成 4MB | C1 变红，退出码 1 |

| harness 基线 | 130 → 131 |
| 文本断言 | 1729 → 1729 |

`ChatViewModel.kt` 仍是 3588 行（冻结上限 3588）：URL 入口少 4 行、SAF 入口持平、
import 增删相抵，兜底判据搬进了仓库。

## 五、没做的

1. **URL 入口不加「先问一句」的确认**：用户自己输入的地址，装之前还会看到技能卡上的
   声明行；再加一层弹窗属于流程噪音。
2. **不做断点续传**：8MB 上限下没必要，弱网重试一次的成本低于维护续传逻辑。
3. **`contentResolver` 的 `openInputStream` 仍可能抛非 `IOException`**（个别 ROM 的
   `SecurityException`）：VM 里的 `runCatching` 会接住并显示「导入失败」，不属于本轮范围。
