## 一、七条缺陷

### 4.1 会话截断静默丢数据（中）

**问题**：单会话超过 200 轮时删最旧轮，`appendMessage` 返回 `Unit`，界面无从得知；
常量名 `MAX_MESSAGES` 与实际作用对象（轮）不符。

**修法**：

| 改动 | 位置 |
|---|---|
| `MAX_MESSAGES` → `MAX_TURNS`，公开并改正注释 | `core/ConversationStore.kt` |
| `appendToTurns` 返回 `(turns, dropped)`；`appendMessage` 返回丢弃轮数 | 同上 |
| 丢弃量回传宿主，由宿主记 warn 日志并出提示 | `ui/ChatViewModel.kt` |
| 新增 `onHistoryTruncated` 回调（默认空实现） | `ui/ConversationProjection.kt` |
| 接到已有的 `truncationNotice` 流，复用截断 banner | `ui/ChatViewModel.kt` |

**没做**：阈值仍是 200。问题从来不是「有上限」，而是「删了不说」。文案里的数字
直接引用 `ConversationStore.MAX_TURNS`，不在界面另写一个 200。

**为什么日志不在存储层**：`ConversationStore` 被 r06 / r10 以「逐个列源文件、纯 JVM
自编译」的方式测，引入 `AgentLogger` 会连带拉进一套日志设施，破坏「零依赖可跑」
这个前提——第一轮 CI 就是这么红的。丢弃量已经通过返回值给出，记日志是宿主的事。

### 4.2 超时判定用墙钟（中）

**问题**：6 文件 9 处（实际清点后是 7 文件 18 处）用 `System.currentTimeMillis()` 做
截止时间。时钟回拨 → `JobRunner` 与 `LocalLlamaClient` 的轮询永不退出（这两处没有
外层 `withTimeout` 兜底）；时钟前跳 → `BuildEngine` 的 40 分钟等待立刻误报超时。

**修法**：新增 `core/time/Monotonic.kt`，`System.nanoTime() / 1_000_000` 派生，
零 Android 依赖、可在纯 JVM 里注入假时钟。替换范围：

- `core/job/JobRunner.kt`（任务运行时轮询）
- `core/llm/local/LocalLlamaClient.kt`（重试生成 join 循环）
- `skill/SkillExecutor.kt`（脚本指令看门狗 + 截止）
- `core/build/BuildEngine.kt`（CI 轮询超时）
- `automation/AgentAccessibilityService.kt`（窗口稳定等待 + `lastWindowSwitchAt` 写点）
- `automation/shizuku/ShizukuShell.kt`（exec 的 started/deadline/elapsed）
- `ui/ChatScreen.kt`（审批倒计时）

成对时间戳一并换源，避免两种时钟相减。`lastWindowSwitchAt` 的初值仍是 `0` 作哨兵，
但**读取处**显式映射成 `Long.MAX_VALUE`：

```kotlin
elapsedSinceSwitchMs = if (lastWindowSwitchAt == 0L) Long.MAX_VALUE
                      else Monotonic.nowMs() - lastWindowSwitchAt
```

不能把初值直接写成 `Long.MAX_VALUE`：`nanoTime` 起点任意，`now - MAX_VALUE` 会下溢成
一个大正数（或被当成"很久以前"），两种错法都比哨兵判断更难查。

**为什么不用 `SystemClock.elapsedRealtime`**（报告 4.2 的原建议）：那是 Android API，
`System.nanoTime` 在 Android 上映射的 `CLOCK_MONOTONIC` 与它只差"是否计入休眠"。
选 `nanoTime` 有两个硬理由：① `:core` 不能引 `android.*`，而 `JobRunner` /
`LocalLlamaClient` / `SkillExecutor` / `BuildEngine` 全在 `:core`，用 `elapsedRealtime`
就得在每个调用点做平台分叉，或者把时钟源抽象成接口再注入——两样都比现在这行重；
② harness 要在纯 JVM 上跑，`nanoTime` 到处都有。

语义上这也是**刻意**的："休眠不计时"意味着用户放下手机一晚上，后台任务不会因为
"过了 8 小时"被判超时；反过来，`elapsedRealtime` 会让审批倒计时在息屏期间继续走，
用户点亮屏幕时闸门已经落下。真要改成"休眠也计时"，改 `Monotonic.DEFAULT` 一行即可，
调用点一处不用动。

**没做**：纯耗时统计（`elapsedMs`、日志时间）、租约空闲判定、工作流持久化时间保持墙钟。
前三者只是展示，后两者要与存盘值/跨进程值比较，换源反而错。

### 4.3 草稿缓冲 O(n²)（低，性能）

**问题**：`draftBuffer = (draftBuffer ?: "") + delta`，每段增量复制已有全文。

**修法**：缓冲改 `StringBuilder`（摊还 O(1)），对外仍投影为 `String`。

**二轮修正（交付前自审发现）**：第一版只给 `appendText` / `appendReasoning` /
`takeDraft` 加了 `draftLock`，但 `start()` 的重置、`finish()` 的清空、`syncDisplay()`
的读取都在锁外——**不参与同一把锁的写点等于没被保护**。两处实际后果：

1. `StringBuilder` 不是线程安全的。流式读取在 IO 线程 `append`，收尾在协程 `finally`
   里置 `null`，两者交错时有把内部数组写坏的可能；
2. 普通字段没有可见性保证。`start()` 在主线程为 regenerate 置了一个空缓冲，IO 线程的
   `appendText` 可能仍读到 `null`，于是另建一个 StringBuilder 把增量写进野对象——
   症状是「重做时占位气泡一直不出字」，而日志一切正常。

现在字段的全部 14 个读写点都在 `draftLock` 内（`grep` 可核）。锁内只做字符串投影与
StateFlow 赋值，不调宿主代码，不会与 Compose 侧的收集构成锁序问题。

**没做**：`StateFlow<String>` 的逐 token 投影仍在——每次增量仍要生成一个新 String
给 Compose。要再省得把 UI 侧改成「版本号 + 共享缓冲」并做帧级节流，那是界面层的
独立改动，不在本次范围。本次只解决报告点名的那行拼接。

### 4.4 Shizuku 探测跑在主线程（低）

**问题**：`refreshShizukuStatus()` 在调用线程同步做两次 binder IPC + 一次
PackageManager 查询，而调用方全在主线程（权限页 LaunchedEffect、Shizuku 的
Binder 收到/断开回调、授权结果回调）。

**修法**：`scope.launch` + `withContext(IO)` 探测，结果回主线程写三条 StateFlow。
新探测会取消旧的（避免慢探测后到覆盖新结果）。能力链重算用**按次传入**的
`afterProbe` 回调——这既保证「探测之后才算」，也避开 1.607 踩过的递归类型推断
（facade 持有宿主 lambda ↔ 宿主读 facade 属性）。

**没做**：`reprobeShizukuStatus()` 保持同步（唯一调用点在工具执行链的 IO 线程上），
补了注释写明线程前提。

### 4.5 空响应体 NPE（低）

**问题**：6 处 `body!!.string()` / `body!!.source()`，2xx 但无 body 时抛 NPE，
上层 `catch (IOException)` 抓不到，文案退化成「请求失败：null」。

**修法**：显式判空并抛 `LlmHttpException(code, "xx 响应体为空（HTTP n）", "")`。
文案带状态码，能与网络错误、限流区分；仍是 `IOException` 子类，既有重试/脱敏链路不变。
Claude 的 `null` 保留给「400 缓存被拒 → 降级重发」这个专用语义，不被空体污染。

### 4.6 catch Throwable 吞取消（低）

**问题**：`refreshGrants` 里两处 `catch (_: Throwable) { false }`，把
`CancellationException` 与 `Error` 都当成「没权限」。

**修法**：先重抛 `CancellationException`，兜底收窄到 `Exception`。

### 4.7 无障碍点击的空断言（低）

**问题**：两处 `result.clickIndex ?: result.matchIndex!!` 依赖「matched 蕴含 matchIndex
非空」，破掉就抛 NPE，被外层 `catch (Exception)` 折成 `false`。

**修法**：显式判空，各写一条带策略与候选数的日志。「没命中」与「命中但下标丢了」
从此在日志里能分开。

## 二、三项工程债

### 版本目录

新增 `gradle/libs.versions.toml`，收口五个被 `:core` / `:app` 共用的坐标
（core-ktx / coroutines / serialization-json / okhttp / rhino）。判据是「第二个模块要用它」，
Compose BOM / WorkManager / Shizuku / ML Kit 仍留在 app 脚本里。

### 行为测试

三个纯函数里 `UiNodeMatcher` 已有 Hotfix3 的行为断言（归一化/包含/前缀/多命中/上溯/候选），
本次补另外两个：

- **BackupArchive**（W26，4 条）：非白名单成员被忽略、版本过新被拒、条数不符被拒、
  缺 `conversations` 成员被拒。这些包 `create()` 造不出来，用手工拼 ZIP 构造——
  用 `create` 造等于拿被测函数验证自己。
- **ConversationStore**（Branch，1 条）：恰好 `MAX_TURNS` 轮不丢、超一轮丢一轮且返回 1、
  丢完仍是上限且丢的是最早那条。

全部是行为断言（真调被测函数），不占文本断言额度，census 仍是 1368 条 / 53 文件。

### 没做的

真正的 JVM 单测源集（`src/test` + JUnit）没建。现有 harness 机制已经能在纯 JVM 上
跑纯函数（`kotlinc` + `java`），再引入一套测试框架会增加 CI 依赖与构建复杂度，
收益要等「需要 mock Android 依赖」时才兑现。等 `:core` 里那些依赖 `android.*`
的文件被拆成纯逻辑 + 适配层之后再考虑。

## 三、顺带修掉的两处

1. **`.gitignore` 的例外路径失效**（3.5 拆模块遗留）。`core/build` 是源码包，
   例外规则还写着 `app/src/main/...`，搬迁后不再命中——已追踪文件不受影响，
   但该目录下新增文件会被静默忽略，`git add` 整目录还会被拒。已补 `core/src/main/...` 一条。
   这个问题在本次改 `BuildEngine.kt` 时当场撞上。

2. **`Monotonic` 未登记 AppGraph**。AppGraph 的双向对账抓出「源码里带可变成员的 object
   全部已登记」不成立。补 `reset()` + 清单登记，期望条数 22 → 23。
   这正是清单存在的意义：新增通道不会被静默放过。

1. **超时行为**：后台任务、脚本看门狗、CI 轮询、审批倒计时的时长是否与改前一致
   （单调时钟在设备休眠期间会暂停，"休眠不计时"是刻意的）。
2. **Shizuku 权限页**：进入页面后状态会晚一帧出现（异步探测），从 Shizuku 授权返回后
   是否仍能正确翻成「就绪」。

4. **备份恢复**：正常备份件仍能往返（W26 happy path 未变）。
5. **LLM 请求**：正常响应不受影响；空响应现在报「响应体为空（HTTP 200）」而不是 NPE。
