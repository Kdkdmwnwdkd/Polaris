# 备份件不含密钥：导出脱敏 + 恢复回填

**日期**：2026-11-10　**基线**：`a8a08da`
**对应审计项**：F6 第二条（备份包含明文 Key）

---

## 一、问题

备份是个 ZIP，用户存网盘、发微信、拷电脑——这正是导出功能存在的意义，也是它危险的地方。

W-47 已经因为同一个理由把 GitHub PAT 剔出了备份包，注释写得很直白：

> 备份件常被存到网盘/微信，明文 token 外流等于送出仓库读写权限。

但同一句话对 API Key 一样成立，而这三处一直是原样写进去的：

| 位置 | 内容 | 后果 |
|---|---|---|
| `profilesJson` | 每个档案的 `config.apiKey`（含 `customHeaders` 里的 `X-Api-Key`、`customBody` 里的 `api_key`） | 别人拿到包可以直接刷额度 |
| `mediaKeys` | 各 provider 的媒体 Key | 同上（出图/出视频更贵） |
| `keyPoolJson` | 备用 Key 池的全部槽位 Key | 同上，且是「一整套」 |

顺带说明：系统级备份（`adb backup` / 云备份）是关的（`android:allowBackup="false"`），
所以泄露面只有 App 内的这个导出功能——这也是它值得先修的原因，范围清楚、判据可测。

## 二、做法

新增 `core/BackupRedaction`（纯 Kotlin + kotlinx-serialization，零 Android 依赖）。

**导出**：清空所有密钥字段，保留结构与名字。

| 字段 | 导出后 | 为什么保留外壳 |
|---|---|---|
| `config.apiKey` | `""` | 档案本身（地址/模型/名字）仍要能恢复 |
| `config.customHeaders` 中头名含 `key`/`token`/`auth`/`secret`/`cookie`/`signature` 的值 | `""` | `HTTP-Referer`、`X-Title` 这类正常头不能被误伤，所以按**头名**判，不按位置 |
| `config.customBody` 顶层敏感键 | `""` | 有的中转站用 `{"api_key":"..."}` 而不是请求头 |
| `mediaKeys` 的值 | `""` | 保留 provider 键集合，恢复侧据此知道「备份里有哪些」 |
| `keyPool` 每个槽位的 `key` | `""` | 保留 `id`/`label`，用户恢复后看得到自己配过几个、叫什么 |

**恢复**：以**本机现值**为基底合并，而不是用包里的空值覆盖。

| 场景 | 结果 |
|---|---|
| 同设备（档案 id 相同） | 沿用本机 Key，地址/模型等结构性字段按备份更新 |
| 跨设备（id 全不同） | Key 保持空，用户重填（id 是随机 UUID，无从匹配） |
| 老备份件（包里带非空 Key） | 照旧覆盖——升级不该让老备份失效 |
| 包解析不出来 | 保留本机原值，不清空（fail-safe） |

**导出脱敏的方向相反，是 fail-closed**：包解析不出来时写空串，宁可这次备份没有配置，
也不把可能含密钥的原文写进包。两个方向都写在 `BackupRedaction` 的类注释里，
因为它们看起来对称、实际上必须不对称。

## 三、代价

**跨设备恢复要重填 Key。** 这是这次唯一的用户可见损失。导出结果文案已改为：

> 已导出 N 个会话、M 条记忆、K 条提示词（API Key 不随备份导出，恢复后需重新填写）

替代方案是「加密备份 + 用户设口令」，但那要新增口令 UI、口令强度校验、忘记口令的善后，
且会让「一键备份」变成「先想个密码」——收益（省一次粘贴）不值这个复杂度。以后有需要再说。

## 四、边界（已知未覆盖）

1. **请求体只清顶层**。`{"extra":{"api_key":"..."}}` 这种嵌套结构清不到——递归清空会把
   `{"messages":[{"content":"..."}]}` 这类正常载荷一起破坏。猜不到就留原文，这一点写进了
   `redactBody` 的 KDoc，不藏在代码里。
2. **对话内容不脱敏**。用户自己把 Key 贴进聊天记录，那是用户内容，备份照旧保存；
   要处理得先做消息级敏感信息识别，属于另一个课题。
3. **`ConfigStore` 仍明文存 Key**（审计 F6 第一条）。项目已在类注释里决定不加密
   （App 私有目录 + 「加密无法防御 root 设备」）。`allowBackup="false"` 已堵住系统备份；
   剩下的最大面就是本文这个导出包，现已处理。真要动存储层，得先决定是否引入
   `androidx.security:security-crypto`——与「零新增依赖」的立场冲突，留给项目决策。

## 五、验证

`run-backup-redaction-verification.sh`：**31 条**（26 行为 + 5 接线），沙箱与 CI 都真跑。

- **[A] 档案脱敏 5 条**：Key 清空且其余字段原样、敏感头按名清空（`X-Api-Key`/`api-key`/
  `Authorization` 清，`HTTP-Referer`/`X-Title` 留）、畸形输入返回空串（fail-closed）、
  老备份缺字段不崩、空列表仍是合法数组
- **[B] 档案合并 9 条**：同 id 继承、老包非空值照旧覆盖、跨设备保持空、本机也没有 Key、
  坏包不清空本机、本机坏 JSON 时备份原样、多档案按 id 各自继承不串号、
  敏感头回填、包头值不被本机顶掉
- **[C] 媒体 Key 4 条**：值全空键集合不变、空值继承非空保留、备份没提的 provider 不被补进来、
  本机无对应 provider 时空值保持空
- **[D] 备用 Key 池 5 条**：脱敏保留 id/label、同 id 继承、id 不同保持空、畸形不清空、
  老包非空值保留
- **[E] 自定义请求体 3 条**：顶层敏感键清空而普通键保留、非 JSON 不改、恢复时按同名键回填
- **[G] 接线 5 条**：导出三处都脱敏、恢复以本机现值为基底、提示告知、无「原样写进备份」的残留

反向变异两组，都真跑了：

| 变异 | 结果 | 说明 |
|---|---|---|
| `redactProfiles` 不再清空 Key（直接返回原对象） | **A1 / A2 / A4 / E1 四条红** | 四个方向（档案 Key、敏感头、老包缺字段、请求体）各自有独立断言，不靠一条兜底 |
| `mergeProfiles` 的「空值才回填」改成「总是回填」 | **只有 B2 红** | 靶向精确：老包带来的非空 Key 会被本机值顶掉，这正是「升级让老备份变废」的那条 |
