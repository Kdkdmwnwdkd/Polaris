## 0. 一页速览

### 0.1 三句话判断

**第一，v2 的 A 级业务缺陷确实修掉了一大半，而且修法普遍比"打补丁"高一档。**
`ShellCommandRules` 不再是"只看首词"——它处理 `find -delete`、`sort -o`、`uniq a b`（第二参数是输出）、
`$(...)`、反引号、进程替换，并单独回答"只读但绕过工作区沙箱"这一类（`ShellCommandRules.kt:19-40`）✔；
审批通道缺失时**拒绝而不是放行**（`ToolExecutor.kt:358-372` 的 `no_approver`）✔；
MCP 前缀恒不可记忆（`ApprovalScope.kt:131-134`）✔；路径前缀越界补了分隔符（`PathGuard.kt:27-30`）✔；
取消语义落到三态（`ToolExecutor.kt:622-650`）✔；语音回落链是**纯函数 + 四条不变量**（`VoicePlan.kt:45-67`）✔。
这一批改动的共同特征：把判断从"散在各处的 if"收成"一个可被 harness 真跑的纯函数"。

**第二，但守卫体系现在有两条轨，安全性质落空。**
11-13 那一轮新建了 `ToolGuardChain`——`GuardDecision` 只有 `Abstain` / `Deny`，没有 `Allow`，
理由是"守卫只能收窄可执行集合"（`ToolGuard.kt:26-40`，这段推理本身是项目里最好的一段设计说明）✔。
**但它在生产上是空的**：

| 事实 | 证据 |
|---|---|
| 全仓没有任何 `ToolGuard` 的实现类（只有接口与链本身） | `grep ": ToolGuard"` 只命中接口声明与 `ToolGuardChain` ✔ |
| `productionSeams` 零调用方，只出现在注释里 | `SeamDeny.kt:48` 定义，全仓无调用 ✔ |
| 三处 `RealAgentLoop(...)` 都不传 `seams`，默认 `AgentSeams.NONE` | `RealAgentLoop.kt:208`、`ChatViewModel.kt:2000`、`PetAgentSession.kt:104`、`SubAgentRunner.kt:97` ✔ |
| 生产上真正被咨询的守卫是 `FailureGuard`，它**有** `GuardVerdict.Allow` | `FailureGuard.kt:30-32`、`ToolExecutor.kt:342-353` ✔ |
| 技能脚本直接调 `executor.execute`，不经 `executeOne`，因此任何 loop 层守卫都看不到 | `SkillExecutor.kt:452` ✔（○ 后果） |

也就是说：**"守卫不许有 Allow"这条性质，今天保护的是一个没有守卫的链**；而真正在拦东西的那条链，
恰好是有 `Allow` 的那条。这不是实现疏漏，是"接缝落地了、接线没做"。

**第三，新长出来的系统性问题是"装配与状态没有归属"，语音替换把它放大了一倍。**
v2 的头号病是"同一事实多个真源"。这个病**部分治好了**（审批、取消、MCP、路径），
但换成了两个同构的新病：

| 新病 | 证据 | 后果 |
|---|---|---|
| 装配没有唯一实现 | `RealAgentLoop` 三个构造点，桌宠那份硬编码 4 个只读工具、自己读配置、自己造 client，并明确拒绝本地模型（`PetAgentSession.kt:94-118,168-186`） | 能力已经分叉，下一处分叉没人拦 |
| 状态没有归属（第五轴） | 模型就绪态（磁盘）+ 引擎 handle（进程）+ 麦克风租约（瞬时）三者无主；`AppGraph` 只是 28 个单例的清单（`AppGraph.kt:32-58`） | 语音的两条后门（§4.5）：`ChatScreen.kt:252` 自建 `TtsController`、`VoiceRecorder.kt:53` 直接 `AudioRecord`，都绕过仲裁 |

## 1. 约束与事实基线

| 约束 | 事实依据 | 强制影响 |
|---|---|---|
| 单 APK、单进程、无 root | `AndroidManifest.xml`，无多进程声明 | 后台能力只能靠前台服务 / 无障碍 / Shizuku |

### 1.3 依赖台账已经和现实脱节

`DEPENDENCIES.md:9-12` 的结论是：本地推理**只有一条技术栈**（GGUF + llama.cpp），"没有 ONNX Runtime"，
`.so` 只有 `libagentkit-llama.so` / `libagentkit-termux.so` / `libproot.so` 三个，最后核对停在 **1.441（10-28）**。
11-15 之后不成立了：新增 sherpa-onnx 官方 android 运行时（含 `libsherpa-onnx-jni.so`、`libonnxruntime.so`），
ASR 与两套 TTS 全压在它上面，`run-offline-asr-verification.sh:27` 已经在断言这个符号。

这不是文档洁癖。台账是许可与安全评审的输入：一套没登记的 native 栈，意味着没人评估过它的 CVE 面、
ABI 兼容与体积，而它恰恰持有麦克风与音频输出。

### 2.2 边界审计

**成立（沿用，不要重造）**

| 接缝 | 证据 | 为什么值钱 |

| `TerminalSessionPool` ↔ `TerminalBackend` | 池只认接口，四后端独立 | 执行后端可替换 |

## 4. 关键运行链路

### 4.1 一轮对话（成立，不要动）

```
send() → runTurn(turnId, scope)
  ├─ 装配：SystemMessage(FROZEN/SESSION/TURN) + priorMessages + UserMessage
  ├─ 每步重算暴露面（seed file → 强制 pin → 滞回淘汰）
  ├─ 请求视图裁剪：保最近 N 张图 → 按"完整步"整组丢
  ├─ chatOnce → 流式增量只进回调，Completed 整条入历史
  ├─ executeBatch：含写整批串行；只读 chunked(5) 并行且保序
  └─ 取消：每步 ensureActive；NonCancellable 内闭合在飞调用
```

三处设计质量高于其余部分，**v3 明确不改**：三段式系统提示保缓存、按"完整步"裁剪、只读并行但保序。

### 4.2 工具闸门：三层守卫，两层是空的

```
模型 tool_call
 → scopedRegistry.descriptor（只认本回合可见）
 → ① 未启用 → tool_not_enabled
 → ② FailureGuard.check()            ← 生产上唯一真在跑的守卫，有 Allow（DuplicateGuard 性质）
 → ③ AgentSeams.denyOutcomeOrNull()  ← 已接（RealAgentLoop.kt:901），但 seams 恒为 NONE
 　   └─ ToolGuardChain.check()      ← 有实现、无守卫、零装配
 → ④ 审批（真源 ToolCatalog，57 条；通道缺失 → no_approver 拒绝）
 → ⑤ 副作用登记 DISP，写不进则拒写
 → ⑥ 执行（只读 90s / 写 600s，按调用取 min）
 → ⑦ truncateToolResult → ToolMessage 回灌
```

**判定**：三层里第②层是"重复/失败熔断"，不是策略守卫；第③层是空链；第④层是唯一真正在挡人的。
所以"守卫只能收窄执行集合"这条安全性质**目前没有生效对象**——它保护的是一个 `emptyList()`。

**一个已知旁路**：`SkillRuntimeBridge` 直接调 `executor.execute`（`SkillExecutor.kt:452`），不走 `executeOne`，
所以即使将来把守卫接上，技能脚本的 `writeFile` 仍然绕过它。

### 4.3 取消语义（部分修）

| 终态 | 含义 | 现状 |
|---|---|---|
| `ok` | 真实结果保留 | ✔ 成功卡不再被改写 |
| `cancelled_unknown` | 已越过执行边界、结果未知 | ✔ 可达 |
| `not_dispatched` | 从未越过执行边界 | ✗ 活路径不可达：取消只调 `onInterrupt`，写了就判 Unknown |

判据（沿用 v2 并加一条）：3 个串行写替身，第 2 个执行中取消 → #1 成功、#2 unknown、#3 **not_dispatched**；
扩展判据：5 个写的批次在第 2 个后取消，后 3 条终态必须是 `NOT_DISPATCHED`，且无一条 `unknown`。

### 4.4 执行后端

链条唯一：`proot → shizuku → adb → user`；`TerminalIdentity` 带 `uid` + `satisfies()`，身份维度成立。
今天真正高于 App 身份的只有 uid 2000 一档，两个独立入口——"无 root"在实现上自洽。

已修：同别名并发 `open`（A-4）、超时按调用传入（A-5）、租约双闸互斥（B-8）。
未修：死会话识别（A-6，`desynced` 是死分支）、回执不可归因（B-10，五套回执并存、`errno` 零命中）、
包管理器闸门只覆盖一条路径（B-9：`shell_run` 进 proot、交互终端里的 `apk add` 不过闸）。

**头号缺陷**：`AdbTerminalBackend.isAlive = !closed && stream != null`（`:76`），而 `readLoop` 在 `null`/`Exit` 帧上
`break` 后既不置 `closed` 也不清 `stream`（`:120-145`），只有 `release()` 才置。配合池的复用分支与 20 分钟预算，
**无线调试端口一变，后续每条命令都白等到超时**。pty 同病（`TerminalSession.kt:84`）。

### 4.5 语音：一条干净的链，两个后门

回落链（纯函数，四条不变量）：

```
online → [online, local, system]
local  → [local, system]          ← 不回在线：他选本地就是要离线
clone  → [clone, local, system]   ← 回声失败换内置，不偷偷联网
system → [system]                 ← 别替他升级
```

离线承诺成立 ✔：LOCAL/CLONE 链不查网，Edge 失败即继续下一环（`VoiceSpeech.kt:116-118`），
三环全败才失败且文案具体（`TextSpeaker.kt:309-313`）。

**但"唯一持有者"在接缝处不成立，失守点正是当初要修的那个场景**：

| 后门 | 证据 | 后果 |
|---|---|---|
| `ChatScreen.kt:252` 自建 `TtsController` 朗读消息 | 不经 `TextSpeaker`、不申请 Speak 租约；`:274-284` 的麦克风入口也不停它 | 点朗读 → 点麦克风 → Capture 拿到时系统 TTS 还在念，**识别结果录进 AI 自己的声音**。这正是 `MicClaim.kt:76-78` 点名要修的场景 |
| `VoiceRecorder.record`（`VoiceRecorder.kt:53-138`） | 经 `VoiceCloneScreen.kt:98` 直接 `AudioRecord`，不申请租约、不看 `ExternalBusy` | 克隆录音页与任何播报/识别可并发开麦 |

kernel 侧 harness 100% 通过而线上仍错，因为失守发生在 harness 明确声明"不测"的那一层
（`VoiceArbiterVerification.kt:19-22`：AudioManager 探测与 UtteranceProgressListener "由代码审查保证"）。
**这是分层验收判据本身的问题，不是实现疏漏。**

其他三处：
- `AsrRouter.active` 硬编码"准的优先"（`AsrRouter.kt:21-25`）且刻意不落盘 → **用户并不存在"更快/更准"的选择**，
  装了 paraformer 后 24MB 流式永不启用，而音色页还在劝用户删它；
- `LocalVoiceEngine.release()` / `ZipVoiceEngine.release()` 都不持 mutex（`:87-91` / `:111-115`），
  会与 `generate` 抢同一句柄，造成 use-after-free（仅 `reset` 可触发）；
- ASR 的 build **没有** `NativeStderr.install()`（只有两个 TTS 装了），所以 ASR 原生失败仍只剩
  "识别器创建失败：Invalid…"，诊断报告也不含 native 段。

### 4.6 模型下载通道

| 环节 | 结论 |
|---|---|
| zip slip | ✔ 拒 `..` + canonicalPath 前缀双保险 |
| 解压炸弹 | ✔ 按实际写出字节封顶 `zip.length()*4+64MB`，不信声明尺寸 |
| 符号链接 | ✔ `ZipInputStream` 不创建链接，条目只落成普通文件 |
| 完整性 | ✖ 只覆盖整包；就绪判定只查 `length>0`；**清单无签名** |
| 信任根 | ✖ 清单与 zip 同走 `GitHubMirror` 的第三方前缀，且 tag 是 `latest`——同一代理可自洽投递任意包 |
| 多源降级 | ✖ 顺序 ghfast.top → gh-proxy.com → 直连，两个第三方优先；`.part` 无字节上限 |
| 原子性 | ○ `.new` → 校验 → 换名在单次运行内安全；但 `dest→.old` 与 `.new→dest` 之间被杀会留下 dest 缺失 + `.old` 永久滞留，下轮又删掉完整的 `.new` |
| 删除 | ✔ 路径由枚举常量拼出，只删该目录（无 canonicalPath 归属校验，纵深不足） |

> `ModelSpec` 现在是 **6** 项（2 识别 / 2 音色 / Alpine / Shizuku），不是文档写的"四套语音模型"。

### 4.7 落盘与恢复

```
persist: 写脏分片（tmp→fsync→.bak→rename）→ 写 index
load   : index + .bak → 逐分片 readShard → mapNotNull（缺则静默丢）
```

A-7 未修的具体形态：`persist` **在写之前**就 `clear` 了 dirty/removed，`writeShard` 返回 0 被 `if(n>0)` 吞掉，
index 仍无条件重写 → 写失败的分片变成 index 里的死 id，**重启后静默消失，且永不重试**。
目录里多出的分片只有 index 全坏时才被收编。

### 4.8 自动续跑（11-14 落地，但有时序洞）

`ChatViewModel.kt:1046-1054` 的 init 里：

```
runStateReady.complete(interrupted)      // :1052  先放行
runCatching { recoverInterruptedJournal() }  // :1053  后扫描，内部再 launch
```

而 `pendingRecoveryNote` 在 `:1137` 才被赋，`:2733` 才被 `send()` 消费。
自动续跑在 `:3694` 等 `runStateReady` 后立刻 `send()` → **note 必为 null**。
续跑的首条请求因此只有"继续" + 纯文本历史（`:2644-2663`，不含 `tool_calls`），
模型看不到"上一次那条写可能已经生效"，自然会重做。

熔断（`AutoResumePolicy.kt:136-207`：attempts≤2、24h、输入非空不跑）只防"同一任务反复被杀"，
**不防"同一副作用做两次"**——幂等事实上为零。

## 9. 演进路线

### 9.1 排序原则

## 10. 质量体系

### 10.1 六条门禁的实际判别力

| # | 判据 | 判别力 |
|---|---|---|
| 1 | `known-broken.txt` 归零 | ✔ 强 |
| 2 | 汇总 `FAIL=0` 且无 `ENV STALE` | ✔ 强 |
| 3 | 无 XPASS | ✔ 中 |
| 4 | 每个 `*Verification.kt` 被引用；`ran ≥ runner` | ✔ 强 |
| 5 | `PASS ≥ 基线` | ✘ **失效**：`SKIP>0` 整条短路（`gate.sh:145`）；基线文件里有两行裸数字（142 / 143），`awk` 取首行 |
| 6 | 每个 SKIP 登记、无僵尸、条目 ≤42 | ✔ 中：只比名字，不核理由 |

另：不带日志参数时只做第 1 条，结尾照样打印 `GATE PASS`；日志编号 `1/5…6/6` 混用（表述问题）。

### 10.2 三个结构性弱点

**一、门禁 5 让位给门禁 6，而门禁 6 只核"登记过"。** 任一登记项改成首行 `echo KS_HARNESS_SKIP …; exit 3`，
`skip_claim_is_true` 取不到绝对路径就放行，门禁 6 见名字已登记且 cap 未变 → `GATE PASS`。
v2 的 A-15 只是把"任意新增"收紧成"登记后合法"。

**二、断言锚在文件路径。** 626 条 `assertContains` 里有大量 `readSource("ui/ChatViewModel.kt")`。
一旦拆分，要么改成全树 grep（退化成存在性检查），要么全红。这是 P1 必须先做的原因。

**三、文档是第三种真源。** README（369/89,998/142、工具面 22,360/10,055）、
HANDOFF（782 提交 / 141 runner / 基线 141）、DEPENDENCIES（一条推理栈）三份都与实测不符。
文档不参与门禁，所以它永远滞后——`README.md:40-49` 的能力一览里**零命中"语音"与"桌宠"**。

顺便记一条：`scripts/qa` 里对 7 个已删类的引用**都是反向断言**（"类不得出现在包内"），
没有指向不存在目标的假绿 ✔——这一轮清理做得比 v2 记的"断言指向不存在类名"干净。
