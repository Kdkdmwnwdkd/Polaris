# 审计 F15：读通知的授权粒度停在「工具」这一层

**日期**：2026-11-11
**范围**：`core/src/main/java/com/beichen/polaris/core/agent/`（`ApprovalScope` / 新增 `NotificationScope`）、`app/src/main/java/com/beichen/polaris/automation/`（`DeviceNotificationsTool` / `NotificationStore` / `AgentNotificationListener`）
**PR**：[#16 通知按应用授权](https://github.com/Kdkdmwnwdkd/Polaris/pull/16)

---

## 一、缺陷

F9 给 `device_notifications` 加了审批，F11 又把「通知正文自动拼进每条消息」那条暗道堵了。两条都做完之后，「读通知要授权」看起来已经成立：

- 工具 `needsApproval = true`；
- 归组 `Approval.PRIVATE_READ`，弹窗有中文文案；
- 自动注入那条路只传来源与时间。

但这个审批的**粒度**是「这个工具」：

```kotlin
// ApprovalScope.kt（修前）
key = "${ApprovalGrouping.GROUP_PRIVATE_READ}:$toolName",   // private_read:device_notifications
memorizable = true
```

而工具本身没有参数：

```kotlin
// DeviceNotificationsTool.kt（修前）
override val parameters = JsonSchema.objectSchema()          // ← 空
override suspend fun execute(args: JsonObject): ToolResult {
    val list = NotificationStore.all                        // ← 最近 60 条，全部应用
```

两段各自都对。合起来的语义是：

> 用户在弹窗上勾一次「本次会话不再询问读取通知」，同意的是——**本会话内，任意次，读取全部应用最近 60 条通知**。

用户心里那句话通常不是这个：

| 用户以为同意的 | 实际同意的 |
|---|---|
| 读**一次** | 本会话内**任意次** |
| 只读**微信** | **全部应用**：短信验证码、银行推送、私聊、邮件 |
| 只读「刚才那条」 | 缓存里**所有**历史通知（60 条） |

这不是「少弹了一次窗」，而是**弹窗承诺的范围与实际读取的范围不是一回事**。

## 二、和 R-08 是同一个病

R-08 修过 `shell` 的组键：用户为 `npm install` 勾了「不再询问同类操作」，之后 `rm -rf` 也不再问。当时的结论是——

> 根因不是「少了一个判断」，而是审批键与风险的粒度对不上：组键描述的是**工具类别**，而用户同意的是**这一次的风险**。

R-08 把范围编进了键：网络按**域名**（`network:api.example.com`）、shell 读按**目录**（`shell_read:/sdcard/DCIM`）、不可逆命令**永不记忆**。

私有读这一档当时只做到「按工具」就停了：

```kotlin
// ApprovalScope.kt（F9 的版本，注释里自己写着）
// 粒度按工具：同意读剪贴板不等于同意读通知（一个是「我刚复制的那段」，
// 一个是「此刻手机在响什么」，后者的范围用户很难想象）。
```

「后者的范围用户很难想象」——这句话是对的，但结论下反了。**用户想象不出的范围，就不该给一个能记住的授权**。正确做法不是「把范围写进注释」，而是「把范围写进键」。

## 三、修法

### 3.1 工具说清读谁

`packages` 可选参数（最多 8 个）；不传就是全部：

```kotlin
override val parameters = JsonSchema.objectSchema(
    "packages" to JsonSchema.Property(
        type = "array",
        description = "只读这些应用的通知（Android 包名，如 com.tencent.mm）。最多 8 个。" +
            "不传 = 读取全部应用（每次都会单独确认）。",
        items = JsonSchema.Property(type = "string", description = "应用包名")
    ),
    required = emptyList()
)
```

### 3.2 键里带上范围

```kotlin
// NotificationScope.kt（新增，纯函数、零 Android 依赖）
fun keyOf(filter) = when (filter) {
    is Named  -> keyPrefix() + filter.packages.sorted().joinToString(",")  // …:com.tencent.mm
    All       -> keyPrefix() + "*"                                        // …:*
    is Invalid-> keyPrefix() + "!"                                        // …:!
}

fun memorizable(filter) = filter is Named    // 只有点名了应用才能「本次会话不再询问」
```

三档对应的可记忆性：

| 输入 | 键 | 可记忆 | 理由 |
|---|---|---|---|
| `packages: [com.tencent.mm]` | `…:com.tencent.mm` | 是 | 范围明确：用户知道自己批的是微信 |
| 不传 / `null` / `[]` | `…:*` | **否** | 范围不可界定，记住它 = 以后随便读 |
| 脏项 / 超过 8 个 | `…:!` | **否** | 工具直接报错，不猜 |

第 2 行是整条修法的兜底：**只要「全量不可记忆」成立，任何解析上的降级都不会退化成「一次授权、以后随便读」。**

### 3.3 不静默截断，也不静默放大

范围写坏（数组里混了数字、给了对象、超过 8 个）时，两种省事的做法都是错的：

- **截断取前 8 个**：弹窗写「8 个应用」，实际模型以为读了 20 个——两边说的不是一件事；
- **当成全部**：把一个格式错误放大成全量放行。

所以直接失败：

```kotlin
if (filter is NotificationFilter.Invalid) {
    return ToolResult.fail(
        code = "notifications_bad_scope",
        message = "读取范围无法识别：${filter.reason}",
        hint = "packages 传应用包名数组，例如 [\"com.tencent.mm\"]，最多 8 个；不确定包名先用 app_list 查。"
    )
}
```

### 3.4 唯一真源：审批算的范围 = 读取用的范围

这是整条修法里最容易做假的一处。只改键不改过滤，结果是「弹窗写着微信，实际 60 条全读走」——用户看着一个更精确的弹窗，拿到的却是和以前一样的范围。**比不修更糟**：它让用户以为自己已经收紧了。

所以两处都调同一个纯函数：

```kotlin
// ApprovalScope.of(...)
val filter = NotificationScope.parse(args)
return ApprovalGrant(
    key = NotificationScope.keyOf(filter),
    label = NotificationScope.labelOf(filter),
    memorizable = NotificationScope.memorizable(filter)
)

// DeviceNotificationsTool.execute(...)
val filter = NotificationScope.parse(args)
val list = if (filter is Named) NotificationStore.byPackages(filter.packages)
           else NotificationStore.all
```

同一个 `args` → 同一个 `NotificationFilter` → 同一个集合。不是「两边各算一遍但愿算得一样」，而是**在构造上没有第二处算法**。

### 3.5 顺带把数据源拆出来

`NotificationStore` 原先寄生在 `AgentNotificationListener.kt` 里，而那个文件 import 了 `NotificationListenerService`——整个文件在 JVM 上编不过，于是「按应用过滤」这件事只能靠 grep 静态断言。

现在它独立成 `NotificationStore.kt`（只依赖 `ConcurrentLinkedQueue`），过滤函数可以被行为断言直接驱动：灌 4 条通知、按微信过滤、数出来必须是 2 条。

## 四、不变量（写进 harness，改坏就红）

1. **键里的包名集合 == 实际读到的包名集合**（`D1`/`D2`：同一个 args，一边解键、一边真读，逐项相等）；
2. 全量读取不可记忆（`B4`），且勾选框**不能**写「本次会话不再询问」（`C4`）——写了就是骗人；
3. 跨应用不互相放行（`D7` 批微信不放行短信；`D8` 范围变大要重问；`D9` 授权不向下拆）；
4. 升级前写进白名单的老键 `private_read:device_notifications` 不再命中任何新键（`B7`）——宁可多问一次，不能让老授权自动升级；
5. 空集合 fail-closed（`D6`）：读不到 优于 读到全部；
6. 功能没被砍（`D4`）：不传 `packages` 仍然读全部，只是要每次确认。

## 六、没做的事

1. **没有做「永久允许读某应用」**：现在的最长记忆是「本次会话」。再往上需要设置页 + 持久化白名单，而且「永久」与「一次会话」的风险量级不同（用户换手机、换账号、装了新应用之后，那份白名单还在），应当作为独立设计，不能顺手塞进这次。
2. **弹窗里显示的是包名，不是应用名**：`ApprovalScope` 是 core 层的纯函数，拿不到 `PackageManager`。`com.tencent.mm` 不如「微信」直观。要修得把「包名 → 应用名」的解析放在弹窗渲染层（UI 侧已有 `Context`），而不是给纯函数塞 Android 依赖——留给审批 UI 那一条线。
3. **`ConfigStore` 明文存 Key**：需要产品决策（Keystore 可用则加密 + 明文回退），且必须真机验证，不在本轮。
