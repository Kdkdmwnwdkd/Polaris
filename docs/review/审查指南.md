# 北辰代码审查指南

给**没有上下文**的审查者（人或模型）的入口文档。目标：半小时内能判断这个仓库
的约束是什么、最近改了什么、哪里最可能藏问题，以及怎么验证自己的判断。

写这份文档的原则：**先给自查结论，再给可疑点**。凡是"我知道有风险但没解决"的，
都写在第七、八节，不藏在措辞里。

---

## 一、这是什么

Android 应用，定位是本地 LLM Agent：手机里跑 llama.cpp（GGUF）+ 自写 JNI 桥，
可选接云端供应商（OpenAI / Claude / Gemini 兼容协议）；Agent 能通过无障碍服务、
Shizuku、adb、proot 四条通道操作设备。

| 项 | 值 |
|---|---|
| 语言 | Kotlin 1.9.25，Compose（BOM 2024.09.00） |
| 模块 | `:core` 35,131 行 / `:app` 41,998 行，共 414 个 `.kt` |
| minSdk / targetSdk | 26 / **28**（故意，见第五节） |
| 构建 | Gradle 8.5 + AGP 8.5.0 + NDK 26.3 |

## 二、目录与分层

```
core/src/main/java/com/beichen/polaris/
├── core/        LLM 客户端、会话存储、任务、构建、时间源
├── skill/       JS 技能执行（Rhino）
└── terminal/    PTY / proot / shell 会话

app/src/main/java/com/beichen/polaris/
├── ui/          界面 + ViewModel + 20 个 Contract 实现
│   └── contract/    ★ 界面契约，只加不改签名
├── automation/  无障碍、Shizuku、adb、UiNodeMatcher
├── tools/       Agent 工具实现
├── runtime/     推理引擎生命周期
├── memory/      长期记忆存储与检索
├── workflow/    WorkManager 定时任务
└── startup/     启动序列
```

依赖方向只有一个：`app → core`。`:core` 不得反向依赖 `:app`，也不得依赖 Compose /
WorkManager / Shizuku / ML Kit。

## 三、六条硬约束

改这个仓库之前必须知道。每条后面是"违反时哪道门禁会红"。

| # | 约束 | 违反了会怎样 |
|---|---|---|
| 1 | `ui/contract/` 里的接口签名只加不改 | 编译失败（20 个实现类同时不满足） |
| 2 | `:core` 不引 `android.*`、不引日志设施 | `r06` / `r10` 等 harness 以"逐个列源文件、纯 JVM 自编译"的方式跑，多一个依赖就编不过 |
| 3 | `:core` 里带可变成员的 `object` 必须登记进 `AppGraph` | `run-appgraph` 双向对账转红（当前期望 23 项） |
| 4 | `scripts/qa/arch-baseline.txt` 的行数上限**只准下调** | `run-arch-guard` 转红；上调必须在文件头写明理由 |
| 5 | 文本断言只减不增（当前 1368 条 / 53 文件） | `run-assertion-census` 转红 |
| 6 | 每个改动一个提交，可单独 `git revert` | 不是自动检查，是协作纪律 |

第 2 条最容易踩：`ConversationStore` 里删掉一行 `AgentLogger.w(...)` 就是为此——
日志改由宿主 `ChatViewModel.noticeHistoryTruncated` 记，丢弃量通过返回值传出去。

## 四、质量保障的真实形状

85 个 `*Verification.kt` harness、115 个 runner。听起来很多，但要看清它在守什么：

| 断言类型 | 条数 | 能抓到 | 抓不到 |
|---|---|---|---|
| 源码文本（`assertContains`） | 1,368 | 代码被搬到别处、常量被改 | 逻辑写错但字符串还在 |
| 条件表达式（`assertTrue`） | 约 1,800 | 同上 + 部分行为 | "阈值写错一位""超时判断反了" |
| 真行为（调被测函数） | 十余条 | 输入输出正确性 | 并发、时序 |

**这是已知的最大短板**：一半以上的断言在守"这句话还在不在文件里"。它对纯搬迁
（拆模块、抽 facade）极其有效，对逻辑错误几乎没有分辨率。

已有行为断言的三个纯函数类：`UiNodeMatcher`（Hotfix3）、`BackupArchive`（W26，4 条）、
`ConversationStore`（Branch，1 条）。都在纯 JVM 上跑，不需要 Android。

## 六、明确的取舍（不是遗漏）

| 事项 | 决定 | 理由 | 什么时候该翻案 |
|---|---|---|---|
| 时钟用 `System.nanoTime` 而非 `elapsedRealtime` | 保留 | `:core` 不能引 `android.*`；休眠不计时是刻意的产品语义 | 需要"息屏也计时"时，改 `Monotonic.DEFAULT` 一行 |
| 流式逐 token 投影 | 不改 | 要动 `StateFlow<String>` 契约 + 帧级节流，属界面层独立改动 | 真机实测打字机卡顿 |
| 建 `src/test` + JUnit 源集 | 不建 | 现有 harness 已能在纯 JVM 跑纯函数；再加一套框架增加 CI 依赖 | 需要 mock Android 依赖时 |
| 200 轮上限 | 不改 | 问题从来不是"有上限"，是"删了不说" | 用户实际撞到上限 |
| `targetSdk = 28` | 保留 | ≥29 禁止从应用数据目录 `execve`，proot 直接失败 | proot 改用其他入口 |
| 会话截断只提示一次 | 保留 | 横幅已有，反复弹更烦 | 用户反馈"不知道又删了" |

## 七、建议重点审查的 8 个点

按下述顺序看，每条都写了"为什么可疑"和"什么算错了"。

### 1. 并发：`ui/GenerationRunController.kt` 的锁范围

本轮刚修过（第一版只给 `appendText` 加锁，`start` / `finish` / `syncDisplay` 在锁外）。
现在字段的 14 个读写点都在 `draftLock` 内。

**该怀疑什么**：`syncDisplay()` 在锁内调用 `isOwnerActive()` → `activeId()`，后者是宿主
传入的 lambda。如果宿主那个 lambda 又回调本类的方法，`synchronized` 可重入不会死锁，
但会重复执行。看 `ChatViewModel` 里 `activeId = { conversationId.value }` 是否真的只读。

### 2. 竞态：`ui/PermissionFacade.kt` 的两条写路径

`refreshShizukuStatus()`（协程，Main 上写三条 StateFlow）和 `refreshGrants()`
（`Dispatchers.IO` 上直接写同样两条）都会写 `_shizukuStatus` / `_shizukuInstalled`。
两者并发时"谁后写谁赢"，先发后至的旧探测可能覆盖新结果。

**该怀疑什么**：这是**既有**设计，不是本轮引入，但本轮把前者改成异步后窗口变大了。
判断标准：从 Shizuku 授权返回后，权限页是否稳定翻成"就绪"。这需要真机。

### 3. 有损操作：`core/ConversationStore.kt` 的截断

`appendToTurns` 超 200 轮 `removeAt(0)`，返回丢弃轮数。调用方 `ConversationProjection.appendToStore`
再把数传给 `ChatViewModel.noticeHistoryTruncated`。

**该怀疑什么**：`noticeHistoryTruncated` 里 `if (_truncationNotice.value == null)` 是
check-then-act，两个线程同时首次截断可能都写（后果只是文案重复覆盖，可接受但不干净）。
另外：提示只出一次，之后继续丢不再提示，是否符合预期。

### 4. 时钟：`core/time/Monotonic.kt` 的替换是否都成对

原则是"成对时间戳必须同源"。已核 9 处：`JobRunner`（轮询）、`LocalLlamaClient`
（重试 join + 停滞看门狗）、`SkillExecutor`（脚本看门狗）、`BuildEngine`（CI 轮询）、
`AgentAccessibilityService`（窗口稳定等待）、`ShizukuShell`（exec）、`ChatScreen`
（审批倒计时）、`RealAgentLoop`（回合总预算）。

**后两处是交付前才补的**，值得说明原因：它们不是 `val deadline = now + X` 的形状，
而是**存一个起点、之后再相减**。按"找 deadline / timeout 变量"的方式扫，扫不到。

**该怀疑什么**：还有没有同形状的漏网。正确的扫描方式是

```bash
grep -rn "= System.currentTimeMillis() -" --include=*.kt app/src core/src
```

逐个看差值的用途：只用于 `elapsedMs` 展示的可以留（跨设备对照需要墙钟），
参与 `if (idleMs > budget)` 这类判定的必须换。

另外 `Monotonic.nowMs() + timeout` 这种**绝对 deadline** 写法，在 `nanoTime` 返回值
接近 `Long.MAX_VALUE` 时会溢出（Android 上实际不会，理论风险）。

### 5. 错误处理：`LLMClient` / `ClaudeClient` / `GeminiClient` 的空响应体

6 处 `body!!.string()` 改成显式判空 + `LlmHttpException`。`LlmHttpException` 是
`IOException` 子类，会走既有重试链路。

**该怀疑什么**：HTTP 200 但 body 为空时，重试是否有意义？现在会重试（继承自 IOException
分支），可能白白多打一次请求。Claude 的 `null` 保留给"400 缓存被拒 → 降级重发"，
看这个分支是否会被空 body 误触发。

### 6. 取消语义：`PermissionFacade` 的两处 `catch`

`catch (e: CancellationException) { throw e }` 在 `refreshGrants` 的电池白名单与
AppOps 查询上。这两处在 `scope.launch(Dispatchers.IO)` 里，捕获后重抛是正确的。

**该怀疑什么**：仓库里还有十余处 `catch (t: Throwable)`，多数在同步上下文（正确），
但值得逐个确认没有吞掉 `CancellationException` 的。`grep -rn "catch (.*Throwable" app/src core/src`。

### 7. 数据完整性：备份信封

`BackupArchive` 的 W26 新增 4 条负向契约：非白名单成员被忽略、版本过新被拒、条数不符
被拒、缺 `conversations` 成员被拒。

**该怀疑什么**：这 4 条用手工拼 ZIP 构造（用 `create()` 造等于拿被测函数验证自己）。
看拼出来的字节是否真的覆盖了想测的分支，而不是被更早的校验挡掉——那样断言会通过，
但没测到目标逻辑。

### 8. 构建：version catalog

`gradle/libs.versions.toml` 收口 5 个共用坐标。`:core` / `:app` 都改 `libs.*`。

**该怀疑什么**：`:core` 用 `api` 声明是为了让 app 侧能解析 core 公共签名里的 okhttp /
serialization 类型。如果某个依赖其实只出现在 core 内部，用 `api` 是过宽暴露。

沙箱环境限制，下面这些**没有做**，不要当成"已验证"：

| 项 | 状态 | 原因 |

**能做的验证都做了**：`run-all.sh` → PASS=66 / SKIP=48 / FAIL=0；文本断言 census
1368 条 / 53 文件不变；架构守卫 5/5。

语法上是最保守的写法；但仍应视为**未编译验证**。

## 十、给审查者的两个提醒

1. **注释极长是刻意的**。这个仓库的注释大量记录"这里以前怎么错过、为什么改成现在这样"
   （例：`GenerationRunController` 类注释的三条不变量、`Monotonic` 的休眠语义）。
   它们不是自我辩解，是防止下一次重构踩回去。看到长注释请当成设计文档读，不要当噪声。
2. **文本断言多不等于没测试**。这是一套为"大范围搬迁"设计的护栏：拆模块那六轮 CI
   失败里三轮是路径/常量拼接找不到文件，文本断言正是针对这类问题。它的盲区在第四节
   写明了，评估时请把两件事分开算。
