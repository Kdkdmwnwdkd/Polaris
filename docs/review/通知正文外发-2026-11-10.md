# 审计 F11：通知正文随每条消息自动外发

**日期**：2026-11-10
**范围**：`app/src/main/java/com/beichen/polaris/automation/`（通知监听 / 设备上下文）、`ui/ConsoleScreen.kt`
**PR**：[#12 通知正文外发](https://github.com/Kdkdmwnwdkd/Polaris/pull/12)

---

## 一、缺陷

F9 那一轮给 `device_notifications` 加了审批：「读通知」要弹窗，用户点了才读。看起来这件事做完了。

但通知有**两个**出口：

| 出口 | 谁发起 | 修前有没有审批 |
|---|---|---|
| `device_notifications` 工具 | 模型主动调 | 有（F9 刚加） |
| `DeviceContextStore` → 每条消息的上下文 | **App 自动** | **没有** |

第二个出口长这样：

```kotlin
// AgentNotificationListener.kt（修前）
val body = if (title.isNotBlank()) {
    if (text.isNotBlank()) "$title：$text" else title
} else text
DeviceContextStore.addNotification("$label - $body")     // ← 正文全在里面
```

```kotlin
// ChatViewModel.kt:2648
val ctxPrompt = DeviceContextStore.snapshot().toPrompt()  // ← 每条消息都拼进去
```

两段代码都在自己的上下文里完全正常：监听服务「把通知摘要同步给设备上下文」是设计目标，对话层「让模型知道手机在干什么」也是 L4 主动感知的设计目标。**问题出在两段之间的连接处**：一个把正文传了过去，另一个把它拼进了模型请求。

后果：

- 用户一旦在系统里开了通知访问权限（这是使用自动化功能的前置），此后收到的**每一条**通知——验证码、私聊、银行推送——都会自动进模型上下文；
- **每条**用户消息都带一次，不是一次性的；
- 模型不用做任何事，用户不用点任何东西；
- F9 的审批在这条路上完全不生效，因为压根没有工具调用。

也就是说：**F9 修的是「模型去读」，但正文本来就自己会到。**

## 二、为什么这类缺陷不会被「测」出来

它不报错、不崩溃、界面正常、日志正常。唯一的表现是「本该弹的那次授权，从来没有发生过」——而这件事**没有观察点**：

- 用户视角：Agent 突然很懂「你刚才收到的验证码」，认为它很聪明；
- 开发者视角：`device_notifications` 的审批代码在、测试在、断言在；
- 日志视角：没有工具调用记录，也谈不上可疑。

这正是审计里最该抓、又最难自动抓的一类：**两个各自正确的模块接线接错**。

## 三、修法：不收集，而不是收集后过滤

两种改法：

| 方案 | 做法 | 漏点 |
|---|---|---|
| 出口过滤 | 照样存全文，在 `toPrompt` 里过滤掉 | **每个出口**都得写对。将来多一个出口（日志、导出、调试面板、崩溃上报）就多一个漏点 |
| 不收集 | `DeviceContextStore` 根本不接收正文 | **只有一处**需要写对：监听服务不构造它 |

选了后者。落点是一个新类型：

```kotlin
// NotificationDigest.kt
data class NotificationSummary(
    val packageName: String,   // 用于聚合
    val label: String,         // 展示用应用名
    val postTime: Long         // 投递时间
)                              // ← 没有 content / text / title
```

`DeviceContextStore.addNotification(summary: NotificationSummary)`——参数从 `String`（什么都能装）改成结构体（装不下正文）。队列也从 `ConcurrentLinkedQueue<String>` 变成 `ConcurrentLinkedQueue<NotificationSummary>`。

**类型上装不下，就没人能顺手塞回来。** 这比在方法体里加一行 `filter` 强得多：后者下一个人重构时很容易绕开，前者绕不开。

### 顺带：注入的内容反而更有用

修前是 8 行「应用名 - 标题：正文」，占上下文又没信息量。现在是聚合摘要：

```
[当前设备上下文]
- 前台应用：微信 (com.tencent.mm)
- 最近通知：微信 ×2（2 分钟前）、支付宝（40 分钟前）、短信（3 小时前）
  （这里只有来源与条数，没有正文。需要内容请调用 device_notifications，会向用户申请授权。）
```

第二句不是客套。模型看到「微信 ×2」极容易顺势编出「它说了什么」，而它其实什么都没看到——**编造比拿不到更危险**。把边界写在数据旁边，比写在系统提示的某个角落更有效。

## 四、不变量（写进 harness，改坏就红）

1. 注入文本里不含任何正文片段（`A3`：验证码 / 123456 / 在吗 / 转账 / 元 / 标题，一个都不许出现）；
2. 注入文本必须**明说**「没有正文」（`A4`）；
3. `NotificationSummary` 的字段里不能有正文位（`D1`：反射查 `text`/`title`/`content`/`body`/`message`/`summary`）；
4. `DeviceContext.recentNotifications` 的元素类型是 `NotificationSummary`，不是 `String`（`D3`）；
5. 自动注入链路必须仍在（`W6`）——**把整段删掉也能让上面全绿，但那是砍功能不是修缺陷**；
6. `NotificationStore` 仍存全文（`W7`）——正文不能跟着一起被删，`device_notifications` 还要读它。

第 5、6 条是这次特意加的：一个只验证「坏东西没了」的 harness，会奖励「把功能删光」。

## 五、验证

| 项 | 结果 |
|---|---|
| 新增 runner | `run-notification-body-leak-verification.sh`（**42 行为 + 8 接线 = 50**） |
| 变异 ①：给 `NotificationSummary` 加回 `text` 字段 | D1 变红，退出码 1 |
| 变异 ②：删掉「没有正文」的声明 | A4 变红，退出码 1 |
| 变异 ③：监听服务改回 `addNotification("$label - $body")` | W1/W2 变红，退出码 1 |
| 变异 ④：连 `NotificationStore.add` 一起删掉（过度修） | W1/W2/W7 变红，退出码 1 |
| 既有 harness | arch-guard 5/5、文本断言 1729 → 1729（未增） |
| harness 基线 | 131 → 132 |

harness 真编真跑（`NotificationDigest.kt` / `DeviceContext.kt` 零 Android 依赖，沙箱与 CI 都不 SKIP）。为此把 `DeviceContext` 从 `DeviceContextStore.kt` 里搬了出来——后者 import 了 `android.content.Context`，整个文件在 JVM 上编不过，而 `toPrompt` 正是「决定什么内容进模型请求」的那个函数，它必须能被行为断言。

## 六、没做的事

1. **不做「按应用过滤通知」**：用户可能只允许读某几个 App 的通知。这需要 `NotificationStore` 按包名查询 + 一份持久化的白名单设置，是一次独立改动，且属于「粒度优化」而非「漏洞」——当前的洞是「根本不问」，先堵这个。
2. **不动前台应用包名**：`DeviceContext` 仍自动带上「你在用哪个 App」。F9 已判定 `device_foreground_app` 只给包名、不含内容，敏感度与通知正文差一个量级；并进同一档只会多一次无意义弹窗。
3. **不给 `DeviceContextStore` 加开关**：有人会问「能不能让用户选择要不要注入」。能，但那是在「已经安全的默认」上加一个「变得更宽松」的选项，优先级远低于此，且需要一套持久化设置。现在的行为是：**注入元信息，永不注入正文**——没有需要用户决策的地方。
