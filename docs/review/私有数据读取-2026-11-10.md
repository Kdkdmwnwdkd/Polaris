# 私有数据的读取审批（W-56）

> F7 修的是「读文件的路」，这一轮修的是「没有路的读」。

**基线**：`1afdd56`（main，PR #8 合并后）
**对应问题**：`clipboard` / `device_notifications` 读用户私有数据，零审批

## 一、问题：两个工具从来没有问过

审计 F7 修的是「`shell_run` 一条 `cat` 绕过工作区沙箱」——判据落在**路径**上（`/sdcard`、`/data/data`）。
但有两类工具根本没有路径可判，因为内容本来就在内存里：

| 工具 | 读到的东西 | 审批 |
|---|---|---|
| `clipboard action=get` | 用户刚复制的密码、验证码、卡号 | **无**（`needsApproval` 默认 false） |
| `device_notifications` | 此刻手机在响什么：验证码短信、聊天正文、银行推送 | **无** |

`AgentTool.needsApproval` 的默认值是 `false`，这两个类都没有覆写它，`ToolCatalog` 里
也没标归组键。于是：

```
模型调 clipboard(get) → 剪贴板内容进上下文 → 随下一次请求离开本机
                        ↑ 用户看不到任何一步
```

而 `device_notifications` 更彻底：它的 description 写着「当用户问『有没有新消息』**或需要上下文时**调用」——
「需要上下文时」这句话把判断权整个交给了模型。

`PathGuard`、`EndpointPolicy`、`ShellCommandRules` 三条判据都够不着它们：
一个没有路径、一个不是网络、一个不跑命令。

## 二、做法

### 2.1 与 F7 同族：粒度对得上风险

「读」是 Agent 的本职，拦不住也不该拦；能拦的只有**读的那一刻让用户看见**。

| 档 | 粒度 | 理由 |
|---|---|---|
| F7 工作区外文件 | 按**目录**（`/sdcard/DCIM`） | 同意读相册 ≠ 同意读 `/data/data` |
| **F9 私有数据** | 按**工具**（`private_read:clipboard` / `private_read:device_notifications`） | 一个是「我刚复制的那段」，一个是「此刻手机在响什么」，后者范围大到用户很难想象 |

两档都**可记忆**（「本次会话不再询问读取剪贴板」）。这与 shell 的破坏类命令不同：
读是一次性的、可撤销的（下一次对话就重新问），而 `rm -rf` 是永久的。

### 2.2 写入不拦

`clipboard action=set` **不弹窗**。三条理由：

1. 它把内容**放到**用户手上，没有把用户的秘密送出去；
2. 弹窗会出现在「模型帮你复制一段文本」这种完全无害的场景里；
3. 每一次无害弹窗都在训练用户闭眼点「允许」——真正危险的那次就更没人看。

未知 action（`dump` 之类）按**读取**处理（fail-closed），而不是当写入放过。

### 2.3 目录标注 + 归组分档，两层都要

- `ToolCatalog`：`clipboard`、`device_notifications` 标 `Approval.PRIVATE_READ`
  ——没有这一层，弹窗会显示裸键 `private_read`；
- `ApprovalScope`：把组键细化成 `private_read:<工具名>`
  ——没有这一层，同意读剪贴板会顺带放行读通知。

变异验证正好证明了这两层的关系：去掉 `ApprovalScope` 那一层后，键从
`private_read:clipboard` 退化成 `private_read`，6 条断言变红。

### 2.4 顺带修了一处守卫盲区

`run-r13-catalog-verification.sh` 的 B4 判据是「要审批的工具必须在目录里声明归组」，
而它只认 `override val needsApproval = true` 这一种写法。两种工具被漏掉：

- `override fun needsApprovalFor(...)`（`shell_run` / `clipboard`——按入参决定）；
- `override val needsApproval: Boolean = true`（带显式类型标注）。

也就是说，**`clipboard` 这种写法下「弹窗文案退化成裸工具名」这条守卫完全失效**。
现在两种写法都纳入，工具数从 18 变 20（`shell_run` / `shell_background` / `clipboard`
本来就在弹窗，只是守卫看不见）。

### 2.5 F9b：读屏的第二个入口

同一族缺陷换了张脸。`ocr_image` 有两个来源：

```
ocr_image(path="screenshots/a.png")  → 读工作区里的文件（PathGuard 管，与 read_file 同档）
ocr_image()                          → 截当前屏再识别 —— 这就是 ui_screenshot 做的那件事
```

修前它 `needsApproval` 默认 `false`。于是「用户拒了截图」这条防线上留了一道侧门：
模型改用 `ocr_image` 就能拿到同样的内容，而且**产出是纯文本，比图片更容易随下一次请求外发**
（图片还得挂视觉模型，文本直接进上下文）。

修法与 F9 同构，但粒度取向相反——**归组按动作，不按工具**：

| 做法 | 后果 |
|---|---|
| 给 `ocr_image` 单开一档 | 同一个「读这块屏幕」，在工具 A 上同意过，换了工具 B 还要再问一遍 |
| **共用 `Approval.UI_SCREENSHOT`**（本轮） | 用户同意的是「读这块屏幕」，不是「用某个特定工具读」 |

传了 `path` 不问：读的是工作区内的文件，边界由 `PathGuard` 管，与 `read_file` 同一档——
给「读一张自己的图」加弹窗，只会稀释真正该拦的那次。

顺带更正上一版报告里的一句话：原先写「`ocr_image` 不拦，因为图是用户主动给的」——
这句话对 `path` 分支成立，对**不传 path 的截屏分支不成立**，而后者才是默认用法。

## 三、不变量（写进 harness，改坏就红）

1. 同意过 `shell` 组 ≠ 同意读剪贴板（F1）；
2. 读过相册（`shell_read:/sdcard/DCIM`）≠ 同意读通知（F2）；
3. 批准过一次外发（`net_request:api.example.com`）≠ 同意读剪贴板（F3）；
4. `private_read` 与任何既有组名不重叠（F4）；
5. 同意读屏 ≠ 同意读剪贴板 / 通知，反之亦然（G3）。

## 五、没做的

1. **`device_foreground_app` 不拦**：只给包名，不含内容，隐私度与通知差一个量级；
   并进同一档只会多一次无意义弹窗。
2. **`ocr_image` 的能力分级仍是 `PRIVILEGED`**（`ui_screenshot` 是 `DANGEROUS`）：
   能力分级管的是「哪种信任等级的 skill 能调它」，审批管的是「这一次要不要问用户」。
   同一个工具两种用法（读工作区图 / 截屏）风险差一个量级，而分级不能按入参取——
   取宽的那个、让审批层做细粒度判断，比把「读自己工作区的一张图」也抬到最高信任更合算。
3. **通知的「按 App 过滤」没做**：用户可能只想让 Agent 看某些 App 的通知。
   当前粒度是「全读或全不读」，够用但不精细——需要 `NotificationStore` 支持按包名查询，
   是一次独立改动。
4. **审批弹窗不显示剪贴板内容预览**：显示内容等于把「要不要给它看」变成「已经给它看了」。
   预览只写长度（`execute` 的 message 里本来就是「已读取剪贴板（N 字符）」）。
